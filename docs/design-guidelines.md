# デザインガイドライン（app-expo）

**UI を追加・変更する前に、必ずここを読むこと。** ここは «見た目の正本» である。
Copilot Instructions / CLAUDE.md / codex 系の指示書はこのファイルを参照する形にし、
色や余白の具体値を他の文書へ複製しない（複製した瞬間からズレが始まる）。

参照実装は **検索タブの初期画面**（`app-expo/app/[locale]/(tabs)/index.tsx` 周辺）である。
「この画面のトーンに合っているか」が迷ったときの最終判定になる。

---

## 1. 色

### 基調はモノクロ＋灰。赤はアクセントであって基調色ではない

このアプリのブランド色（`#F05537`）は**「ここを押すと前へ進む」1 箇所**にだけ使う。
1 画面の中で赤を使ってよいのは、原則:

- 主 CTA（適用する / 保存する / ログインする など、画面に 1 つ）
- FAB（＋ボタン）
- 選択中チップの強調（背景 `#FDE7E1` + 文字 `#F05537`）

**使ってはいけない場所:**

- ナビゲーション（タブ・ビュー切替・戻る）。ここは黒 `#111827` / 灰 `#9CA3AF` で表現し、
  アクティブは **黒 + 下線**で示す（Instagram のストーリーズアーカイブの型）。
  実例: my-dishes のビュー切替（`app/[locale]/(tabs)/my-dishes/index.tsx`）
- 見出し・本文・アイコンの既定色
- 2 つ目以降のボタン（副 CTA は灰背景 `#F3F4F6` + 濃灰文字）

> 2026-08 実機レビューでオーナーから「赤を使いすぎ」という指摘が出ている。
> 迷ったら**まず赤以外で組み、最後に 1 箇所だけ赤を置く**。

### パレット（実コードで使っている値）

| 役割 | 値 |
| --- | --- |
| 文字・主 | `#111827` |
| 文字・副 | `#374151` / `#6B7280` |
| 文字・淡（プレースホルダ・非アクティブ） | `#9CA3AF` |
| 罫線・淡い背景 | `#E5E7EB` / `#F3F4F6` |
| ブランド（CTA のみ） | `#F05537`（淡: `#FDE7E1`） |
| 「食べたい」バッジ | 緑塗り `#2E7D32` + 白枠（文字は `#FFFFFF`） |
| 「食べた」バッジ | オレンジ塗り `#ED6C02` + 白枠（文字は `#FFFFFF`） |
| エラー | `#B91C1C` |

新しい色を発明しない。この表に無い色が要るときは、この表へ追加する PR にすること。

> **「食べたい / 食べた」は «色相» で区別する**（2026-09 オーナー指示。#1834）。
>
> 経緯: 2026-08 に «緑 / 赤の色相分け» をやめて «塗りの有無» にしたが、チームレビューで
> 「見分けにくい」と指摘され、**緑塗り（食べたい）/ オレンジ塗り（食べた）** に決まった。
>
> ⚠️ **区別が色相 1 本になったので、色以外の手がかりを削らないこと。**
> バッジには «食べたい» / «食べた» の文字を必ず添える。文字が入らない表示
> （カレンダーの点・地図の帯）は **凡例を必ず一緒に出す**（`MyDishStatusLegend`）。
>
> ⚠️ **どちらの塗りも明るくしない。** 上に載る白の文字・枠が読めなくなる
> （`#2E7D32` = 5.13:1 / `#ED6C02` = 3.11:1。UI 部品の下限は 3:1）。
> `statusBadges.test.tsx` が輝度比を機械検査している。
>
> 値の正は `app-expo/features/myDishes/statusColors.ts`（`fill` / `border` / `on` の 3 つ組）。
> 塗りの色だけを配ると「白地に白文字」を作れてしまうので、必ず 3 つ組で配ること。

## 2. タイポグラフィ

| 用途 | サイズ / 太さ |
| --- | --- |
| 画面タイトル・大見出し（例: カレンダーの「8月 2026」） | 20–22 / 700 |
| セクション見出し | 14–15 / 700 |
| 本文・チップ | 13–14 / 400 |
| 補足・説明（1 行の説明文） | 12–13 / 400、色は `#6B7280` |
| バッジ・カウンタ | 10–11 / 700 |

- 見出しは**消さない**。チップだけが並ぶ画面は「何をすればよいか分からない」
  （実機レビューで実際に指摘された）。小さくてよいので «何の話か» + «押すとどうなるか» を添える。
- ユーザーに見せる数値は読める単位にする（`5000m` ではなく `5.0km`、生の緯度経度を出さない）。

## 3. 余白・形

- 画面の左右余白は 16。カード内余白は 12–14。
- 角丸: カード 12 / チップ 16 / ボタン 8–14 / 円形要素は正円。
- チップは `#F3F4F6` 背景、選択中だけ `#FDE7E1` + `#F05537`。
- 押せるものは押せる見た目にする（チップ化・丸囲み）。押せない説明文と同じ見た目のボタンを作らない。

## 4. 画面の型

- **段取りのある画面**（取り込み・投稿など）は「導入 1 段落 + 番号付き手順カード」。
  実例: `app/[locale]/sns-import.tsx`（① URL を貼る → ② お店 → ③ 料理カテゴリー）。
- **主 CTA はスクロールの底に埋めない。** 常に見えるフッタに置き、押せない間は理由を 1 行添える。
- 空状態は「なぜ空か + 次に何をすればよいか」を必ず言う。案内文が指す導線
  （例:「地図の店舗をタップ」）が**その画面から実際に辿れる**ことを確認する。
- ラベルを言い直すだけの帯・バナーは置かない（例: 地図上の「このエリアで絞り込み中」は廃止した）。

## 5. プロセス: UI は自分でレンダリングして自分でレビューしてから納品する

コードを書いた ≠ できた。**スクリーンショットを撮って自分の目で見る**まで完了ではない。

1. `e2e-web/scripts/ui-preview.mjs` で対象画面を撮る（API・認証・地図・画像は全部モックで動く。
   使い方はファイル冒頭のコメント）
2. 撮ったものをこのガイドラインと突き合わせてセルフレビューする
   （色 / 見出し / 揃え / 押せるものの見た目 / 空状態）
3. 指摘され得る点を直してからもう一度撮る。**納品にはスクリーンショットを添える**
4. web で再現できない挙動（共有シート・ネイティブモーダル・実地図）は
   「実機でしか確認できない」と明記してオーナーへ依頼する

## 6. このファイルの育て方

- 実機レビューで出た指摘は、直すだけでなく**規則としてここへ还元する**
  （例: 「赤を使いすぎ」→ §1、「簡素すぎて分からない」→ §2/§4）。
- 具体値を変えるときは実装と同じ PR で変える。文書だけ・実装だけの変更をしない。
