# 認証フローの自動テストカバレッジ

このドキュメントは「**認証フローのどこが自動テストで守られていて、どこが守られていないか**」を 1 か所にまとめたものです。
#1124（ログアウトすると ①ホームへ戻らない ②API が全滅する ③画面が固まる）が、E2E が 1 本も無かったために
実機で触るまで誰も気付けなかったことを受け、#1131 で作成しました。

新しく認証まわりを触るときは、まずこの表で「今どこに穴があるか」を確認してください。
**穴が埋まった / 増えたときは、この表を更新するのが実装の一部です。**

---

## 1. 認証フローの全体像

このアプリの認証は Supabase Auth の 1 本道ですが、入口と出口が複数あります。

```
                       ┌──────────────────────────────┐
   起動 ───────────────►│ AuthProvider.runAuthAttempt  │
                       │  1. セッション復元            │
                       │  2. 無ければ匿名サインイン    │
                       └───────┬──────────────────────┘
                               │
        ┌──────────────────────┼───────────────────────┐
        │                      │                       │
   [匿名ユーザー]        [ログイン済み]           [確立できない]
        │                      │                       │
        │ ログインモーダル      │ 設定 → ログアウト      │ エラー UI + 再試行
        ▼                      ▼                       ▼
  signInWithOAuth /       supabase.auth.signOut    retryAuth()
  linkIdentity                 │                    AppState 復帰
        │                      │
        ▼                      ▼
  外部 IdP（Google/Apple）  SIGNED_OUT ハンドラ
        │                      │  ・匿名サインインをやり直す
        ▼                      │  ・ホーム（検索画面）へ遷移する
  /[locale]/auth/callback      ▼
        │                  ホーム（匿名ユーザーとして継続）
        ▼
   プロフィール作成 → /[locale]/profile
```

| #   | 経路                                                                  | なぜ自動テストが無いのか                                                                                                                                                                                  | 現状の担保                                                                       | 次の一手                                                                                                                                            |
| --- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | **OAuth の実往復**（Google / Apple のログイン画面での操作）           | 外部 IdP の画面は自動化できない（bot 検知に掛かる。各社の利用規約上もアンチパターン）。E2E はセッション注入方式で「ログイン済み状態」から始める設計を採っている                                           | 手動確認のみ                                                                     | **自動化しない**（方針として確定）。代わりに前後の経路（#6 のモーダル表示、下の B のコールバック処理）を個別に固める                                |

## 4. #1131 で追加したログアウト E2E の実効性（実測）

「テストがあること」と「テストが壊れたときに赤くなること」は別なので、
#1124 の修正を**一時的に戻したビルド**を作って実測しました。

| 戻した修正                                                                  | 症状                                                | このテストは検知したか                                                                     |
| --------------------------------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `68d44720`（SIGNED_OUT コールバック内で `supabase.auth.*` を await しない） | ①ホームへ戻らない                                   | ✅ **赤くなる**（設定画面に留まり、検索画面が出ない）                                      |
| 同上                                                                        | ②匿名セッションが再確立されず API が全滅する        | ✅ **赤くなる**（localStorage に匿名セッションが現れず、場所オートコンプリートも空のまま） |
| 同上                                                                        | ③画面が固まる                                       | ❌ **緑のまま**（→ 下記）                                                                  |
| `f8c6a437`（ログアウト後の行き先を `app/index.tsx` へ明示的に引き継ぐ）     | ①ホームへ戻らない（プロフィールタブへ戻ってしまう） | ✅ **赤くなる**                                                                            |

### ③「画面が固まる」を直接は検知できていないことについて

Web ビルドでの #1124 は、**React の描画スレッドが止まる種類のフリーズではありません**。
`GoTrueClient` のロックがデッドロックしたまま解放されず、以降の `supabase.auth.*` が
永久に解決しなくなるものです。そのため:

- DOM の操作（タブ切り替え・トグル・入力）は**壊れたビルドでも普通に効きます**（実測で緑のまま）
- ユーザーから見た「固まった」は、**ログアウト後に再ログインしようとしても何も起きない**という形で現れます

再ログインの検証は Google のログイン画面へ実際にリダイレクトすることになるため、
「OAuth の実往復は自動化しない」という方針（§3 A）と衝突します。よって:

- テストには UI 応答性のアサーション（タブ遷移・純クライアント操作）を**残してあります**。
  これは「本物のフリーズ（無限レンダー、モーダルが閉じない等）」の回帰は捕まえられます
- #1124 のデッドロックそのものは、**症状 ① と ② が同じ根本原因から出ている**ため、
  結果的にこの 1 本で検知できます

ネイティブ（Android / iOS）では事情が異なり、スプラッシュ固着や実際の無反応として現れるため、
Detox のほうがこの症状に向いています（→ §6）。

## 5. 「コールバック画面の統合テスト（提案 B）」を今回やらない理由

#1131 では提案 A（ログアウトの E2E）と提案 B（コールバック画面の統合テスト）が挙がっていましたが、
**オーナーが「A のみ対応したい」と判断した**ため、B は実装していません。

B 自体が不要になったわけではないので、§3 の表に「守られていない範囲」として残しています。
着手する際は、この節を「実施済み」に書き換えてください。

## 6. モバイル（Detox）側への提言

ログアウトの Detox テストは **e2e-web 版をそのまま移植しても動きません**。
着手前に次の 2 点を解く必要があります（このため #1131 では実装せず、別 Issue 化を推奨します）。

### (1) ログアウトすると、テスト用セッションが再注入されてしまう

`AuthProvider` の SIGNED_OUT ハンドラは `runAuthAttempt()` を呼び、その先頭で `injectTestSession()` が走ります。
`injectTestSession` は「セッションの有無」ではなく「**launchArgs の期待ユーザーと一致するか**」で注入を判断するため
(`app-expo/lib/e2e/injectTestSession.ts`)、`e2eSessionOwner=authenticated` で起動したアプリでログアウトすると、
匿名サインインへ進まずに**ログイン済みセッションが注入し直されます**。
そのままでは「ログアウトしたのにログイン済みに戻る」テストになります。

対処案（どれを採るかは別 Issue で設計すること）:

- **a. 1 プロセス 1 回だけ注入する**: `injectTestSession` を「アプリのプロセス内で初回のみ有効」にする。
  2 回目以降は素通りするので、ログアウト後は本番と同じ `signInAnonymously()` の経路に合流する。
  E2E ビルド専用コード（本番バンドルには含まれない）への変更で済み、影響範囲が小さい
- **b. launchArg でオプトアウトする**: `e2eAllowAnonAfterSignOut=1` のようなフラグを足し、
  ログアウト spec だけ再注入を止める

いずれの場合も、ログアウト後の匿名サインインは**実際に 1 回発生します**（30 回/時/IP の枠を 1 消費）。
逆に言えば、そこを潰してしまうと「匿名セッションが再確立される」ことを検証できません。
**ログアウトの Detox テストは 1 本に留めること。**

### (2) 共有セッションを失効させてしまう

アプリは `logout({ scope: "local" })` を呼びますが、これは `POST /auth/v1/logout?scope=local` で
**サーバ側のセッションも失効させます**。e2e-mobile は run 全体で 1 つのログイン済みセッションを共有しているため
(`e2e-mobile/utils/sessionEnv.ts`)、そのセッションでログアウトすると後続の authenticated テストが軒並み落ちます。

→ **ログアウト spec 専用のセッションを別途発行して launchArgs で渡すこと**。
e2e-web 版（`e2e-web/tests/authenticated/logout.spec.ts`）はテスト内で `signInWithPassword` を 1 回追加実行して
同じ問題を回避しています（この副作用は実測で確認済み。共有 storageState でログアウトすると
後続テストが 403 になりました）。

### (3) ネイティブでこそ価値がある部分

`AuthProvider` の SIGNED_OUT ハンドラには `Platform.OS !== "android"` の分岐があり、
**この分岐は e2e-web では片側しか通りません**。#1124 の修正履歴（`c982ee10` / `e0fc1ef0` / `a8562970`）が示すとおり、
ログアウト後のフリーズは Android と iOS で原因も直し方も違いました。
また §4 で述べたとおり「画面が固まる」を**本当のフリーズとして**検知できるのは Detox 側です。

つまり e2e-web の 1 本は #1124 の再発を web で止められますが、**ネイティブの再発は止められません**。
ネイティブ側は別 Issue として、Android / iOS それぞれで 1 本ずつ流すことを推奨します。
