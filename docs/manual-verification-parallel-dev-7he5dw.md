# 実機確認チェックリスト（統合ブランチ `claude/parallel-dev-orchestration-7he5dw`）

このドキュメントは、統合ブランチ `claude/parallel-dev-orchestration-7he5dw` へマージした 13 件の変更のうち、
**自動テストでは守れず、人間が実機・実ブラウザで触らないと確認できない項目**をまとめたものです。

## なぜこれが要るのか

この統合ブランチの検証は、すべて次の範囲で行われています。

- jest（ユニット・コンポーネントテスト）
- `tsc --noEmit`
- Playwright（`e2e-web`。ログアウト E2E のみ）

つまり **Android / iOS の実機挙動、実ブラウザでの OAuth 往復、見た目の良し悪しは一切検証されていません。**
特に今回は SafeArea・タッチジェスチャ・OAuth リダイレクトという「エミュレータや jest では原理的に再現できない」
領域の修正が含まれます。ここを人間が確認しないと、直ったつもりで直っていない状態のままマージされます。

各項目には**何を見れば良いか**と、**なぜ自動テストで守れないのか**を書いてあります。

### #1135 Web で OAuth ログインが 1 回目で入れず、2 回目で入る

**なぜ自動テストで守れないか**: 実 Google IdP との往復は bot 検知・利用規約の制約で自動化できません。
競合の解消自体はユニットテストで固定済み（修正前のコードで実際に赤くなることを 2 回の独立レビューが実測）ですが、
**「1 回目のログインで入れる」ことの最終確認だけは実ブラウザが要ります。**

- [ ] **Web で、1 回目の Google ログインでログイン状態になる**（これが完了条件そのもの）
- [ ] Android で OAuth ログインが回帰していない
- [ ] iOS で OAuth ログインが回帰していない
- [ ] ログアウト → 再ログインも 1 回目で入る

**devtools での切り分け手順**（再現した場合に原因を絞るため）:

1. Application → Local Storage の `sb-<project-ref>-auth-token` を開き、`user.is_anonymous` を控える（JWT 本体は貼らないこと）
2. Console / Network の **Preserve log** を ON にしてログイン
3. コールバック着地の直後、画面遷移する前に確認する

| 見るもの | 期待 | 外れたときの意味 |
| --- | --- | --- |
| `sb-<ref>-auth-token-code-verifier`（飛ぶ直前） | 存在する | 無ければセッション削除で verifier ごと消えている |
| 同上（着地の数秒後） | 消えている | 交換が実行された証拠 |
| `sb-<ref>-auth-token` の `user.is_anonymous`（着地後） | `false` | `false` なのに画面がゲスト表示なら React state だけ巻き戻っている |
| Network の `POST /auth/v1/token?grant_type=pkce` | 200 | 400 なら `code_verifier` 側の問題 |
| Network の `GET /auth/v1/user` | **出ないはず** | 出ていたら削除したはずの `setSession` が残っている |
| Network の `POST /auth/v1/signup` | **出ないはず** | 出ていたら匿名サインインが OAuth セッションを潰している |

**BigQuery（後追い）**: `frontend_event_logs` で 1 回目に `oauth_callback_success` が出た後に
`sessionRestored`（`payload.user_id` が匿名 ID）が続いていないこと。続いていたら未解決です。
新イベント `sessionRestoreSuperseded` / `anonymousSignInSuperseded` / `anonymousSignInDiscarded` の解釈は
`.codex/bigquery/event-catalog.md` を参照してください。**`sessionRestoreSuperseded` は正常起動でも発火する**ため、
`stale_user_id` と `current_user_id` の一致/不一致で正常系と競合を区別します。

### #1126 保存したお店リストの横スクロールで縦に広がる（Android）

**なぜ自動テストで守れないか**: 実タッチのジェスチャ競合は Android 実機でしか再現できません。
しきい値の判定ロジックはユニットテストで固定していますが、**触り心地は数値からは判断できません。**

設定値: カルーセル活性化 `activeOffsetX = ±10dp` / 縦とみなして fail `failOffsetY = ±20dp`。
理屈上、シートへ譲るのは約 63° 以上の急角度のみです。

- [ ] **レビュータブ（ログイン後）で保存店リストを普通に横スクロールしても、縦並び UI に変わらない**

  - 独立レビューの指摘: `draggable=false` の反映は JS の setState を経由するため、
    **非常に速いスワイプでは prop 反映前にシートが掴む短い競合窓が理論上残ります。**実用上問題になるかは実機判断
- [ ] 斜め方向のスワイプが不自然に感じない
