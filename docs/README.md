# リポジトリ内ドキュメントの管理規約

このリポジトリの Markdown ドキュメント全部（`docs/` に限らず、コード隣の README も含む）に適用する規約。
制定の経緯と既存ファイルの処分は [decisions/20260823-documentation-cleanup.md](decisions/20260823-documentation-cleanup.md) を参照。

## 大原則: 設計はドキュメントではなくコードに書く

このリポジトリでは設計と実装を分けない。

- **設計の議論・経緯** → Issue / PR に書く。md ファイルにしない
- **設計で決まったこと** → 該当コードに `#Issue番号 【設計】...` 形式のコメントで書く。
  書き方の正は [.codex/commentary-policy.md](../.codex/commentary-policy.md)
- **実装の解説** → 書かない。**ソースコードを見た方が早いものは、ソースコードを見る**。
  アーキテクチャ解説 md はコードの変更に追従できず、嘘をつき始める（実際に複数堆積した）

md ファイルとして残してよいのは、**コードを読んでも分からないこと**だけである。

## 残してよいドキュメントは 5 種類

| 種類           | 内容                                                                                                                                                                       | 置き場所                                                                                                  | 命名                 | 更新義務                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------- | -------------------------------------------------------------------------------------- |
| 仕様サマリー   | 横断的な仕様・外部契約を**一目で引ける形に圧縮したもの**（イベントカタログ、URL 設計、Cookie 属性、環境変数の意味など）。詳細はコードへの参照で示し、だらだら説明しない    | 単一パッケージで閉じるなら**コード隣の `README.md`（1 ディレクトリに 1 つだけ）**、横断なら `docs/specs/` | kebab-case           | **対象のコードを変えた PR で一緒に更新する。** 更新できないなら削除する                |
| ランブック     | 繰り返し実行する運用手順。コピペで実行できるコマンド列                                                                                                                     | 操作対象の隣（例: `infra/big-query/`）か `docs/runbooks/`                                                 | kebab-case           | 手順が変わったら更新。動かない手順書は削除する                                         |
| 意思決定記録   | コードに置き場が無い横断的な決定（機能の撤去、プロセス、規約）の記録。**該当コードがある決定はコードコメントに書き、ここには書かない**                                     | `docs/decisions/`                                                                                         | `YYYYMMDD-<slug>.md` | 書いたら変更しない。覆すときは新しい記録を書き、古い方の冒頭に superseded リンクを足す |
| プロダクト定義 | «誰の、どの瞬間の、何を» 解くプロダクトかの正本（コアペルソナ / コア価値 / 現在地の実測 / 未検証仮説）。機能を足す・削る判断の照合先。**議論と経緯は書かず、Issue へ置く** | `docs/product/README.md`（1 ファイルのみ）                                                                | —                    | 実測は取得日を併記して更新。覆った仮説はその場で書き換える（経緯は Issue）             |
| 作業ログ       | 一回きりのバッチ・PoC・調査の記録と再現手順                                                                                                                                | `scripts/<YYYYMMDDT0000_名前>/` に自己完結                                                                | ディレクトリ名に日付 | 凍結扱い。更新義務なし                                                                 |

この 5 種のどれでもないものは、リポジトリにファイルとして置かない。

## 作ってはいけないもの

- **設計・アーキテクチャ解説の md**: 設計判断はコードコメント、経緯は Issue / PR へ。
  「〜の仕組み」「〜アーキテクチャ」を数百行で解説するファイルを作らない
- **PR 説明の残骸**: `IMPLEMENTATION_SUMMARY.md`、「✅ 実装完了」「このPRでは〜」で始まる文書。
  その内容は **PR 本文・Issue コメントに書く**。マージ後にファイルとして残さない
- **2 枚目の README**: `README_ARCHITECTURE.md` のような分冊。1 ディレクトリ 1 README に統合する
- **`*_OLD.md` / `*_V2.md` / 改名で退避したファイル**: 古くなったら削除する。履歴は git が持っている
- **検証チェックリスト・実機確認メモ**: Issue / PR に書く
- **アーカイブディレクトリ**: `docs/archive/` のような墓場は作らない。価値がないものは削除する

## 書くときの規則

- **同じ事実を 2 箇所に書かない。** 正とする場所を 1 つ決め、他からはリンクで参照する
  （例: EAS のネイティブ差分判定の正は `.codex/skills/gh-nanitabeyo-release/scripts/audit-ota-inputs.sh`。差分パスのリストを他の文書へコピーしない）
- 冒頭 3 行以内に「何の文書で、読者は誰か」を書く
- 「詳細はコードを見ろ」でよい箇所は、説明を書かずにファイルパスを示す
- 陳腐化した記述を見つけたら、**その場で直すか消すかのどちらか**を行う。「気づいたが放置」を禁止する。
  存在しない API を説明する文書は、無い文書より有害である
- 自動生成物（`docs/ui-catalog*.md` 等）は手で編集しない。生成コマンドをヘッダに明記する

## 新しくファイルを作る前の判定

1. その内容は該当コードのコメントに書けるか → 書けるならコメントに書く（`【設計】` 形式）
2. その内容は Issue / PR 本文で足りるか → 足りるならファイルにしない
3. それでも作るなら「**マージ 1 か月後に、誰が、何のために開くか**」に具体的に答える。答えられなければ作らない

## いま何がどこにあるか

| 場所                                      | 中身                                                                                                                                                  |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `docs/specs/`                             | 横断的な仕様サマリー（行動ログ、CDN 署名 Cookie、共有リンク、メンテナンス制御、DB 接続プール、認証 E2E カバレッジ）                                   |
| `docs/product/`                           | プロダクト定義（コアペルソナ / コア価値 / 実測の現在地）。機能判断の照合先                                                                            |
| `docs/runbooks/`                          | 繰り返す運用手順（料理カテゴリの画像・テキスト手動供給）                                                                                              |
| `docs/decisions/`                         | 意思決定記録                                                                                                                                          |
| `docs/detailed_design/`, `docs/sequence/` | 詳細設計の一次資料（CSV / Mermaid）                                                                                                                   |
| `docs/ui-catalog*.md`                     | `pnpm catalog:doc` の生成物。手で編集しない                                                                                                           |
| 各パッケージの `README.md`                | そのディレクトリで閉じる話（`api/src/internal/resize-image/`, `infra/big-query/`, `e2e-web/`, `e2e-mobile/`, `catalog/`, `app-expo/features/*` など） |
| `scripts/<日付_名前>/`                    | 一回きりのバッチ・PoC の作業ログ（凍結）                                                                                                              |
| `.codex/`, `.claude/skills/`              | エージェント向けの規約とスキル定義                                                                                                                    |
