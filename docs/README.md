# リポジトリ内ドキュメントの管理規約

このリポジトリの Markdown ドキュメント全部（`docs/` に限らず、コード隣の README も含む）に適用する規約。
制定の経緯と既存ファイルの処分は [decisions/20260823-documentation-cleanup.md](decisions/20260823-documentation-cleanup.md) を参照。

## ドキュメントは 4 種類しか作らない

| 種類 | 内容 | 置き場所 | 命名 | 更新義務 |
| --- | --- | --- | --- | --- |
| リファレンス | アーキテクチャ・仕様・設計の解説。読者は「これからこのコードを触る人」 | 単一パッケージで閉じる話は**コード隣の `README.md`（1 ディレクトリに 1 つだけ）**、パッケージ横断の話は `docs/architecture/` | kebab-case | **参照先のコードを変えた PR で一緒に更新する。** 更新できないなら削除する |
| ランブック | 繰り返し実行する運用手順。コピペで実行できるコマンド列 | 操作対象のツールの隣（例: `infra/big-query/`）か `docs/runbooks/` | kebab-case | 手順が変わったら更新。動かない手順書は削除する |
| 意思決定記録 | 「なぜこうしたか」の記録。読者は「将来これを覆したくなった人」 | `docs/decisions/` | `YYYYMMDD-<slug>.md` | **書いたら変更しない。** 覆すときは新しい記録を書き、古い方の冒頭に superseded リンクを足す |
| 作業ログ | 一回きりのバッチ・PoC・調査の記録と再現手順 | `scripts/<YYYYMMDDT0000_名前>/` に自己完結 | ディレクトリ名に日付 | 凍結扱い。更新義務なし |

この 4 種のどれでもないものは、リポジトリにファイルとして置かない。

## 作ってはいけないもの

- **PR 説明の残骸**: `IMPLEMENTATION_SUMMARY.md`、`FEATURE_XXX_SUMMARY.md`、「✅ 実装完了」「このPRでは〜」で始まる文書。
  その内容は **PR 本文・Issue コメントに書く**。マージ後にファイルとして残さない
- **2 枚目の README**: `README_ARCHITECTURE.md`、`README_IMPLEMENTATION.md` のような分冊。1 ディレクトリ 1 README に統合する
- **`*_OLD.md` / `*_V2.md` / 改名で退避したファイル**: 古くなったら削除する。履歴は git が持っている
- **検証チェックリスト・実機確認メモ**: Issue / PR に書く。恒久的な判断が混ざっているなら、その部分だけ意思決定記録へ移す
- **アーカイブディレクトリ**: `docs/archive/` のような墓場は作らない。価値がないものは削除する

## 書くときの規則

- **同じ事実を 2 箇所に書かない。** 正とする場所を 1 つ決め、他からはリンクで参照する
  （例: EAS のネイティブ差分判定の正は `.codex/skills/gh-nanitabeyo-release/scripts/audit-ota-inputs.sh`。差分パスのリストを他の文書へコピーしない）
- 冒頭 3 行以内に「何の文書で、読者は誰か」を書く
- 陳腐化した記述を見つけたら、**その場で直すか消すかのどちらか**を行う。「気づいたが放置」を禁止する。
  存在しない API を説明する文書は、無い文書より有害である
- 自動生成物（`docs/ui-catalog*.md` 等）は手で編集しない。生成コマンドをヘッダに明記する

## 新しくファイルを作る前の判定

「このファイルは **PR がマージされた 1 か月後に、誰が、何のために開くか**」に具体的に答えられないなら、作らない。PR 本文に書く。
