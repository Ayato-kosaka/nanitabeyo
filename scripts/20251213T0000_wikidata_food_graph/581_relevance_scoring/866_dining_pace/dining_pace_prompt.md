# `dining_pace` プロンプト仕様 v1.0

> 対象: `scripts/20251213T0000_wikidata_food_graph/581_relevance_scoring/866_dining_pace/`
>
> 本書は、料理カテゴリ等に `dining_pace` feature を付与するための、Phase 1 採点プロンプトおよび運用ルールの仕様である。

---

## 1. 目的

`dining_pace` は、ユーザーがある料理・料理ジャンル・店型カテゴリを選んで**店内で外食する際に、どのような過ごし方・心構えの外出として自然か**を表す特徴量である。

```yaml
feature_type: dining_pace
feature_keys:
  - quick
  - leisurely
score_values:
  - 0
  - 0.5
  - 1
market: Japan
scope: dine-in
```

ここで評価するのは、料理の物理的な提供速度や完食までの分数ではない。

評価したい問いは次の二つである。

```text
「サクッと○○を食べに行こう」は自然か？
「ゆっくり○○を食べに行こう」は自然か？
```

両者は独立であり、逆数ではない。

---

## 2. この feature が表すもの

### 2.1 `quick`（サクッと）

`quick` は、次のような**低コミットメントな外食の選択肢**として、そのカテゴリがどの程度自然かを表す。

- 予定の合間に、気軽に一食を済ませる
- 食事そのものを主目的にせず、実用的に立ち寄る
- 「サクッと○○にしよう」と自然に言える
- 一人または少人数で、あまり構えずに選べる
- そのカテゴリを目的にした外食でも、心理的な負担が小さい

`quick` は、以下を意味しない。

- 料理が早く提供される
- 調理時間が短い
- 行列が短い
- 店内滞在が必ず短い
- 安価である
- ファストフードである

たとえば、ラーメンは一般に `quick=1` になり得るが、それは「ラーメンをサクッと食べに行く」という外食の選び方が自然だからであり、提供時間を測るためではない。

### 2.2 `leisurely`（ゆっくり）

`leisurely` は、次のように**食事自体を外出の一部として楽しむ選択肢**として、そのカテゴリがどの程度自然かを表す。

- 会話・共有・飲酒・カフェ時間を含めて食事を楽しむ
- 食事のために店を選び、少し構えて出かける
- 複数皿、取り分け、鍋、焼き、コースなどの体験が自然に結びつく
- 「ゆっくり○○を食べに行こう」と自然に言える
- 食事そのものが、その日の小さな目的になる

`leisurely` は、以下を意味しない。

- 店で長居できる
- 店が空いている
- 提供が遅い
- 行列が長い
- 高級である
- 料理を放置して冷ます

たとえば、カフェが `leisurely=1` になり得るのは、単に席に長く座れるためではなく、会話・休憩・飲食を含めた外出として訪れる代表像が強いからである。

## 3. 最重要ルール

### 3.1 `quick` と `leisurely` は独立

次は禁止する。

```text
quick = 1 - leisurely
quick = 100 - leisurely
quick と leisurely の合計を 1 にする
```

次のすべてが許容される。

| quick | leisurely | 読み方                                     | 例                                                     |
| ----: | --------: | ------------------------------------------ | ------------------------------------------------------ |
|     1 |         1 | サクッとも、ゆっくりも自然                 | 握り寿司、ベトナム料理、タイ料理                       |
|     1 |       0.5 | サクッとが強く、ゆっくりも可能             | 天ぷら、中華料理                                       |
|     1 |         0 | サクッとが代表的                           | ラーメン、牛丼、油そば                                 |
|   0.5 |         1 | ゆっくり寄りだが短時間利用も可能           | カフェ、居酒屋、和食                                   |
|   0.5 |       0.5 | 店型・注文・カテゴリの幅で混在             | インドカレー、ビビンバ                                 |
|     0 |         1 | ゆっくり食べに行く代表                     | ピザ、パンケーキ、鍋、懐石料理                         |
|     0 |       0.5 | サクッとには向かず、ゆっくりも中心ではない | 原則として少ない。根拠を慎重に確認する。               |
|     0 |         0 | どちらの代表像も弱い                       | 原則として少ない。カテゴリ定義・入力品質を再確認する。 |

### 3.2 料理の提供速度と混同しない

以下は `dining_pace` の直接根拠にしない。

- 調理に時間がかかる
- 出てくるのが早い／遅い
- 行列がある
- 混雑している
- 会計が早い／遅い
- 店の回転率が高い／低い

たとえば、フレンチトーストを `leisurely=1` とする場合も、「焼成に時間がかかるから」だけでは不十分である。カフェ・ブランチ・会話・ゆったりした外出として選ばれやすいことを理由にする。

### 3.3 料理カテゴリの代表値として採点する

本 feature は現在、厳密な `dining_offer`（店舗、注文構成、人数、提供形態まで含む単位）ではなく、**料理カテゴリ等の代表値**として付与する。

評価対象になり得るもの:

- 個別料理: ラーメン、ピザ、握り寿司
- 料理ジャンル: イタリアン、韓国料理、中華料理
- 店型: カフェ、居酒屋、ワインバル
- 広い検索カテゴリ: 海鮮、和食

このため、個別の店舗、コース、人数、価格帯、注文内容による差異を完全には表現しない。

```text
例: 握り寿司
- 立ち食い寿司なら quick が強い
- 寿司店で会食なら leisurely が強い
→ カテゴリ代表値では quick=1 / leisurely=1
```

### 3.4 店内外食のみを対象にする

対象は、日本の一般的な**店内外食**である。

対象外:

- テイクアウト
- デリバリー
- 自宅調理
- 当日の行列・予約状況・混雑
- 特定店舗の営業時間・席数・価格

## 4. カテゴリの見方

### 4.1 個別料理

個別料理では、レシピの性質だけで判断しない。

次を考える。

- 日本でその料理を食べに行くとき、どのような店を想起しやすいか
- その料理を「サクッと」選ぶ会話が自然か
- その料理を「ゆっくり」選ぶ会話が自然か
- 単品完結・日常食・専門店・カフェ・会食・共有のどれと結びつくか

### 4.2 料理ジャンル

料理ジャンルは、個別の一品より幅が広い。

- ランチの単品利用と、夜の複数皿利用の双方を考慮する
- 日本の一般的な外食検索で、どのような店の集合を想起しやすいかを考える
- ただし、特定の Google Maps の現在順位・広告・店舗数を事実として推定してはならない
- 一般に知られる検索・店選びの代表像を使い、幅が大きい場合は `0.5` と `confidence` で表現する

### 4.3 店型

店型では、料理単体の食べやすさではなく、その店を訪れる目的を考える。

```text
カフェ:
  短い利用も可能だが、休憩・会話・飲食を含む外出として訪れるため leisurely=1

居酒屋:
  一杯だけの短時間利用も可能だが、少しずつ頼み、飲み、会話する代表像が強いため leisurely=1
```

**注意（v1.1 追記）**: 焼き鳥・やきとん・串カツのように、居酒屋の代表的な提供品目を
「個別料理」として単独で採点する場合も、店型としての居酒屋と同じ判断基準を当てる。
「1本・1皿を単品で素早く済ませられるか」ではなく、「そのカテゴリを頼みに行く外食全体が、
居酒屋的な少量ずつの注文・飲酒・会話を代表像とするか」で判断する。この観点を欠いたまま
個別料理として採点すると、居酒屋自体より高い `quick` を与えてしまいやすい
（詳細は §9.1 および #1383）。

### 4.4 広い・曖昧なカテゴリ

「海鮮」「和食」のように、異なる店型・注文形式を広く含むカテゴリは、特定の料理一品に還元しない。

- 代表像が二極化する場合は、両軸を独立に `0.5` または `1` にできる
- 根拠に「カテゴリが広く、店型により代表像が割れる」ことを書く
- 無理に一方へ寄せない

## 5. スコア定義

すべての feature_key は `0 / 0.5 / 1` の離散値で出力する。

| score | 定義                                                                                                                     |
| ----: | ------------------------------------------------------------------------------------------------------------------------ |
|     1 | その外食スタイルで選ぶことが、自然かつ代表的。カテゴリが強くその過ごし方を想起させる。                                   |
|   0.5 | そのスタイルでの利用は現実的で、一定の代表性がある。ただし最も強い代表像ではない、またはカテゴリ・店型によって分かれる。 |
|     0 | そのスタイルを目的にこのカテゴリを選ぶことは、一般に想像しにくい。物理的に不可能という意味ではない。                     |

### 5.1 `0.5` の重要な意味

`0.5` は、単なる不明値ではない。

```text
正しい 0.5:
- 天ぷら: チェーンならサクッと、専門店ならゆっくり
- 中華料理: 町中華ランチならサクッと、夜の円卓ならゆっくり
- インドカレー: 店内外食としては一定の構えがあるが、サクッと／ゆっくりのどちらにも強く寄り切らない
- ビビンバ: 韓国料理店での外食像があるが、サクッと／ゆっくりの両方で代表的とは言い切れない
```

情報が不足して判断できない場合は、既存 #581 のデータ契約に合わせて `score=0.5`、`confidence=low` を使う。この場合、reason には「カテゴリ説明が不足」「店型の想定が広い」など、判断の限界を明記する。

## 6. 判定手順

LLM は、各カテゴリにつき次の順序で考える。

### Step 1: カテゴリ型を認識する

以下のいずれかとして扱う。

```text
個別料理 / 料理ジャンル / 店型 / 広い検索カテゴリ / 判別不能
```

### Step 2: 店内外食の代表像を一つまたは複数想定する

考えるのは、レシピそのものではなく、ユーザーがその語を検索・選択して店へ行くときの代表像である。

```text
ラーメン → 一杯完結の専門店・日常昼食
ピザ → ファミレス・カジュアルイタリアン・複数人での食事
焼き鳥 → 立ち飲みの一杯／居酒屋での飲食
ビビンバ → 韓国料理店での店内食事
```

### Step 3: `quick` を独立に判断する

次の問いを使う。

```text
「サクッと [カテゴリ] を食べに行こう」は自然か？
そのカテゴリを、低コミットメントな外食として選ぶ代表像は強いか？
```

### Step 4: `leisurely` を独立に判断する

次の問いを使う。

```text
「ゆっくり [カテゴリ] を食べに行こう」は自然か？
会話、共有、飲酒、カフェ時間、複数皿、コース、店選びなどを含め、
食事自体が外出目的になる代表像は強いか？
```

### Step 5: confidence を付ける

| confidence | 使用条件                                                                           |
| ---------- | ---------------------------------------------------------------------------------- |
| `high`     | カテゴリの外食代表像が明確で、採点根拠が安定している。                             |
| `medium`   | 複数の外食像があるが、カテゴリとして妥当な代表値を置ける。                         |
| `low`      | ラベル・説明が不足している、カテゴリが極端に広い、または店内外食像を確定できない。 |

### Step 6: 短い reason を書く

reason は 120 文字以内の日本語とし、必ず外食スタイルの根拠を書く。

良い例:

```text
立ち食いの短時間利用と、寿司店での会食の両方が一般的。
```

悪い例:

```text
提供が速い。
混んでいる。
高級店が多い。
人気がある。
```

## 7. 内部チェック観点（出力しない）

以下は、スプレッドシートやレビューで再現性を持たせるための内部チェック観点である。LLM の出力 feature として追加してはならない。

### 7.1 quick 側

| 観点                             | 問い                                                       |
| -------------------------------- | ---------------------------------------------------------- |
| Q1: サクッと選びやすさ           | 「サクッと○○」という会話がどの程度自然か。                 |
| Q2: 低コミットメント外食の代表性 | 日常の一食、短い寄り道、予定の合間の選択肢として一般的か。 |

### 7.2 leisurely 側

| 観点                         | 問い                                                                 |
| ---------------------------- | -------------------------------------------------------------------- |
| L1: ゆっくり食べに行きやすさ | 「ゆっくり○○」という会話がどの程度自然か。                           |
| L2: 外出体験性               | 会話、共有、飲酒、カフェ、複数皿、コース、店選びが自然に結びつくか。 |

### 7.3 注意

この内部チェックは、料理の提供速度・食事時間を数式化するものではない。

- Q1/Q2/L1/L2 の単純な足し算だけで最終値を決めない
- 最終値はカテゴリの代表的な外食イメージに対する離散的な判断とする
- 中間観点は、レビュアー間で理由を比較するために使う

---

## 8. 禁止事項

次のような直接推論は禁止する。

```text
「焼く時間が長いから leisurely=1」
「提供が早いから quick=1」
「高級店だから leisurely=1」
「安いから quick=1」
「混んでいるから leisurely=1」
「健康的だから quick=0.5」
「人気だから leisurely=1」
「韓国料理だから共有で leisurely=1」
```

料理の国籍・価格・人気・高級感・待ち時間を、直接の根拠にしてはならない。

ただし、カテゴリの一般的な外食体験として、共有、飲酒、カフェ利用、複数皿、コース進行などが自然に結びつく場合は、その**外食スタイル**を根拠にしてよい。

### 9.1 特に重要な補足

```text
焼き鳥 / やきとん / 串カツ:
  quick=0.5 / leisurely=1
  v1.0 では quick=1 / leisurely=1 としていたが、#1383 のレビューで見直した。
  ラーメン・牛丼のような「一杯・一皿で完結し、単品を素早く済ませる」quick=1 の代表像とは異なり、
  串を数本ずつ注文しながら飲む居酒屋的な利用が代表像である。これは店型としての「居酒屋」
  （quick=0.5 / leisurely=1）と同じ利用像であり、個別料理として採点する場合も居酒屋と
  揃えるべきだった。単品ですぐ食べ終えられることと、そのカテゴリを選ぶ外食全体が
  低コミットメントであることを混同しないこと（§4.3 参照）。

インドカレー:
  quick=0.5 / leisurely=0.5
  「すぐ済ませる」代表でも、「ゆっくり過ごす」代表でもない。
  インド料理店で食事をする外食の構えはあるが、両極に強く寄せない。

ビビンバ:
  quick=0.5 / leisurely=0.5
  日本の地図検索・店選びのイメージでは、韓国料理店で食べるカテゴリとして捉えられやすい。
  ただし焼肉・鍋・コースのように、ゆっくりした外出体験が必須ではない。
  一方で、牛丼やラーメンほど「サクッと食べに行く」代表でもない。
```

## 10. Phase 1 出力契約

既存の `581_relevance_scoring` の保存形式に合わせ、各 item について以下を出力する。

```yaml
item_qid: Q...
features:
  - feature_type: dining_pace
    feature_key: quick
    score: 0 | 0.5 | 1
    confidence: high | medium | low
    reason: 120文字以内の日本語
  - feature_type: dining_pace
    feature_key: leisurely
    score: 0 | 0.5 | 1
    confidence: high | medium | low
    reason: 120文字以内の日本語
```

必須ルール:

1. 各 item につき `quick` と `leisurely` を**必ず一件ずつ**出す。
2. 同一 key を重複させない。
3. `score` は `0 / 0.5 / 1` 以外にしない。
4. `null` を返さない。
5. `feature_type` は必ず `dining_pace`。
6. reason は、提供速度や待ち時間ではなく、外食の過ごし方・店選びの代表像を述べる。
7. 不確実性は score を乱用せず、`confidence` と reason で明示する。

## 11. Phase 1 用 system prompt（実装用原文）

以下は、Phase 1 で LLM に渡す system prompt の基礎文である。既存 `jp_relevance_scoring_phase1.py` に統合する場合は、feature definitions と tool schema もこの仕様に合わせて更新する。

```text
You are assigning dining_pace features for dish, cuisine, and venue categories
in a restaurant recommendation app for the Japanese dining-out market.

This feature measures the kind of dining occasion a category naturally supports.
It does NOT measure food preparation time, serving speed, queue length,
restaurant congestion, price, popularity, luxury, or how long a person can stay.

Evaluate the representative dine-in dining image of the category in Japan.
Do NOT assume a specific restaurant, menu combination, party size, course,
price point, queue, or takeout/delivery use.

For each item, score these two independent feature keys:
- quick
- leisurely

Ask these two separate questions:
1. Is “サクッと [category] を食べに行こう” a natural choice?
2. Is “ゆっくり [category] を食べに行こう” a natural choice?

quick and leisurely are NOT opposites.
They may both be 1, both be 0.5, or both be low.
Never calculate one as the inverse of the other.

Use only these values:
- 1: strong, natural, representative fit
- 0.5: realistic and familiar fit, but not the strongest representative image,
       or the category has materially mixed restaurant patterns
- 0: choosing this category specifically for that style is generally unnatural

quick means a low-commitment, practical, casual dining choice.
It is about whether “サクッと [category]” is a natural way to choose an outing,
not whether food is served quickly.

leisurely means that the meal itself naturally becomes part of the outing,
such as through conversation, sharing, drinking, cafe time, multiple dishes,
course-like dining, or choosing a restaurant for the experience.
It is not a measure of waiting time or stayability.

When information is insufficient, do not return null.
Return score=0.5, confidence=low, and state the uncertainty in reason.
Do not use 0.5 merely because you are uncertain when the category's dining image
is otherwise clear.

Output exactly two features for every item:
- dining_pace / quick
- dining_pace / leisurely

Each feature must include:
- score: 0, 0.5, or 1
- confidence: high, medium, or low
- reason: concise Japanese explanation, maximum 120 characters

Reasons must cite a dining-out image such as a casual single-dish meal,
cafe visit, shared dishes, drinking, conversation, or a restaurant experience.
Never cite preparation time, serving speed, queues, congestion, price, luxury,
popularity, or healthiness as the direct reason.

Calibration anchors:
- pizza: quick=0, leisurely=1
- nigiri sushi: quick=1, leisurely=1
- tempura: quick=1, leisurely=0.5
- cafe: quick=0.5, leisurely=1
- Chinese cuisine: quick=1, leisurely=0.5
- Japanese cuisine: quick=0.5, leisurely=1
- Vietnamese cuisine: quick=1, leisurely=1
- Indian curry: quick=0.5, leisurely=0.5
- bibimbap: quick=0.5, leisurely=0.5
- hot pot: quick=0, leisurely=1
```

## 13. レビュー（Phase 2）で確認すること

Phase 2 では、新しい判断軸を作らず、次のみを確認する。

1. `quick` と `leisurely` を逆数扱いしていないか。
2. 提供時間・行列・価格・高級感を直接根拠にしていないか。
3. 個別レシピではなく、店内外食の代表像を見ているか。
4. カテゴリの幅がある場合、無理に片方へ寄せていないか。
5. `0.5` を「混合的な代表像」として正しく使っているか。
6. confidence が、カテゴリの明確さ・幅・入力情報量に対応しているか。
7. キャリブレーション例と整合するか。
