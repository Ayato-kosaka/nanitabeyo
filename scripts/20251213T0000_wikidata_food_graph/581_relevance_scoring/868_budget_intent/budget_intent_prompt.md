# `budget_intent` プロンプト仕様 v3.0

## 1. 目的

`budget_intent` は、料理・料理ジャンル・店型カテゴリが、ユーザーの持つ予算意図に対して**修飾なしのカテゴリ名だけで自然な提案になるか**を表す特徴量である。

```yaml
feature_type: budget_intent
feature_keys:
  - inexpensive
  - moderate
  - expensive
  - very_expensive
score_values:
  - 0
  - 0.5
  - 1
market: Japan
scope: restaurant-category-discovery
```

これは、客単価、固定の金額帯、安い店・高い店の存在数を表す feature ではない。

評価するのは、次の会話が自然に成立するかである。

```text
ユーザー: 「ケチりたい」
提案: 「じゃあ、[カテゴリ] にしよう」

ユーザー: 「お手頃に食べたい」
提案: 「じゃあ、[カテゴリ] にしよう」

ユーザー: 「ちょい贅沢したい」
提案: 「じゃあ、[カテゴリ] にしよう」

ユーザー: 「高級なものを食べたい」
提案: 「じゃあ、[カテゴリ] にしよう」
```

---

## 2. 最重要原則: 無修飾カテゴリテスト

採点時は、カテゴリ名をそのまま提案する。

以下のような補足・限定を加えない。

```text
高級イタリアン
グルメバーガー
専門店のリゾット
高級中華のエビチリ
ホテルのカフェ
予約制の焼き鳥店
```

その予算意図に答えるために、店型・コース・専門店・高級・産地・ブランドなどの修飾が必要なら、カテゴリ単体の score は原則 `0` とする。

```text
誤り:
「高級イタリアンなら成立する」
→ イタリアンの very_expensive を 1 にする

正しい判定:
「高級なものを食べたい」→「イタリアン」は弱い
「高級イタリアン」と補足しないと成立しない
→ イタリアンの very_expensive は 0
```

---

## 3. 採点の本質

`budget_intent` は、カテゴリに属する店の価格分布ではなく、**予算意図を持つユーザーへの第一候補としての提案適合度**を評価する。

```text
評価する:
- その予算意図に対して、カテゴリ名だけで「それだ」と感じられるか
- カテゴリが予算意図の代表候補として想起されるか
- 追加説明なしで提案が成立するか

評価しない:
- 高級店・安価店が存在するか
- 平均客単価が高いか低いか
- 特定店舗の価格
- ランチとディナーの価格差
- 現在の地図検索順位や広告
```

---

## 4. 採点単位と対象範囲

### 4.1 採点単位

採点単位は `dish_category` 相当のカテゴリ代表値とする。

対象になり得るカテゴリ:

- 個別料理: ラーメン、ピザ、握り寿司、鰻重
- 料理ジャンル: イタリアン、韓国料理、中華料理、和食
- 店型: カフェ、居酒屋、ワインバル
- 広い検索カテゴリ: 海鮮、定食

厳密な `dining_offer`、店舗、注文、人数、コース単位の評価ではない。

### 4.2 対象

- 日本における一般的な店内外食のカテゴリ提案
- ユーザーがカテゴリを起点に飲食店を探す場面

### 4.3 対象外

- テイクアウト、デリバリー、自宅調理
- 固定の円価格、客単価、価格帯の閾値
- 特定店舗のメニュー価格
- ランチ／ディナー
- 一人／複数人／デート／接待／記念日
- 行列、混雑、予約、待ち時間
- 提供速度、調理時間、滞在時間
- 現在の地図検索順位、広告、口コミ数

これらは別 feature または店舗・offer 単位のデータとして扱う。

## 5. スコア定義

4キーはすべて独立して `0 / 0.5 / 1` で採点する。

| score | 定義 |
| ---: | --- |
| 1 | その予算意図に対し、修飾なしのカテゴリ名を主要候補として出して自然。「それだ」となりやすい。 |
| 0.5 | 修飾なしでも候補にはなるが、第一想起ではない。意図への適合はあるものの、代表性が弱い。 |
| 0 | 修飾なしで提案すると意図とずれやすい。成立させるために店型・専門店・コースなどの補足が必要。 |

`0.5` は不明値ではない。

```text
0.5:
「候補にはなるが、最初に出して強く納得されるほどではない」

0:
「そのカテゴリを出すと、ユーザーが意図と違うと感じやすい」
```

### 5.1 禁止する推論

次を直接根拠にしてはならない。

```text
高級店があるので very_expensive=1
安いチェーンがあるので inexpensive=1
夜は高いので expensive=1
ランチなら安いので moderate=1
コースなら高いので very_expensive=1
```

## 6. feature_key ごとの定義

### 6.1 `inexpensive` — ケチる

```text
「今日はなるべくお金を使いたくない」
「とにかく安く済ませたい」
```

この意図に対し、カテゴリ名だけで自然な候補になるかを評価する。

| score | 判断 |
| ---: | --- |
| 1 | 節約目的の第一候補として自然 |
| 0.5 | 安く済ませることも可能だが、節約目的の代表カテゴリではない |
| 0 | ケチる意図で出すと違和感がある |

安価なチェーン店が存在するだけでは `1` にしない。

### 6.2 `moderate` — お手頃に

```text
「高すぎず、気軽に、ほどよい予算で食べたい」
```

この意図に対し、カテゴリ名だけで自然な候補になるかを評価する。

| score | 判断 |
| ---: | --- |
| 1 | お手頃な外食の第一候補として自然 |
| 0.5 | お手頃な選択肢もあるが、カテゴリの代表イメージとしては弱い |
| 0 | お手頃なものを求める意図には合いにくい |

`inexpensive` と `moderate` は同義ではない。

```text
鰻重:
inexpensive = 0
moderate = 0
expensive = 1
very_expensive = 1
```

### 6.3 `expensive` — ちょい贅沢

```text
「普段より少し良いものを食べたい」
「気分を上げる食事にしたい」
```

この意図に対し、カテゴリ名だけで自然な候補になるかを評価する。

| score | 判断 |
| ---: | --- |
| 1 | ちょい贅沢の第一候補として自然 |
| 0.5 | 少し良い食事として候補にはなるが、カテゴリ名だけでは強くない |
| 0 | 「ちょい贅沢したい」への回答として出すと違和感がある |

高価格の専門店が存在するだけでは `1` にしない。

```text
チーズバーガー:
「ちょい贅沢したい」→「チーズバーガー」は弱い
「グルメバーガーなら成立する」は修飾が必要
→ expensive = 0

リゾット:
「ちょい贅沢したい」→「リゾット」は弱い
「イタリアンでリゾット」などの補足が必要
→ expensive = 0

エビチリ:
「ちょい贅沢したい」→「エビチリ」は弱い
「高級中華のエビチリ」などの補足が必要
→ expensive = 0
```

### 6.4 `very_expensive` — 高級

```text
「高級なものを食べたい」
「明確に上質な食事にしたい」
```

この意図に対し、カテゴリ名だけで自然な候補になるかを評価する。

| score | 判断 |
| ---: | --- |
| 1 | 高級な食事の第一候補として自然 |
| 0.5 | 高級な店もあるが、カテゴリ名だけでは高級意図への回答として弱い |
| 0 | 高級なものを求める意図に対し、カテゴリとして出すと期待を外しやすい |

```text
very_expensive = 1 の代表例:
- 握り寿司
- 鉄板焼き
- 懐石料理
- 鰻重
- すき焼き
- 蟹料理
- 天ぷら

very_expensive = 0 の代表例:
- イタリアン
- ピザ
- ハンバーグ
- 蕎麦
- サラダボウル
- サンドイッチ
- オムライス
```

「高級イタリアン」であれば成立しても、`イタリアン` 単体で高級意図へ答えにくいため、`very_expensive=0` とする。

## 7. 4キーの独立性

4キーは、単一の価格帯を4分割するものではない。

次は禁止する。

```text
4キーの合計を常に1にする
必ず1つだけを1にする
inexpensiveが高ければvery_expensiveを必ず低くする
価格の高低だけで単調に並べる
```

許容する組み合わせの例:

| カテゴリ | inexpensive | moderate | expensive | very_expensive | 解釈 |
| --- | ---: | ---: | ---: | ---: | --- |
| 握り寿司 | 0 | 1 | 1 | 1 | 節約以外の3意図で自然に提案できる。 |
| ピザ | 0 | 0.5 | 1 | 0 | 少し良い食事として自然。節約・高級の代表ではない。 |
| 焼き鳥 | 0.5 | 1 | 0.5 | 0.5 | お手頃中心。贅沢・高級は候補止まり。 |
| 蕎麦 | 1 | 1 | 0.5 | 0 | 節約・お手頃が強い。高級意図の第一候補ではない。 |
| 鰻重 | 0 | 0 | 1 | 1 | ちょい贅沢・高級の意図に強く合う。 |
| 韓国料理 | 0 | 0.5 | 1 | 0 | ちょい贅沢として自然。節約・高級の代表ではない。 |
| カフェ | 0.5 | 1 | 0.5 | 0 | お手頃が中心。節約・ちょい贅沢は限定的に候補になる。 |
| イタリアン | 0 | 0.5 | 1 | 0 | ちょい贅沢には自然だが、高級意図には修飾が必要。 |
| チーズバーガー | 0.5 | 1 | 0 | 0 | お手頃な外食として自然。贅沢意図の第一候補ではない。 |
| リゾット | 0.5 | 1 | 0 | 0 | お手頃な洋食・カフェ利用として扱う。 |
| エビチリ | 0.5 | 1 | 0 | 0 | お手頃な中華として扱う。 |

## 8. カテゴリ幅の扱い

カテゴリが広い場合は、ユーザーが地図検索等でカテゴリを選ぶ際に想定する、一般的な店群・外食イメージで判断する。

ただし、以下を根拠にしてはならない。

```text
高級店が一店でもある
安価なチェーンが一店でもある
現在の地図検索順位
広告の表示
口コミ数
特定都市の店舗構成
```

カテゴリが広く、修飾なしでは予算意図に答えにくい場合は、`0.5` または `0` を使う。

## 9. 別 feature として扱うもの

以下は `budget_intent` に混ぜない。

| 要素 | 扱い |
| --- | --- |
| ランチ／ディナー | `timeSlot` などの時間帯 feature |
| 一人／複数人 | `scene`・人数系 feature |
| デート・接待・記念日 | `scene` 系 feature |
| 飲酒の有無 | `scene`・飲酒系 feature |
| 提供速度・滞在時間 | `dining_style` などの別 feature |
| 実際の客単価 | 店舗・offer単位の別データ |
| 行列・混雑・予約 | 動的な店舗情報 |

## 10. 判定手順

各カテゴリについて、以下の4文をそのまま読んで判断する。

```text
「ケチりたいなら、[カテゴリ] にしよう」
「お手頃に食べたいなら、[カテゴリ] にしよう」
「ちょい贅沢したいなら、[カテゴリ] にしよう」
「高級なものを食べたいなら、[カテゴリ] にしよう」
```

判定順序:

1. カテゴリ名だけで提案文が自然か確認する。
2. 店型・専門店・コース・高級などの修飾が必要か確認する。
3. 修飾なしで強く自然なら `1`。
4. 修飾なしでも候補としては成立するが、第一想起ではなければ `0.5`。
5. 修飾が必要、または出すと違和感が強ければ `0`。

## 11. キャリブレーション例

### 11.1 予算意図への自然な第一候補

```text
「ちょい贅沢したい」→「ピザ」
「高級なものを食べたい」→「握り寿司」
「高級なものを食べたい」→「鉄板焼き」
「ちょい贅沢したい」→「鰻重」
「ケチりたい」→「ラーメン」
「お手頃に食べたい」→「定食」
```

### 11.2 補足がないと成立しにくいので0

```text
「高級なものを食べたい」→「イタリアン」
  - 「高級イタリアン」が必要
  - very_expensive=0

「ちょい贅沢したい」→「チーズバーガー」
  - 「グルメバーガー」が必要
  - expensive=0

「ちょい贅沢したい」→「リゾット」
  - 「専門店のリゾット」「イタリアンでリゾット」等が必要
  - expensive=0

「ちょい贅沢したい」→「エビチリ」
  - 「高級中華のエビチリ」が必要
  - expensive=0
```

### 11.3 候補にはなるが第一想起ではないので0.5

```text
「高級なものを食べたい」→「焼き鳥」
  - 高級焼き鳥店はあるが、無修飾の焼き鳥は高級の第一候補ではない
  - very_expensive=0.5

「ちょい贅沢したい」→「ラーメン」
  - 少し良い一杯はあり得るが、第一想起ではない
  - expensive=0.5

「お手頃に食べたい」→「焼肉」
  - お手頃な選択肢はあるが、第一想起としては強くない
  - moderate=0.5
```

## 12. Phase 1 出力契約

各 item について、4件を必ず出力する。

```yaml
item_qid: Q...
features:
  - feature_type: budget_intent
    feature_key: inexpensive
    score: 0 | 0.5 | 1
    confidence: high | medium | low
    reason: 120文字以内の日本語

  - feature_type: budget_intent
    feature_key: moderate
    score: 0 | 0.5 | 1
    confidence: high | medium | low
    reason: 120文字以内の日本語

  - feature_type: budget_intent
    feature_key: expensive
    score: 0 | 0.5 | 1
    confidence: high | medium | low
    reason: 120文字以内の日本語

  - feature_type: budget_intent
    feature_key: very_expensive
    score: 0 | 0.5 | 1
    confidence: high | medium | low
    reason: 120文字以内の日本語
```

必須ルール:

1. 各 item につき4キーを必ず1件ずつ出力する。
2. `feature_type` は必ず `budget_intent` とする。
3. score は `0 / 0.5 / 1` のみとする。
4. `null` は出力しない。
5. 同じ feature_key を重複させない。
6. reason に固定価格、客単価、ランチ／ディナー、人数、現在の店舗価格を書かない。
7. 情報不足時は `score=0.5`、`confidence=low` を使い、reasonで判断の限界を示す。

## 13. reason の書き方

reason には、金額・客単価ではなく、予算意図に対してカテゴリ名だけで提案できる自然さを書く。

良い例:

```text
「高級な食事を求める意図に対し、カテゴリ名だけで自然な第一候補になる。」

「お手頃な外食の代表として自然だが、ちょい贅沢の第一想起ではない。」

「高級店の存在はあるが、修飾なしでは高級意図への提案として弱い。」
```

悪い例:

```text
「平均客単価が高い。」
「高級店がある。」
「ランチは安い。」
「専門店なら高い。」
```

```text
対象カテゴリについて、feature_type=budget_intent の4キーを独立に評価してください。

- inexpensive: ケチる
- moderate: お手頃に

- very_expensive: 高級

各予算意図を持つユーザーに対して、カテゴリ名だけを修飾なしで提案したときに、主要候補として自然かを評価してください。

必ず次の無修飾カテゴリテストを使ってください。

「ケチりたいなら、[カテゴリ] にしよう」
「お手頃に食べたいなら、[カテゴリ] にしよう」
「ちょい贅沢したいなら、[カテゴリ] にしよう」

「高級イタリアン」「グルメバーガー」「専門店のリゾット」「高級中華のエビチリ」のように、店型・専門店・コース・高級などの追加修飾が必要なら、カテゴリ単体の該当スコアは原則0です。

スコアの意味:
- 1: 修飾なしのカテゴリ名だけで、その予算意図への第一候補として自然

アンカー例:

各カテゴリについて、4キーすべてを必ず出力してください。
reasonは120文字以内の日本語で、予算意図に対する無修飾カテゴリ提案の自然さを説明してください。
```

## 15. Phase 2 レビュー観点

レビュー時は、以下を確認する。

1. 修飾なしのカテゴリ名だけで判定しているか。
2. 高級店・安価店の存在だけでスコアを上げていないか。
3. `0.5` を「候補だが第一想起ではない」として使えているか。
4. 修飾が必要な場合に、原則 `0` とできているか。
5. ランチ・ディナー・人数・シーンを混ぜていないか。
6. 4キーを単一の価格帯や排他的な段階として扱っていないか。
7. reason が、予算意図への提案自然さを説明しているか。
8. 次のアンカーと矛盾していないか。

```text
ピザ: 0 / 0.5 / 1 / 0
握り寿司: 0 / 1 / 1 / 1
蕎麦: 1 / 1 / 0.5 / 0
鰻重: 0 / 0 / 1 / 1

イタリアン: 0 / 0.5 / 1 / 0
```

## 16. 実装・データモデルへの接続

採用版 feature は、既存の relevance scoring 形式を維持する。

```yaml
feature_type: budget_intent
feature_key: inexpensive | moderate | expensive | very_expensive
score: 0 | 0.5 | 1
source: llm
note:
  confidence: high | medium | low
  reason: string
  model: string
  phase: phase1 | phase2
```

カテゴリ評価であり、`dining_offer` を新設しない。

BigQuery投入時には `item_qid` と結合し、各カテゴリにつき4キーをそれぞれ1レコードとして保存する。
