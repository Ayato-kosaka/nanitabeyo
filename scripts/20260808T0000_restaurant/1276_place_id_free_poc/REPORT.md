# 実測レポート: 無料SKUだけの google_place_id 逆引き（Issue #1261 Step 1）

- 測定日: 2026-08-12
- seed: Overture Maps Places `2026-07-22.0`、日本 `food_and_drink` **789,612行**
  （SHA-256 `8c2c2432…5be06` を検証済み。`0000_open_data_poc/sources.lock.json` と同一）
- 呼んだSKU: Text Search Essentials (IDs Only) / Nearby Search Essentials (IDs Only)
- **課金額: 0円**。fieldMask は `places.id` 固定、応答に他フィールドが来たら停止する実装。
  Google 由来の店名・住所・座標は1件も取得していない。

## 結論

1. Issue 記載のダブルクエリ相互検証（A と B が単一候補で一致）は、そのままでは
   **確定率 55.6%、負例での誤マッチ率 11.3%** だった。「一致したら確定」は成り立たない。
2. `locationRestriction`（矩形）による座標の裏取りを必須にすると、誤マッチ率が
   **11.3% → 0.33%** に落ちる。しかも残った1件は誤りではなく、負例の作り方に由来する
   偶然の実在ペアだった（後述）。**実質的な捏造率は 0/300**。
3. 採用ルール `layered_strict_wide` の確定率は **63.6%**。座標裏取りを入れても確定率は
   55.6% → 63.6% と**むしろ上がる**。厳しくしたのに増えるのは、A・B の件数条件を
   矩形の証拠で置き換えられるからである。
4. 残り約35%は無料では確定できない。主因は Overture 側の座標ズレと住所欠損であり、
   Google 側の問題ではない。Issue の Step 3（需要駆動）で埋める設計が妥当。

## 較正セット

| 種別 | 件数 | 作り方 |
| --- | --- | --- |
| 正例 | 1,000 | Overture 日本 food_and_drink から reservoir sample（seed 42、再現可能） |
| 負例 | 300 | 正例の座標・住所に、**5km以上離れた別店舗の店名**を貼り付けたもの |

正解付きデータ（Issue の Step 2）は手元に無いため、負例で precision の下限を測った。
負例には正解が存在しないので、確定matchが出たらそれは誤りである。

正例のうち 58件（5.8%）は住所も郵便番号も無く、クエリBを組めないため `ineligible`。
これは Overture 側の欠損であり、Google の探索失敗ではない。

読み方: 座標の裏取り（`_geo_hard` と `layered*`）が入っているかどうかで誤マッチ率が
2桁変わる。件数条件を緩める方向（`top1_agree`, `intersection_unique`）は、裏取り抜きだと
確定率と引き換えに誤マッチを3割まで増やす。

### 採用ルール `layered_strict_wide`

矩形内に実在することを全層で必須にした上で、3つの層で拾う。

- 層1 `layer1_intersection_in_box`: A と B の共通集合がちょうど1件で、それが矩形内（604件）
- 層2 `layer2_top1_in_box`: A と B の最上位が一致し、それが矩形内（19件）
- 層3 `wide1_strict_in_wide_box`: A と B がどちらも単一候補で一致し、それが**半辺250m**の
  矩形内（13件）。Overture の座標が数十mずれている行の救済層

層1・層2だけの `layered_strict`（62.3%）に対し、救済層は +1.3pt を**負例の誤マッチ0件**で
稼いだ。救済層を入れるかどうかは `--rule` で切り替えられる。

一方、矩形内に唯一ある同名店を A か B の片方だけが支持する層（`layered` の
`layer3_unique_in_box`）は確定率を +2.4pt 上げるが、負例の誤マッチ3件のうち2件を
この層が出したため採用しなかった。

### 唯一の「誤マッチ」の中身

`layered_strict` が負例で出した1件は、`Tully's Coffee` という店名を柏市大島田の座標へ
貼り付けたものだった。A・B・C の3クエリすべてが同じ place_id を返している。C は矩形で
切り落とす検索なので、**その座標の75m以内に本当に Tully's Coffee が存在する**。
チェーン店を無作為に貼り替えたために、偶然「正しいペア」ができてしまった負例である。

つまり実測 0.33% は誤マッチ率の**上限**であり、捏造（存在しない対応を作る）は
300件中0件だった。

## 棄却した作戦

**「店名+住所」を広い矩形で検索する救済（`layered_wide` の wide2・wide3）**。
狭い矩形（半辺75m）で決まらない行を、半辺250mの矩形の中で住所つきクエリを投げて救う案。
確定率は 64.7% → 69.0% に上がるが、負例の誤マッチが 1.0% → **14.67%** に跳ねた。
層別に見ると内訳は明確で、負例での誤マッチ41件は全て住所つきの2層から出ている。

| 救済層 | 正例で救えた数 | 負例での誤マッチ | 採否 |
| --- | ---: | ---: | --- |
| `wide1_strict_in_wide_box`（店名のみ・A と B が単一候補で一致） | 13 | **0** | 採用 |
| `wide2_address_box_unique`（店名+住所が矩形内で単一） | 23 | 36 | 棄却 |
| `wide3_address_box_in_box`（店名+住所と矩形の共通集合が単一） | 7 | 5 | 棄却 |

矩形内のText Searchは名称が合わなくても近い候補を返すため、地理を広げるときは
テキスト側の合意を strict に保つ必要がある、というのがこの表の読み方である。
再現できるよう `layered_wide` は残したが、`EXPORT_SAFE_RULES` から外して
CSV 出力には選べないようにした。

**括弧書きを外した別表記での再検索**。`Mermaid Cafe（マーメイドカフェ）`のような
行を対象に再検索したが、対象が1,000件中13件しかなく、確定率の改善は +0.1pt に
留まった。コストは無料なので実装は残したが、効果はほぼ無い。

**Nearby Search による座標裏取り**。半径40mの Nearby Search で候補の実在を確認する案。
密集地では20件の上限で打ち切られ、「含まれない＝遠い」と言えなくなる。同じ座標検証を
矩形Text Searchで代替できたため、こちらは C が失敗したときのフォールバックに降格した。

## 確定できなかった約35%の内訳（正例1,000件）

| 理由 | 件数 | 中身 |
| --- | ---: | --- |
| `no_candidate_in_box` | 220 | 矩形内に同名の place が無い。Overture の座標が75m以上ずれているか、閉店 |
| `no_layer_satisfied` | 73 | 矩形内に候補はあるが、A・B の合意が取れない |
| `missing_name_or_address` | 58 | Overture に住所も郵便番号も無く、クエリBを組めない |
| `layer3_rejected_by_strict_policy` | 24 | 片側支持だけの層。精度を優先して落とした |
| `empty_result` | 2 | A も B も0件 |

最大の損失要因は Overture の座標精度である。矩形を広げれば拾えるが、上記のとおり
誤マッチが跳ねるため、無料の範囲では**確定率62%で止めて残りは確定しない**のが
正しい設計だと判断した。

## スループットと全国展開の見積り

| 項目 | 実測値 |
| --- | --- |
| 1 seed あたりのリクエスト数 | 4（A・B・C・c_wide） |
| 実効スループット | 5〜10 req/s |
| HTTP エラー | 35,724件中1件 |
| 課金 | 0円 |

`--qps 15` 以上、または2プロセス同時実行にすると 429 が増え、バックオフで実効レートが
かえって落ちる。10 req/s・36 worker が安定した。

全789,612件に適用する場合は約316万リクエスト、10 req/s で約88時間。課金は0のまま。
`cache/probe.sqlite` により中断・再開ができるので、分割実行して差し支えない。

なお長時間の一括実行では `http.client.RemoteDisconnected` が発生した。urllib はこれを
`URLError` で包まないため、当初の実装では worker thread ごと実行が落ちた。到達性の例外は
全て再試行対象にして修正済みで、単体テストで固定してある。

## 突合してもらうときのお願い

`results/matched_place_ids.csv` を PostgreSQL の `restaurants` と `google_place_id` で
join してください。判定は**座標の距離**でお願いします。CSVの `name` は Overture の表記で、
既存DBの名称は Google の表記なので、同じ店でも文字列は一致しません。

`confidence_tier` が `A`（A・B とも単一候補で一致し、かつ矩形内。負例での誤マッチ 0/300）と
`B`（それ以外の確定層）に分かれています。tier ごとに距離分布を見れば、
どの層まで本番投入してよいかが数字で決まります。
