# 実測レポート: 無料SKUだけの google_place_id 逆引き（Issue #1261 Step 1）

- 測定日: 2026-08-12 〜 2026-08-15
- 呼んだSKU: Text Search Essentials (IDs Only) / Place Details Essentials (IDs Only)
- **例外あり**: 途中で Nearby Search を「IDs Only なら無料」と誤認して使った。
  Nearby Search (New) に IDs Only の無料枠は無く、fieldMask を絞っても
  Nearby Search Pro として課金される（Google サポートの回答、#1331）。
  発生量はおよそ **3,700 リクエスト**。詳細は「課金してしまった箇所」を参照。
- **請求額: ¥0**。ただし内訳に注意が要る。Text Search と Place Details は無料SKUで
  構造的に0円。**Nearby Search 3,750件は課金対象SKUを叩いていた**が、月次無料枠に
  収まり Usage cost の時点で ¥0 だった（クレジット相殺ではない）。
  Google 由来の店名・住所・座標は1件も取得していない。

## 結論（3つの数字）

出荷ルールは `box_unique_strict`。**「確定したものは 100% 正しい」を最優先**にしてある。

| | 何を測ったか | 分母 | 結果 |
| --- | --- | ---: | ---: |
| **②（最優先）** | 確定した place_id のうち正しかった割合 | 5,083（全ラベル 6,000 件のうち確定した分） | **100.000%**（誤り0件、95%下限 99.92%） |
| **③（主KPI）** | Google のレストランのうち place_id を出力できた割合 | 1,747（敷き詰めて列挙） | **63.37%** → 目標 90% |
| ① | オープンデータの行のうち place_id が1つに決まった割合 | 5,850（1,482,423 行からの一様抽出） | **55.61%** |

②は機械裁定で確かめている。ラベルと食い違った 14 件は**全て `db_stale`**（DB 側の
place_id が実店舗の位置に無い）で、`mine_wrong` と `inconclusive` は 0 件だった。

### ②を 100% にするために払った代償

`box_unique`（前の出荷ルール）と比べると、③と①をそれぞれ 4.6pt / 11.0pt 捨てている。

| ルール | ② 全ラベル | ② 金ラベル | ① | ③ |
| --- | ---: | ---: | ---: | ---: |
| `box_unique` | 99.863%（誤り8） | 100% | 66.65% | 68.00% |
| **`box_unique_strict`（出荷）** | **100.000%（誤り0）** | **100%** | **55.61%** | **63.37%** |

`box_unique` で残る 8 件は、どれも裁定が `inconclusive` で `mine_wrong` は 0 件、
ラベル側が距離 28〜101m・名前類似度 0.50〜0.82 で作られた弱いものだった。
それでも「弱いラベルとも食い違わない」ところまで絞るために、使える条件を総当たりで
採点し、次の2つを足した。

- 選んだ place_id が **±25m の矩形の中にある**こと
- **B（店名+住所）の候補が1件以下**であること

条件はラベル 6,000 件の上で選んでいるので、別のラベル集合でも 0 になる保証は無い。
95%下限が 99.92% であることは併記しておく。

### IFAS の住所列には落とし穴がある

`都道府県名` / `市区町村名` は**許可を出した自治体**であって店の所在地ではない。
北海道庁が出した分は全行が `北海道` / `札幌市中央区` になり、実際の店は深川市だったりする。
当初これを住所に前置していたため、`北海道札幌市中央区北海道深川市音江町…` という
クエリを投げていた。`営業施設所在地` は全行が都道府県から始まることを確認（52,392/52,392）
したので、そちらだけを使うよう直した。

### IFAS を足して増えたもの

既存 `public.restaurants` 103,440 行が、オープンデータ側にどれだけ載っているか。

| seed | 名称も一致（covered） | 網羅率 | 近傍に1行も無い（absent） |
| --- | ---: | ---: | ---: |
| Overture 単独 789,612（旧照合器・しきい値0.78） | 43,342 | 41.90% | 4,208 |
| Overture + IFAS 1,042,255（同上） | 47,751 | 46.16% | 3,393 |
| Overture + IFAS + OSM 1,169,886（同上） | 50,435 | 48.76% | 2,999 |
| 同 1,169,886（**照合器を修正**） | — | **72.83%** | 2,999 |
| Overture修正 + IFAS + OSM 1,458,458（照合器も修正） | 75,990 | **73.46%** | **2,706** |

（100m以内。`results/coverage_v2.json`）

**48.76% は照合器の弱さによる過小評価だった。** `jp_text.name_similarity` は
文字bigramのJaccardと部分文字列包含だけで、しきい値0.78では
`カメチク 近江八幡店` ⇔ `カメチク` や `サイゼリヤ` ⇔ `サイゼリア` を別の店と
判定していた。照合器を直すだけで 48.76% → 72.83% になる。ソースを足した効果
（+0.63pt）より一桁大きい。

ソースを足す効果は鈍い一方、`absent`（100m以内にオープンデータ行が1件も無い）は
2,706 件（2.6%）しか残らない。**差は「行が無い」ことではなく「同じ店だと
分からない」ことである。** Google 側から数え直した結果は後述する。

### OSM の取得

`0000_open_data_poc` の OSM 調査は taginfo のタグ件数を数えるだけで実データが
無かったので、Overpass から実際に取った。日本全体を1度のタイルに割り、他ソースに
店が1件も無い1度セル（＝ほぼ海）を除いて 550 → 109 タイルに減らしたうえで、
4並列・重いタイルは4分割して取り直す方式で全件取得した（`failed_tiles` は空）。

OSM は住所タグが付いている行が **15.6%** しかない。住所が無いとクエリB（店名＋住所）が
組めないので、`box_unique` は B を必須にしない作りにしてある。ただし OSM 由来の行が
A と矩形だけでどれだけ確定できるかは、後述のとおり未測定である。

## 課金しないための構造

Google の課金はリクエストした fieldMask で決まる。したがって fieldMask を呼び出し側の
引数にせず定数で固定し、さらに応答側でも `id` 以外のキーが来たら処理を止める。
単体テストで `test_field_mask_is_ids_only` / `test_details_field_mask_is_ids_only` /
`test_billable_field_stops_the_run` として固定してある。

## 判定ルールの組み替え

### 何が起きていたか

当初は層を手で足しては測る進め方をしていた。`layered` → `layered_strict` →
`layered_strict_wide` → `layered_v2` と増やしたが、精度が 99.7〜99.8% で頭打ちになり、
残りの誤りが減らなかった。層の順序と条件を人が決めているので、精度の低い層を
後から見つけて外す、という後戻りが続いた。

そこで進め方を逆にした。候補の選び方と証拠の連言を、正解ラベル2,541件に対して
総当たりで採点する（`gate_analysis.py`、結果は `results/gate_report.json`）。

### 分かったこと: 効いていたのは「合意」ではなく「一意性」

| 根拠 | 確定数 | 一致 | precision |
| --- | ---: | ---: | ---: |
| A と B の最上位が一致 | 2,507 | 2,500 | 99.72% |
| A と B の共通集合が1件 | 2,492 | 2,487 | 99.80% |
| ±75m 矩形 ∩ A ∩ B が1件 | 2,479 | 2,475 | 99.84% |
| ±250m 矩形に同名が1件だけ、かつ A か B が挙げている | 2,455 | 2,453 | **99.92%** |
| ±25m 矩形に同名が1件だけ、かつ A か B が挙げている | 2,327 | 2,325 | **99.91%** |

合意を根拠にする層はどれも 99.7〜99.8% で止まる。**店が Google に無いとき、A も B も
揃って隣の店を返す**からである。合意は「2つのクエリが同じ間違いをしていない」ことを
保証しない。対して「矩形内に同名が1件しかない」は、取り違える相手が存在しないことを
意味する。性質が違う。

### 採用ルール `box_unique`

2層だけで済む。

1. `tight_unique_in_ab` — ±25m の矩形に同名が**1件だけ**で、A か B もそれを挙げている
2. `wide_unique_in_ab` — ±250m まで広げても同名が**1件だけ**で、A か B もそれを挙げている

「A か B が挙げている」という裏取りは必須である。外すとどうなるかを実測した。

| 層1の条件 | 確定数 | 一致 | precision |
| --- | ---: | ---: | ---: |
| ±25m に1件だけ、かつ A か B が挙げている | 2,327 | 2,325 | **99.91%** |
| ±25m に1件だけ（裏取りなし） | 2,376 | 2,326 | 97.90% |
| ↑ の差分（裏取りが無いと通ってしまう行） | 49 | 1 | **2.04%** |

矩形内で唯一でも、店名クエリがその店を指していなければ別の店である。

### ラベル2,541件での結果

| 指標 | 値 |
| --- | ---: |
| 確定 | 2,484 / 2,541 = **97.76%** |
| 既存DBと一致 | 2,482 |
| 既存DBと不一致 | 2 |
| precision（点推定） | 99.92% |
| 正解が候補集合に現れている上限 | 99.92% |

`seed_id` のハッシュで2分割した交差検証でも、両半分とも 99.92%（1,230件中1,229 /
1,254件中1,253）で、当てはめすぎではない。

## 不一致2件の裁定

既存 `public.restaurants` は bulk-import の一回きりのスナップショットで、Google 側の
統廃合には追随していない。不一致を全部「名寄せの誤り」に数えるのも、「DBが古い」で
流すのも正しくない。そこで人の判断を挟まずに決まる裁定を1つ用意した（`adjudicate.py`）。
使うのは無料SKUだけである。

| 判定 | 条件 |
| --- | --- |
| `duplicate` | 両方とも ±5m の矩形に入る。同じ店に place_id が2つある状態 |
| `db_stale` | 自分のは ±25m に入るが、DB のは ±100m にも入らない |
| `mine_wrong` | DB のが ±25m に入り、自分のは入らない。名寄せの誤り |
| `inconclusive` | どれでもない。安全側に倒して誤り扱いで数える |

しきい値は先に決めて全件へ一律に当てる。結果は**2件とも `db_stale`**だった。

| seed | 自分 | DB |
| --- | --- | --- |
| `Little Napoli NOOV` | ±25m 矩形に居る | ±100m 矩形にも居ない |
| `月ノ輪` | ±25m 矩形に居る | ±100m 矩形にも居ない |

したがって `box_unique` の**名寄せ誤りは 0 / 2,484**。

## ① 名寄せ確定率

分母は**統合コーパス 1,482,423 行そのもの**である。Google に載っていない店も、
座標が壊れている行も、閉店している店も、全部入っている。「Google に存在しうる行」
のような絞り込みはしない。絞れば率は上がるが、それは測りたいものではない。

標本は `seed_id` のハッシュで取った一様抽出で、**5,850 件**（`sample_seeds.py`）。
CSV の並び順に依存しないので、Overture / IFAS / OSM が固まって並んでいても偏らない。
標本のソース構成はコーパスと一致している。

| ソース | コーパス | 標本 |
| --- | ---: | ---: |
| Overture | 72.9% | 73.6% |
| IFAS | 16.9% | 16.3% |
| OSM | 10.2% | 10.2% |

### 結果

| | 件数 | 割合 |
| --- | ---: | ---: |
| 標本 | 5,850 | 100% |
| **確定（place_id が1つに決まった）** | **3,899** | **66.65%** |
| ±25m 矩形で一意（`tight_unique_in_ab`） | 3,379 | 57.76% |
| ±250m 矩形で一意（`wide_unique_in_ab`） | 520 | 8.89% |
| 矩形に候補なし（`no_candidate_in_box`） | 1,267 | 21.66% |
| 矩形に同名が複数（`box_not_unique`） | 684 | 11.69% |

95%信頼区間は 65.4%–67.9%。**目標の 70% には届いていない。**

### 未確定 33.35% の中身

3ソース標本 3,000 件で未確定になった 990 件を分解した。

| 未確定の形 | 件数 | 割合 |
| --- | ---: | ---: |
| 矩形に候補なし | 621 | 62.7% |
| 矩形に同名が複数 | 192 | 19.4% |
| 矩形は一意だが A も B もその place を挙げない | 177 | 17.9% |

「矩形に候補なし」621 件を、A（店名+150m bias）と B（店名+住所）の返り値で分けると
こうなる。

| 形 | 件数 | 割合 |
| --- | ---: | ---: |
| A も B も少数（1〜2件）を返す | 286 | 46.1% |
| A か B が上限20件（ありふれた店名） | 116 | 18.7% |
| A も B も 0件（その名前で Google が何も返さない） | 5 | 0.8% |
| その他 | 214 | 34.5% |

**店名で何も返らない行は 0.8% しかない。** Text Search は名前を投げれば必ず
何かを返す。返ってきたものが本当にその店かどうかは別問題で、ここが①の壁である。
矩形を広げれば「返ってきた何か」を掴めるが、それが正しい保証は無い
（後述の「① を 70% に届かせようとして、測って棄却した層」）。

## ② 名寄せ正解率

分母は**①で確定した行**である。正解は既存 `public.restaurants`（bulk-import した
Google 由来の 103,440 件）との突合で作る。

ここに落とし穴がある。**「正解ラベル」を作る作業そのものが名寄せである。**
オープンデータの行と DB の行を、座標の近さと名前の似かたで結んで作るので、
ラベル自体が間違っていることがある。だから2通りの分母で出す。

| ラベル | 作り方 | 件数 |
| --- | --- | ---: |
| 全ラベル | 距離・名前類似度を問わず結べたもの | 6,000 |
| **金ラベル** | **距離 ≤20m かつ 名前類似度 ≥0.90 でだけ結んだもの** | **3,785** |

不一致はすべて `adjudicate.py` の機械裁定にかける。無料SKUだけで、
`duplicate`（同じ店に place_id が2つ）/ `db_stale`（DB側が実店舗の位置に無い）/
`mine_wrong`（名寄せの誤り）/ `inconclusive`（決まらない）に分ける。
`inconclusive` は安全側に倒して誤りに数える。

| | 全ラベル | 金ラベル |
| --- | ---: | ---: |
| ラベル数 | 6,000 | 3,785 |
| 確定 | 5,823 (97.05%) | 3,715 (98.15%) |
| 生の不一致 | 24 | 3 |
| 裁定 `db_stale` | 16 | 3 |
| 裁定 `inconclusive` | 8 | 0 |
| 裁定 `mine_wrong` | 0 | 0 |
| **裁定後の誤り** | **8** | **0** |
| **②** | **99.863%** | **100.000%** |
| 95%下限 | 99.71% | 99.90% |

`mine_wrong`（DB の place_id が ±25m 矩形に居て、自分のものは居ない）は
**全ラベル 6,000 件で1件も出ていない**。

### 全ラベルで残る8件は、ラベル側が怪しい

裁定が `inconclusive` になった8件は、どれも「±100m の中に同名の店が2つあり、
自分のものは ±5〜25m、DB のものは 25〜100m」という形である。そしてその8件の
**ラベルを作ったときの距離と名前類似度**は次のとおりだった。

| 店名 | ラベルの距離 | ラベルの名前類似度 | 自分の place の位置 |
| --- | ---: | ---: | --- |
| 酒楽酒酒酒 | 101.2m | 0.60 | ±5m 矩形の中 |
| 鹿児島ふるさと物産館 | 41.1m | 0.60 | ±100m 矩形の中 |
| アフタヌーンティーティールーム | 47.1m | 0.75 | ±25m 矩形の中 |
| 幸村 | 30.1m | 0.60 | ±25m 矩形の中 |
| はぐるま | 72.3m | 0.60 | ±5m 矩形の中 |
| 焼肉食堂 くたみや 薄場店 | 29.0m | 0.50 | ±5m 矩形の中 |
| 唐揚げ食堂 ごいち ぷらす | 28.5m | 1.00 | ±5m 矩形の中 |
| 大起水産 海鮮丼と干物定食専門店 | 33.6m | 0.82 | ±5m 矩形の中 |

8件中6件で、**自分が選んだ place はオープンデータの座標の ±5m に居て、DB の
place は 25〜100m 離れている**。101m 離れた・名前類似度 0.60 の対応表を
「正解」として名寄せを裁くのは無理がある。金ラベルではこれらが最初から
除かれるので、誤りは0件になる。

②を「100%」と言えるのは金ラベル 3,715 件に対してであって、
「どんなラベルで測っても誤りが0」ではない。**測り方まで含めて書く。**

## ③ 主KPI: Google 側から見た到達率

**これを主KPIにする。** ①②は「オープンデータの行がどれだけ確定したか」であって、
アプリの価値である「Google Maps の店にどれだけ届いたか」ではない。

Nearby Search で 40 区画を敷き詰めて列挙した実在の Google レストラン **1,747 店**を
分母に、この名寄せがその place_id を実際に出力したかを数える。40m 以内にオープン
データ行が1件も無い 11 店も分母に残す。

| 測り方 | 到達 | ③ | 損失率 |
| --- | ---: | ---: | ---: |
| 列挙済みの店から 40m 以内の seed だけを probe（旧） | 1,061 | 60.73% | 39.3% |
| **列挙済みの店から 200m 以内の seed を probe（現）** | **1,084** | **62.05%** | **37.95%** |

半径を 40m → 200m に広げても 1.3pt しか上がらない。座標ずれで届いていなかった分は
少なく、**取りこぼしの大半は座標の問題ではない**。

**列挙そのものは課金対象SKU（Nearby Search）を使ってしまった測定である。**
再実行しない。詳細は「課金してしまった箇所」を参照。

### 取りこぼし 686 件の中身

| | 件数 | 割合 |
| --- | ---: | ---: |
| 40m以内にオープンデータ行が無い | 11 | 0.63% |
| 行はあるが1件も確定しない | 14 | 0.80% |
| **行はあるが別の place_id を出力** | **685** | **39.21%** |
| 到達 | 1,037 | 59.36% |

「別の place_id を出力」が大半である。近くのオープンデータ行は**隣の店**に正しく
当たっていて、その Google 店に対応する行が無い。名寄せの失敗ではない。

さらに、名前が分かる未到達 45 件（既存DBに place_id が在るもの）を、最寄りの
オープンデータ行の名前と比べた。

| | 件数 | 割合 |
| --- | ---: | ---: |
| 最寄り行が**別の店**（オープンデータに無い） | 44 | 97.8% |
| 最寄り行が同じ店（名寄せの失敗） | 1 | 2.2% |

**距離だけを見てはいけない。** 未到達 686 件の 97.5% は 30m 以内にオープンデータ行が
あるが、その行は別の店である。区画は繁華街なので「近くに行がある」はほぼ常に成立する。
以前 40m 基準で「99.4% は対応行がある」と報告したのは、この密度の罠だった。

### 取りこぼしはノイズではない

打ち手を決めるには、取りこぼしが弁当屋・パン屋のような周辺業態なのか、本物の
飲食店なのかを分ける必要がある。店名も業種も Google から買うと課金対象SKUになるので、
**カテゴリ語を textQuery、推定位置の矩形を locationRestriction にして
「その place_id が返るか」**で輪郭を取った（`profile_types.py`）。同じ語を未到達と
到達の両方に当てて分布を比べるので、道具の癖は相殺される。

| | 未到達 (n=400) | 到達 (n=306) |
| --- | ---: | ---: |
| 本体（レストラン/居酒屋/ラーメン等） | 42.8% | 63.7% |
| 周辺（パン/弁当/惣菜等） | 13.0% | 5.6% |
| 飲食店以外（ホテル/スーパー/コンビニ） | 0.2% | 0.3% |
| 無反応 | 44.0% | 30.4% |
| **無反応を除いた本体の割合** | **76.3%** | **91.5%** |

未到達には周辺業態が2.3倍多いが、**それでも 4分の3 は本物の飲食店**である。
「飲食店以外」は両群とも 0.2〜0.3% しかなく、ノイズが混ざっているという説明は成り立たない。

語ごとに見ると、1つだけ逆向きに強く出るものがある。

| 語 | 未到達 | 到達 | 比 |
| --- | ---: | ---: | ---: |
| **スナック** | **9.8%** | **1.3%** | **7.6倍** |
| バー | 11.5% | 10.1% | 1.1倍 |
| レストラン | 12.0% | 24.5% | 0.5倍 |
| 弁当 | 1.2% | 9.0% | 0.14倍 |
| 焼肉 | 2.5% | 7.7% | 0.32倍 |

**取りこぼしの中心はスナック・バーである。** 雑居ビルの上階に入る夜の店で、
Overture も OSM も持っていない。逆に弁当屋・スーパーは到達側に多く、
「取りこぼしているのは弁当屋のようなノイズ」という見立ては数字で否定された。
実際の店名（既存DB由来）も、磯丸水産 横浜西口南幸店・鳥貴族 京急川崎駅前店・
不二家レストラン 数寄屋橋店・立食い寿司 根室花まる 銀座店・元祖やきとり串八珍
大手町ビル店といった、繁華街と雑居ビルのテナントだった。**戦略的対象外にはできない。**

## 4つ目のソース: 自治体の食品営業許可台帳

主KPI（③）の取りこぼしは名寄せの失敗ではなくオープンデータ側の欠落で、
中心はスナック・バーだった。ここを埋めるソースを探して、効果を実測した。

### なぜ IFAS だけでは足りないのか

IFAS（食品衛生申請等システム）には **2021年6月の食品衛生法改正以降**に
オンライン申請された分しか入っていない。許可は5〜8年で更新されるので改正前の
施設は順次入ってくるが、まだ大半が入っていない。改正前の台帳と IFAS に載らない分は、
**各自治体がオープンデータとして個別に公開している**。

鹿児島市の実測: IFAS 9,812 行に対し、改正前の台帳が別に 4,885 行あった。
未到達だった `與庵 in Liberty House` は改正前の台帳に在り、住所は
「鹿児島市千日町15番15号**4階**」だった。

### 取得経路は3つある

| 経路 | 例 | 座標 |
| --- | --- | --- |
| CKAN（BODIK・東京都・自治体独自） | 鹿児島市・中央区・名古屋市・宇都宮市 | 無い（ジオコーディングが要る） |
| **ArcGIS Hub の FeatureServer** | **渋谷区** | **`f=geojson` で座標つきで返る** |
| 自治体サイトの直リンク | 新宿区・江東区 | 無い |

CKAN の全文検索は語をばらして当てるので、「食品」「営業」だけで無関係な
データセットが 29,722 リソース釣れた。タイトルで許可台帳に絞って 580 リソース /
33自治体。国のカタログ（data.e-gov.go.jp）は自治体の台帳をほとんど持っていない。

座標が無い台帳は国土地理院の住所検索APIで解決する。**13,896 件を問い合わせて
命中率は 100%**、しかも全件が `full`（階数を含む住所そのまま）だった。
Google のSKUとは無関係なので「絶対に課金しない」制約に触れない。

### 効果（実測）

台帳の行 5,566 件を probe した結果。

| | 到達 | ③ |
| --- | ---: | ---: |
| 3ソースのみ | 1,086/1,747 | 62.16% |
| **+ 台帳（7,641行を probe）** | **1,188/1,747** | **68.00%** |

台帳を足しても②（正解率）は落ちていない。台帳の行と3ソースの行のうち、
表記を正規化した店名が完全一致し 30m 以内にあるものを対にして比べると、
**2,284 対のうち 2,274 対（99.56%）で同じ place_id を出している**。
食い違い 10 対は重複を除くと2店だけである。

（この検証は最初、名前類似度 ≥0.9 で対を作って 66.5% という数字を出した。
『スナック 美代子』と『スナック 鈴』が共通の接頭辞で 0.9 を超え、別の店どうしを
対にしていたためで、対の作り方が誤っていた。正規化した完全一致に変えて測り直した。）

台帳が入手できた6自治体で切ると、効果の大きさが自治体ごとに出る。

**渋谷区の 84.1% が上限の目安である。** 渋谷区の台帳だけ条件が3つ揃っている。

1. ArcGIS Hub から座標つきで取れる（ジオコーディングの誤差が無い）
2. 住所に階数が入る（雑居ビルの上階テナントを指せる）

**捨てた量が見えていないと改善できない。** どれも「落ちた理由の集計」を

## 重複行を merge し直しても①は上がらない

「①が上がらないのは、同じ店がコーパスに2行あって、片方しか確定しないからでは
ないか」を測った。統合時の重複判定（座標60mグリッド + 正規化店名の完全一致）を
「100m 以内 かつ 名前類似度 ≥0.90」まで緩めると、標本 3,000 件のうち **608 件
(20.3%)** に相方が見つかる。

そこで、未確定 990 件の相方 151 件を実際に probe した。

| | 件数 | 確定率 |
| --- | ---: | ---: |
| 未確定行の「相方」151 件 | 151 | **32.45%** |
| （比較）コーパス全体 | 5,850 | 66.65% |

**未確定の行の相方は、相方もまた未確定である**（確定率が半分以下）。同じ店なので
同じ理由で失敗する。当たり前だが、測るまでは分からなかった。

merge し直したときの①を、標本の重みで計算するとこうなる。相方のいる行は
コーパス内で2回数えられているので 1/2 の重みで数える。

| | 重み付き分母 | 重み付き確定 | ① |
| --- | ---: | ---: | ---: |
| 現状 | 3,000 | 2,010 | 67.00% |
| merge し直した場合 | 2,696 | 1,784 | 66.17% |

**上がらない。** 重複を潰すと分子からも分母からも同じだけ消えるので、率は動かない。
「dedupe を強くすれば①が上がる」は成り立たない。

## 1日あたりのリクエスト上限

`places.googleapis.com` の `SearchTextRequestPerDayPerProject` は **75,000/日**である。
IDs Only SKU は $0.00 のままなので**課金ではなく回数の上限**だが、使い切ると全ての
Text Search が 429 を返す。日付が変わるまで回復しない。

3ソース統合の 1,169,886 行に適用するなら 1 seed あたり 4 リクエストで
約468万リクエスト、上限が 75,000/日なら **63日**かかる。上限の引き上げを
申請するか、Issue の Step 3（需要駆動で必要な行だけ引く）に寄せるかの判断が要る。

**追記（2026-08-22）**: バッチ専用プロジェクト `nanitabeyo-places-batch` での
増量申請（#1331、Case# 74395977）が承認された。Text Search **3,000,000/日・
3,000/分**、Place Details 1,000,000/日・3,000/分。adaptive probing（実測
2.17本/seed）と合わせ、全コーパスの初回バックフィルは1〜2日で完了できる。

なお「Google に存在しうる行」は seed 全体の約 79%（2,278/2,866）、そのうち確定するのが
85.21% なので、全件を引いても確定するのは seed 全体の約 68% である。残りに
リクエストを使うより、必要になった行だけ引くほうが上限の使い方としては合理的である。

なお当初の実装は 429 を4回まで再試行していたため、1日上限に当たると全スレッドが
バックオフの sleep から出られず、完了0のまま「生きているのに進まない」状態になった。
本文に `PerDayPerProject` があれば即座に止めるようにしてある。


## Google 側から見た網羅率（Nearby Search で直接数える）

ここまでの網羅率は既存DB 103,440行を分母にしていた。しかし既存DBは Google の
飲食店の1割程度しか持っておらず（後述）、分母として小さすぎた。

Nearby Search は Text Search とは**別の日次クォータ**を持つ。
**ただしこの SKU は課金対象である**（当時は無料だと誤認していた。#1331）。半径を小さくすれば「返ってきた place_id はその半径
以内にある」ことが分かるので、座標を買わずに Google 側の店を位置つきで列挙できる。

### 密度（600点、`results/density_600.json`）

| | 件数 | Google 比 |
| --- | ---: | ---: |
| Google の飲食店 | 3,938 | 1.00 |
| オープンデータの行 | 6,040 | **1.53** |
| 既存DB の行 | 396 | 0.10 |

Google が返した place_id のうち既存DBに在ったのは **9.11%**。行数で見れば
オープンデータは Google より多く、少ないのは既存DBのほうである。

飲食型フィルタ（`includedTypes`）の妥当性も測った。既存DBの飲食店60件のうち
57件（95.0%）がフィルタつきで返る。漏れた2件は「たまご村 法月養鶏場」
「鮮魚山助」で、飲食店として分類されない方が自然なものだった。

### 敷き詰めて列挙した Google の店 1,747件（`results/google_coverage_db.json`）

既存DBの店を中心に40区画・半径25mの円1,000個を敷き、Google 側の place_id を
位置つきで集めた。各々の最寄りのオープンデータ行までの距離を測る。

**ただしこの数字は密度に汚染される。** 密集地ではオープンデータが Google の
1.5倍あるので「近くに何かある」は当たり前に近い。位置を同じ地域内でランダムに
ずらした偽データで同じ測定をして、下駄を測った。

| | 5m以内 | 10m以内 | 20m以内 | 40m以内 | 中央値 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 実際の Google の位置 | 42.5% | 76.9% | 96.6% | 99.4% | 5.9m |
| 75m ずらした偽位置 | 19.5% | 44.2% | 74.6% | 93.9% | 11.4m |
| 300m ずらした偽位置 | 9.7% | 22.6% | 47.7% | 75.3% | 21.3m |

40m では偽位置でも 75.3% が当たるので、**99.4% はほとんど密度の産物**である。
5m では 42.5% 対 9.7% で4倍以上の差があり、ここには本物の信号がある。

観測を「本当に対応する場合」と「たまたま近くにある場合」の混合とみて解く。
本当に対応する場合の距離分布は、名寄せで確定し既存DBの place_id と一致した
4,381組の座標差から実測できる（5m以内 46.3%、10m以内 70.5%）。

| しきい値 | 対応あり | たまたま | 観測 | 推定 |
| --- | ---: | ---: | ---: | ---: |
| 5m | 46.3% | 9.7% | 42.5% | **89.6%** |
| 10m | 70.5% | 22.6% | 76.9% | 100%（飽和） |

**Google の飲食店のうち、オープンデータに対応行があるのは約90%以上**である。

### 逆方向: オープンデータの行は実在するか

同じ40区画の内側（中心から70m以内）で数え直す。

| | 件数 |
| --- | ---: |
| Google の飲食店 | 974 |
| オープンデータの行 | 1,278（**1.31倍**） |

| | 5m以内 | 10m以内 | 20m以内 |
| --- | ---: | ---: | ---: |
| 実際のオープンデータ位置 | 19.2% | 59.5% | 95.0% |
| 120m ずらした偽位置 | 1.6% | 5.9% | 15.0% |

10m で 59.5% 対 5.9%。混合モデルで解くと **約83%** のオープンデータ行が
実在する Google の店に対応する。残りの約17%は閉店・重複・飲食店以外である。
ソース別の20m以内の当たり方は Overture 95.0% / IFAS 95.7% / OSM 93.0% で、
ソースによる差はほとんど無かった。

### ここから言えること

- **「オープンデータは Google Maps の半分しか無い」は成り立たない。** 位置で見れば
  Google の飲食店の約90%以上に対応行があり、行数ではむしろ1.3〜1.5倍ある。
- したがって**ソースを増やす方向の投資は割に合わない**。IFAS の追加取得も、
  Foursquare の追加も、この結論を変えない。
- 残っている課題は「同じ店だと分かる形で結び付けられない」ことである。
  `box_unique` は「Google に存在しうる行」の 85.21% を確定し、裁定後の誤りは
  0/2,716 だった。位置ベースの対応率 90% と掛け合わせると、
  **Google の飲食店の 3/4 程度には無料で place_id を付けられる**見込みになる。


## 課金してしまった箇所

この PoC の第一制約は「絶対に課金しない」だった。Text Search と Place Details は
守れているが、**Nearby Search で守れていない**。経緯と量を残す。

### 何を誤ったか

「課金は fieldMask で決まるので、`places.id` だけにすれば無料」という前提を、
Places API の全 endpoint に当てはめてしまった。**この前提が成り立つのは Text Search と
Place Details だけ**である。Nearby Search (New) には IDs Only の無料枠が無く、
fieldMask を `places.id` に絞っても Nearby Search Pro として課金される。

Google のサポートから明示的に指摘を受けて判明した（#1331 のクォータ増量申請への回答）。

> please be aware that Nearby Search (New) does not offer a free "IDs Only" tier.
> Any Nearby Search request, even if the field mask is strictly limited to places.id,
> will automatically trigger the billable Nearby Search Pro SKU.

### 発生量

| 用途 | リクエスト |
| --- | ---: |
| 初期の probe に入れていた `nearby`（`cache/probe.sqlite`） | 1,242 |

### 何が防げなかったか

課金ガードは fieldMask と応答のキーだけを見ていた。**課金性は endpoint ごとに
決まる**という視点が抜けていたので、「fieldMask は `places.id` だけ」という条件を
満たす Nearby Search は素通りした。

### 直したこと

`FreePlacesClient.search_nearby` は呼ばれた時点で `BillableEndpointError` を送出する。
送信前に落ちること（`request_count` が増えないこと）を単体テストで固定した。
`density.py` と `google_coverage.py` は冒頭に警告を書いたうえで残す。測定結果自体は
有効なので捨てないが、**再実行してはならない**。

### この誤りで得た結果の扱い

Nearby Search を使って出した数字（密度、Google 側から見た網羅率）は測定として有効で、
「オープンデータは Google の飲食店の約90%以上に対応行を持つ」という結論の根拠に
なっている。ただし**この結論はもう無料では再現できない**。同じことを無料で測るなら、
Text Search の矩形（`locationRestriction`）で店名を指定して引く方法しかなく、
店名なしで円の中を列挙する手段は無料SKUには存在しない。

## ラベルの無いところで精度を測る（帰無検定）

ラベル集合には構造的な偏りがある。既存DBと座標で突き合わせて作るので、
**座標が正しく、名前も一致する行しか入らない**。ところが①で取りこぼしているのは
まさにその逆の行である。ラベル 6,000 件のうち未確定は 177 件しかなく、
新しい層を足しても発火が 1〜2 件では精度を語れない。

そこで、ラベルの代わりに座標を壊して測る（`null_test_huge.py`）。

seed の座標を、同じ 0.5°（約55km）セル内の別の seed の座標と入れ替える。
都市は都市と、郊外は郊外と入れ替わるので密度は保たれる。移動距離の中央値は
13.2km で、最小でも 3.0km ある。**この状態では、その seed の本当の店は
±1km の矩形の外に居ることが確実**なので、矩形ベースの層が発火したら必ず誤りである。
発火率がそのまま空撃ち率になり、誤りの上限を与える。

同じ 990 件で層を比べた結果が次である。

| 層 | 本番の発火 | 帰無での発火 | 空撃ち率 |
| --- | ---: | ---: | ---: |
| ±500m 一意 ∧ (A∪B) | 78 | 44 | 4.44% |
| ±1km 一意 ∧ (A∪B) | 122 | 44 | 4.44% |
| ±500m 一意 ∧ B | 61 | 1 | 0.10% |
| ±1km 一意 ∧ B | 90 | 2 | 0.20% |

**A を裏取りに使うと、矩形をいくら広げても空撃ちが 44 件で頭打ちになる。**
A は 150m の `locationBias` でしかなく、矩形の外に本当の店が居ても座標の近所の
別店舗を返す。±25m や ±250m ならその「近所」が矩形とほぼ重なるので害が無いが、
±500m を超えると騒音になる。B（店名+住所、bias なし）は座標と独立なので、
矩形を広げても独立な証拠であり続ける。

### この物差しの限界

採用中の `box_unique`（±25m / ±250m ∧ A∪B）を、**確定した** seed 779 件で
同じように測ると空撃ち率は **1.54%**（12件）だった。上の 0.10〜0.20% より高い。
これは採用ルールのほうが危ういという意味ではない。母集団が違う。
（測定値は `results/null_test.json`）

- 確定した seed は「Google が名前で引ける店」なので、どこへ動かしても
  同名の何かが見つかりやすい
- 未確定の seed は「名前で引いても当たらない店」なので、動かしても当たらない

つまり空撃ち率は**同じ母集団の中で層どうしを比べるときだけ**意味を持つ。
上の表はすべて同じ 990 件で測っているので比較できる。層をまたいで
母集団の違う数字を並べてはいけない。

そして帰無検定は「本当の店が矩形の外に居る」失敗しか測れない。
**「座標は正しいが Google 側の表記が違うので矩形が空になり、矩形を広げたら
同名の別支店を掴んだ」という失敗は測れない。** `±1km 一意 ∧ B` が
帰無検定では 0.20% なのにラベルで誤りを出したのは、この型だった。
2つの物差しが食い違ったときは悪いほうを採る。

## ① を 70% に届かせようとして、測って棄却した層

`box_unique` の未確定は、3ソース標本 3,000 件のうち 990 件ある。内訳は次のとおり。

| 未確定の形 | 件数 | 割合(990中) |
| --- | ---: | ---: |
| `no_candidate_in_box`（±250m 矩形に同名が1件も無い） | 621 | 62.7% |
| `box_not_unique`（矩形に同名が複数） | 192 | 19.4% |
| 矩形は一意だが A も B もその place を挙げない | 177 | 17.9% |

この3つそれぞれに対して層を作り、**①の増分と、②への影響を必ず対にして**測った。
増分だけを見て採用すると②が落ちるので、片方だけの数字は載せない。

### 裏取り（A か B がその place_id を挙げていること）は外せない

「矩形に同名が1件しか無いなら、それで確定してよいのではないか」を最初に試した。
ラベル 6,000 件で測ると、①は 67.00% → 72.90% に上がる。しかし

> `|c_tight| = 1` かつ A も B もその place_id を挙げていない **195 件のうち、
> 正解は 2 件（1.0%）**

だった。矩形が一意でも、店名クエリがその店を指していないなら、それは
「近くにある別の店」である。この層を入れるとラベルでの不一致が 8 件から
215 件に増える。棄却。

### ±1km まで矩形を広げる（座標ずれの救済）

`no_candidate_in_box` の多くは「Google に無い」ではなく「オープンデータ側の座標が
ずれている」ように見える。A も B も1件返しているのに矩形だけが空、という形が並ぶ。
そこで矩形を ±1km に広げた層を4通り作り、2つの独立な物差しで測った。

- **ラベル**: 既存DBとの対応表。`box_unique` が未確定にした 177 件のうち、
  その層が発火した件数と正解数。
- **帰無検定**（`null_test_huge.py`）: 座標を同密度帯の別地点（中央値 13.2km 先）に
  入れ替えると、その店は矩形の外に出る。この条件での発火は**必ず誤り**なので、
  発火率がそのまま空撃ち率になる。990 件で測った。

| 層 | ①の増分 | ①(3,000件) | ラベルでの正解率 | 空撃ち率 |
| --- | ---: | ---: | ---: | ---: |
| ±1km 一意 ∧ (A∪B) が裏取り | +122 | 71.07% | — | **4.44%** (44/990) |
| ±1km 一意 ∧ B が裏取り | +90 | 70.00% | 1/2 | 0.20% (2/990) |
| ±1km に店名+住所で引いて一意 | +247 | 75.23% | **56/74 = 75.7%** | **7.47%** (74/990) |
| ±1km に店名+住所で引いて一意 ∧ A が裏取り | +98 | 70.27% | **42/45 = 93.3%** | — |

①だけを見れば全部「達成」だが、②を見ると全部落ちる。

`±1km 一意 ∧ B` は帰無検定では 0.20% と良いが、ラベルで発火した2件のうち1件が誤りだった。
その1件（`らーめん工房いちにぃさん`、ラベル距離 6.5m・名前類似度 1.00 の金ラベル）は、
±100m 矩形に店名で引くと候補が1件出るのにそれが自分の place_id でも DB の place_id
でもない、つまり **Google 側の表記が違う**ケースだった。座標は正しいのに矩形が空に
なるこの形では、±1km に広げると同名の別店舗を掴む。帰無検定は「本当の店が矩形の外に
居る」場合しか測れないので、この失敗の型を捉えられない。2つの物差しが食い違ったときは
悪いほうを採る。棄却。

### 矩形が一意でないときに A や B で1件に絞る

| 層 | ①の増分 | ①(3,000件) | ラベルでの正解率 |
| --- | ---: | ---: | ---: |
| 箱に複数 → A∩B で1件に絞れる | +45 | 68.50% | 48/63 = 76.2% |
| 箱に複数 → B で1件に絞れる | +43 | 68.43% | 50/65 = 76.9% |
| 箱に複数 → A で1件に絞れる | +36 | 68.20% | 9/23 = 39.1% |

同名の店が矩形内に2つあるとき、どちらが正しいかをテキストクエリの側から決められる、
という前提が成り立っていない。棄却。

### 店名を短縮して矩形を引き直す

Google 側の表記が違うせいで矩形が空になるなら、店名を短縮して引き直せば当たるはず、
という筋である。`jp_name_match.search_variant` で括弧と末尾の支店語を落とした形
（`神戸屋レストラン 浜田山店` → `神戸屋レストラン`）で ±25m / ±250m を引き直した。

| 層 | ①の増分 | ラベルでの正解率 |
| --- | ---: | ---: |
| ±25m 短縮名で一意（裏取り無し） | +29 | 2/11 = 18.2% |
| ±250m 短縮名で一意（裏取り無し） | +43 | 3/10 = 30.0% |
| ±25m 短縮名で一意 ∧ (A∪B) | +2 | 0/0 |
| ±250m 短縮名で一意 ∧ (A∪B) | +5 | 1/1 |

短縮名は「支店を落とした形」なので、同じ系列の別支店に当たる。裏取りを付ければ安全に
なるが、そのときの増分は +5 件（+0.17pt）しかない。棄却。

### 「矩形に候補なし」の 621 件は、そもそも Google に無いものが大半である

既存DB（Google 由来の 103,440 件）を使って、未確定 990 件の座標の周り 250m に
同名の店があるかを**APIを叩かずに**数えた。

| 未確定の形 | DBに同名あり(≥0.90) | 似た名前(0.60-0.89) | 近傍はあるが別名 | 近傍なし |
| --- | ---: | ---: | ---: | ---: |
| 矩形に候補なし（621） | 3 | 1 | 367 | 250 |
| その他の未確定（369） | 12 | 6 | 290 | 61 |

DB は Google 全体の一部（10万件）でしかないので「DBに無い＝Googleに無い」とは
言えない。それでも比率の差ははっきりしている。同名がDBに在る割合は
**候補なし 0.6% に対して、その他の未確定 4.9% と8倍**ある。矩形が空になるのは
「クエリの作り方が悪くて見つからない」からではなく、**その座標にその名前の店が
Google 側に無い**からだと読める。矩形を広げれば当然何かに当たるが、それは
別の店である。上の表で ±1km 系の層がことごとく②を落とすのは、これが理由である。

### 結論

**無料の証拠だけでは、① 70% と ② 100% は同時に立たない。**
①を 67% から 70% 以上へ動かす層は、測った範囲では全て②を落とした。
`box_unique` は①を 67% に留める代わりに、金ラベルでの誤りが 0 である。

## 棄却した作戦

| 作戦 | 棄却の理由 |
| --- | --- |
| A と B が一致したら確定（Issue のまま） | 負例での誤マッチ率 11.3%。「一致したら確定」は成り立たない |
| `locationBias` で座標を効かせる | bias は絞り込まない。大阪の店名を東京の bias で引いても大阪の店が返る |
| Nearby Search で近傍を列挙して名寄せ | 20件で打ち切られる。密集地では「居ない」と「打ち切られた」が区別できない |
| ±25m 矩形の一意性だけ（裏取りなし） | precision 97.90%。裏取りが無いと通る49件のうち正解は1件 |
| 候補を A∩B から選ぶ | ±25m 矩形が正解を1件だけ含んでいるのに、A∩B が別の店を指す例が実在した |
| ±25m で複数残った行を、矩形をさらに縮めて絞る | 下表。座標側の精度が足りず、絞った結果は当てにならない |
| ±25m で複数残った行を、A/B の合意で絞る | 最良でも 92.3%（26件中24件）。ここでも合意は効かない |

矩形を縮める案は筋が良さそうに見えたので実測した。対象は「±25m の矩形に同名が
複数残った」50件（ラベル付き）。

| 矩形 | 一意になり、かつ A か B が挙げている | うち正解 | precision | 0件になった |
| --- | ---: | ---: | ---: | ---: |
| ±12m | 2 | 1 | 50.0% | 17 |
| ±6m | 12 | 7 | 58.3% | 22 |
| ±3m | 9 | 6 | 66.7% | 33 |

縮めても当たらない理由は、seed 側の座標の精度が数十m しかないからである。±3m まで
縮めると「seed の座標に一番近い店」が残るが、その座標自体が数十m ずれているので、
残った1件が正しい保証がない。同名店が数十m 以内に複数ある行は、無料の証拠だけでは
決着しない。①の残りはここに集中している。

## Google 側の重複 place_id

`鮨かんどころ` で、こちらが引いた `ChIJOdlqqcfAQzUROIfP5uqdhkE` と既存DBの
`ChIJZTgUqcfAQzURRzb2dKFNJmE` が食い違った。両方とも ID Refresh で生存を確認でき、
**±5m の矩形の中に両方が入る**。矩形は外を実際に切り落とすことを確認済み
（±200m ずらすと0件になる）なので、これは同じ店に place_id が2つある状態である。
利用者の確認でも両者は同じ住所に解決した。

## まだ終わっていないこと

- **① 66.65% は目標の 70% に届いていない。** 無料の証拠だけで届かせる方法は、
  測った範囲では全て②を落とした（「① を 70% に届かせようとして、測って棄却した層」）。
  ここから先は「②を 100% から下げてよいか」の判断が要る。判断材料としては、
  `±500m 一意 ∧ B` が①を 69.03% まで上げ、帰無検定での空撃ち率は 0.10%（1/990）、
  ラベルでの発火は1件でそれは正解だった。ただしラベルの発火数が少なすぎて
  精度は測れていない。
- **② 100% は金ラベル 3,715 件に対しての 100% である。** 95%下限は 99.90% で、
  「1万件流したら誤りが最大10件出うる」までしか言えない。誤り0を保証する測り方は
  無い。全ラベル 6,000 件では誤り8件（99.863%）だが、その8件はラベル側が
  距離 28〜101m・名前類似度 0.50〜0.82 で結ばれたものである。
- **③ 59.36% の測定は、課金対象SKU（Nearby Search）で列挙した 1,747 店に依存する。**
  無料SKUだけで Google 側を列挙する手段は存在しないので、この数字は更新できない。
- IFAS の 157 自治体は全国 1,741 市区町村の 9.0% でしかない。参加自治体が増えれば
  seed は増えるが、①②の率そのものは変わらない見込みである。
- OSM は ODbL で、Overture の CDLA-Permissive とは継承条項の有無が違う。
  成果物のライセンス上の扱いを分けられるよう、`seed_id` の接頭辞で
  ソースが分かるようにしてある（`osm:type/id`）。

## 再現方法

数字は全て、コミットしてある成果物だけから再計算できる。Overture の parquet や
IFAS の157ファイルを取り直す必要はない。

```bash
mkdir -p out cache
for n in sample_3sources_3000 sample_ifas_labeled_2000 sample_merged_3000 \
         seeds_labeled_4000 seeds_v3_2500 labels_merged_all labels_strict; do
  gunzip -c results/inputs/$n.csv.gz > out/$n.csv
done
python3 cache_io.py load --archive results/probe_cache.csv.gz --cache cache/probe_all.sqlite

python3 resolve_rate.py --seeds out/sample_merged_3000.csv \
  --cache cache/probe_all.sqlite --rule box_unique --by-source
python3 evaluate_labels.py --labels out/labels_strict.csv \
  --seeds out/seeds_labeled_4000.csv --cache cache/probe_all.sqlite --rules box_unique
```

未取得分を取り切って①②を出し直すには `./resume.sh`（`PLACE_API_TEST` が要る）。

## 制約と、測れていないこと

- **②の分母は既存DBに載っている行だけ**である。既存DBは bulk-import のスナップショットで
  全件網羅ではないため、DB に無い店について名寄せが正しいかは、この方法では測れない。
- 裁定は無料SKUで取れる証拠（生存・矩形内かどうか）だけで行っている。店名や座標を
  買えばより直接的に判定できるが、それは本 PoC の第一制約に反する。
- OSM は ODbL で、Overture の CDLA-Permissive とは継承条項の有無が違う。成果物の
  ライセンス上の扱いを分けられるよう、`seed_id` の接頭辞でソースが分かるようにしてある。
