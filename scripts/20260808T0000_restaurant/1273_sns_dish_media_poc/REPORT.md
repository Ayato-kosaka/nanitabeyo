## 【最重要・新規】Meta 経路だけは「照合が要らない」。経路存在率 87.0%

判定表で `socials（Meta, #1314）` は **「実効は未実測」**のまま空欄だった。
オーナーに ¥60,000 の法人登記 + App Review を判断してもらうのに、
最大の経路の欄が空なのは筋が悪いので測った（`measure_overture_facebook_link.py`）。

### socials の内訳（Overture JP food_and_drink 789,612 行・全数）

| host | 店舗数 | 割合 |
|---|---:|---:|
| **facebook.com** | **701,284** | **88.81%** |
| instagram.com | 13,882 | 1.76% |
| twitter.com | 12,471 | 1.58% |

### 決定的な発見: Facebook リンクは 100% が「数値 Page ID」だった

標本300件中 **300件（100%）**が `https://www.facebook.com/840726819593067` の形式、
つまり **vanity name ではなく数値の Page ID** である。

これが効く理由は、ここまで測ってきた全経路との違いにある。

| 経路 | 店舗の特定方法 | 照合による損失 |
|---|---|---|
| YouTube（Route B） | 動画タイトルから店名を逆引き | precision 対策で locality 裏取りが必須。歩留まりの大半を失う |
| 店舗自社サイト | ドメインから店を推定 | portal 混入・precision 0.467 |
| 無料画像サービス | キーワード検索 → 後から店名照合 | 同上 |
| **Meta** | **Overture が Page ID を持っている** | **原理的にゼロ**。`GET /{page-id}` にそのまま渡せる |

**Meta 経路だけは「検索して当てにいく」のではなく「鍵が既に手元にある」。**
他経路が歩留まりの大半を失っている照合ステップが、この経路には存在しない。

### リンクは生きている

Facebook の **Page Plugin**（`/plugins/page.php`、認証不要の公式埋め込み）で生死を判定した。
実在ページは応答HTMLに `/plugins/page` を含み、存在しないIDでは含まない。
負性対照（存在しないPage ID 3件）は3回とも正しく dead と判定された。

同一標本300件を3回測った結果は **live 294 / 297 / 299**（98.00% / 99.00% / 99.67%）。
差は判定器ではなく Facebook 側の絞り（marker を含まない body を返す）由来で、
再試行を入れると負荷が増えて逆に下がった。**保守的に 98% を採る。**

> ### 88.81% × 98.00% = **経路存在率 87.04%**

### ただしこれは coverage ではない

87.04% は「**Meta の審査を通れた場合に、照合を挟まずに到達できる店の割合**」であって、
その先の「ページに料理写真があるか」「134カテゴリに当たるか」「埋め込めるか」は別。
**下流の実測には PPCA 通過が要るので、この環境では原理的に測れない。**
#1319 の外挿の誤りを繰り返さないため、推定値では埋めない。代わりに必要条件だけ出す。

> ### 70% に届くための必要条件: 下流の変換率が **80.4% 以上**であること

言い換えると「レストランの公式Facebookページ 10件のうち 8件以上に、
134カテゴリのどれかに当たる料理写真が1枚以上ある」なら 70% に届く。

### これが意思決定に効く

- 他の無料経路の合算天井は**上限 50.3%**（前節）。**70% はそもそも算術的に不可能**。
- Meta 経路は **87.04%** から始まるので、**70% が算術的に到達しうる唯一の無料経路**。
- Meta は #1314 で確認したとおり、**restaurant-listing 禁止条項が無い唯一のプロバイダ**
  （YOLP #1282 / Foursquare #1270 / 食べログ #1303 / Google Places #1313 は全て禁止）。
- ゲートは ¥60,000 の法人登記 + App Review で、登記費用は審査提出時まで繰り延べ可能（#1319 R8-C）。

**「70%を諦める」か「Meta のゲートを通す」かの二択であり、中間は無い**というのが現時点の結論。

## 【②実装】§39 埋め込みの死活監視: 無料の公式oEmbedで実測できた

`measure_embed_liveness.py`。①で発見した dish_media は自社GCSに実体を持たないので、
元動画が消えれば穴になる。`dish_media_external_embeddings` には
availability_status と `(availability_status, last_verified_at DESC)` の index が既にあるが
（20260812T0100:73）、**中身を更新する手段が無かった**。それを埋めた。

### 判定手段

YouTube 公式 oEmbed（`https://www.youtube.com/oembed`）。APIキー不要・無料。
`rights_basis='official_oembed'` と同じ公式経路なので、監視のために非公式な
スクレイピングを増やさずに済む（#1313/#1318 の ToS 論点を悪化させない）。

| HTTP | availability_status |
|---|---|
| 200 | available |
| 400 | ineligible（ID自体が不正） |
| 401 / 403 | private |
| 404 | deleted |
| 5xx / timeout | **unknown（既存状態を書き換えない）** |

最後の行が重要。5xx を deleted に落とすと、YouTube 側の一時障害で生きている
dish_media を一斉に消すことになる。実装上 unknown は必ず no-op にしてある。

### 実測（n=1,000、母集団 110,656本からデシル層化抽出）

```
合計: 判定 1,000 / 生存 978 (97.80%) / 判定不能 0
内訳: {'available': 978, 'private': 22}
HTTP: {200: 978, 401: 22}
```

- **生存率 97.80%**（Wilson 95%CI 96.79%–98.64%）
- **判定不能 0件**。1,000本すべてが 200 か 401 で確定した。プローブとして信頼できる
- **消失の内訳は private 22件 / deleted 0件。** 失われ方は「投稿者が非公開に切り替える」
  であって「削除」ではない。private は戻ることがあるので、`deleted` と同じ扱いで
  即座に purge するのは早い（後述の運用方針）

### 経年劣化は検出できなかった（ただし代理変数は弱い）

チャンネル内の新しい順の順位（rank）を年代の代理変数にしてデシル別に見た。

| decile(新→古) | 生存率 | upload_date 中央値 |
|---|---:|---|
| 0 | 100.0% | 2026-02-21 |
| 1 | 98.0% | 2023-11-02 |
| 2 | 98.0% | 2023-12-27 |
| 3 | 98.0% | 2025-05-10 |
| 4 | 100.0% | 2022-12-22 |
| 5 | 97.0% | 2023-02-02 |
| 6 | 94.0% | 2024-03-02 |
| 7 | 96.0% | 2021-12-15 |
| 8 | 98.0% | 2023-01-23 |
| 9 | 99.0% | 2021-09-01 |

94–100% に散らばるだけで単調な下降が無い。**少なくとも 2021-09 〜 2026-02 を跨ぐ
標本で、生存率は年代に対して平坦**である。

**ただしこれを「hazard を測った」と言ってはいけない。** rank↔upload_date の相関は
r=-0.671 で、中央値も単調でない（decile 3 が 2025年、decile 7 が 2021年）。
チャンネルごとに投稿頻度が全く違うため、rank% は年代を混ぜてしまう。
#1319 でスケール則を外挿しすぎた誤りと同じ轍を踏まないよう、ここで主張できるのは
**横断面の 97.80%** と **経年下降が見えないこと**までである。

### 掃き替えコスト

24並列で **28.6 probes/sec**（200本を7秒）。

| 対象 | 全件掃き替え時間 |
|---|---|
| ①のクロール全動画 110,656本 | 約 65 分 |
| #1319 の実 dish_media 12,557本 | 約 7 分 |

無料・キー不要でこの速度なので、**30日周期の全件スイープが現実的**。

### 運用方針の提案

1. **30日周期で全件スイープ**。生存率が平坦だったので、これ以上の頻度は無駄。
2. **`unknown` は絶対に上書きしない。** last_verified_at も更新しない（未検証のままにする）。
3. **`private` は即 purge しない。** 削除ではなく可逆なので、`private` が
   **2回連続**（=60日）続いたときだけ配信対象から外す。`deleted` は1回で外す。
4. 配信側は `availability_status = 'available'` を必ず絞り込み条件に入れる。
   既存の部分index（`dish_media_render_type_external_idx`）と組み合わせる。

## 【Round8 追記・最重要】現行DBは Google Places の派生データベースである（#1318）

本PoCは「外部ソースは規約で使えない」という理由で Foursquare・食べログ・Google Places を
次々に却下してきたが、**現行実装のほうが先に同じ条文に抵触している可能性が高い**ことが
コード監査で判明した。

- `shared/prisma/schema.prisma:566` の `google_place_id String @unique`（NOT NULL）により、
  **103,528店の100%が Google Places 由来のキーで作られている**（Place ID 無しの行は物理的に存在不可）
- Places Photo の**バイナリを GCS へ恒久保存し自社CDNで再配信**している
  （`create-dish-media-entry.service.ts:104,112` → `dish-media.assembler.ts:191`）
- **Googleレビュー本文と投稿者名も恒久保存**している（`dishes.service.ts:591`）

Google Maps Platform ToS 3.2.3(a)(b) のキャッシュ例外は **Place ID に限られる**ため、
上記はいずれも例外の外側にある。3.2.3(d)(iii)（listings/directory サービスの構築禁止）とも
`restaurants`+`dishes`+`dish_media`+`dish_reviews` の恒久テーブル群が正面から向き合う。

**これは 48% の評価軸を変える。** 現行103,528店は「規約クリーンな状態で作られた資産」ではない。
したがって無料・規約クリーンな合算天井 48.0% は、**現状より劣化した数字ではなく、
「規約を満たす前提で作り直した場合に初めて成立する数字」**と読むべきである。

法務判断が必要（Google との既存契約に Enterprise 条項があるか等）。詳細は #1318。

## 【Round8 追記】地方は地理の制約で、データ収集では解けない（#1319 R8-B）

「S は rural 36% と最も高いのにセル充足率が 0.0000%」という逆説の正体は**密度**だった。

| tier | 発見率 | 半径1km内の母集団店舗数 |
|---|---:|---:|
| urban | 0.710% | **197.54** |
| suburban | 1.640% | 27.45 |
| **rural** | **2.209%** | **5.66** |

**rural は urban の3.1倍よく発見できている。** 発見不足ではない。密度が35倍違うことが主因で、
rural の64.0%のセルは半径1km内に5店すら存在せず N=5 が構造的に不可能。

**100%発見できたとしても rural の構造上限は N≥1 で 5.317%**（現状 0.1139% は上限の 2.14%）。
発見努力の余地は47倍あるが、使い切っても目標70%には二桁足りない。

地方向けには「半径1km・134カテゴリ全部」ではなく **「半径を広げる + N=1 + any カテゴリ」**に
UX定義を変えるしかない（any指標なら現状 rural 8.39%）。

自治体オープンデータは規約クリーン（政府標準利用規約2.0 = CC BY 互換）だが、
**供給するのは店舗リストであって dish_media ではない**ため充足率を一切上げない。

## 【Round8 追記】PPCA は段階実行できる（#1319 R8-C）

#1314 が「鶏と卵」としていた問題は、**2つに分解すると半分は破れる**。

| 問い | 一次資料での答え |
|---|---|
| 申請用の**稼働アプリ**を承認前に用意できるか | ✅ **YES、コスト0円** |
| 承認前に**飲食店の実歩留まり**を測れるか | ❌ **NO** |

PPCA 原文より、development mode でも「自分が管理しないページ」は読めない。
一方 **自分が admin のページなら承認前・Business Verification 前に `/page/feed` を読める**ので、
App Review が要求するスクリーンキャストと稼働デモは0円で用意できる。

さらに Business Verification 原文に
`If your app will only be used by app users who have a role on the app itself you do not need to complete verification`
とあり、**#1314 の合同会社登記6万円はパイロット段階では不要**。advanced access を要求する
App Review 提出の時点で初めて必要になる。

**推奨は段階実行**: (1) 0円で稼働アプリとスクリーンキャストを作る →
(2) 協力店を数十件確保できるなら承認前に歩留まりの下限を実測 →
(3) そこで初めて6万円を支出して申請。

残る未知は**審査通過率**で、公式サンプル提出例は404で不在、却下理由一覧も承認率の公表値も
存在しないため机上調査では下げられない。

## 判定（Round6 時点。上の Round8 追記で一部が更新されている）

### ゴール

#843 が用意する母集団（Overture 789,612 + IFAS 264,135 + OSM 199,970）× 134 dish_category に対し、
**無料**で dish_media を発見する方法を確立する。オーナー要件は **全店で70%**。

### 到達点

| 経路 | 実測カバレッジ | 状態 |
|---|---:|---|
| YouTube 単独 | **18〜21%** | 供給上限として確定。同定手法の改善では動かない |
| ＋ 店舗自社サイト（#1304） | **48.0%** | 実効7.16%。HTML取得成功率50.2%が主因 |
| ＋ ポータル（#1303） | （65.7%） | **規約でアクセス自体が禁止 → 無効** |
| ＋ socials（Meta, #1314） | （100%） | **法人登記ゲート。ただし実効は未実測** |

**無料かつ規約上クリーンな天井は 48.0%。70%目標に 22pt 足りない。**

### 70%に到達しうる唯一の経路は Meta（#1314）

同一600店での経路存在率は **socials 91.3%**（内訳 **Facebook 90.17% / Instagram 1.33%**）で、
これだけが70%を超える。そして重要な発見が3つある。

1. **法人登記は障害ではない。** 合同会社なら登録免許税6万円・定款認証不要・1〜2週間。
   REPORT.md 前半の「法人未登記のため Business Verification を断念」は**過大評価に基づく判断だった**
2. **Meta には他ソースと違い事業モデル抵触が無い。** Google Places（ToS 3.2.3(d)(iii) が
   listings/directory を禁止）、Foursquare（derivative works 禁止）、食べログ等（営利目的の
   アクセス自体を禁止）、YOLP・ホットペッパー（対価事業を禁止）と異なり、
   Meta Platform Terms / PPCA / oEmbed Read に該当条項が見当たらない
3. **ただし実効は未実測。** PPCA は「稼働アプリを提出しての App Review」が必要で、
   承認前は投稿を1件も読めない（鶏と卵）。#1304 の類推（経路存在50.8% → 実効7.16%、約1/7）を
   当てはめると Meta の実効は13%前後となり70%に届かない可能性がある

### 商用ソースが軒並み使えない構造

| ソース | 判定 | 理由 |
|---|---|---|
| YOLP・ホットペッパー（#1282） | ❌ | 飲食店から対価を得る事業での利用を禁止 |
| Foursquare（#1270） | ❌ | 無料枠500コール + derivative works 禁止 |
| 食べログ等ポータル（#1303） | ❌ | 営利目的での**アクセス自体**を禁止 |
| Google Places（#1313） | ❌ | ToS 3.2.3(d)(iii) listings/directory 禁止。**最安$3,154でも使えない** |
| Meta（#1314） | ⚠️ | 該当条項なし。ただし審査と歩留まりが未確定 |

**主要な商用ソースが揃って「飲食店掲載事業での利用」を禁じている。**
これらのサービス自身が飲食店掲載事業の競合だからと考えられる。

### 確立した発見手法（YouTube、①として動作するもの）

3段構成。詳細は「Round3 の到達点」節。

1. **スノーボール**でチャンネルを発見（0.50 新規ch/クエリ、カテゴリ×エリア検索の5.7倍）
2. **チャンネル逆走査**で過去動画を全列挙（1コール最大400本、24.9店/コール = 検索の50倍）
3. **逆引き**で restaurant（`NameMatcher`）と dish_category（`dish_category_matcher`）を付与

### dish_media_catalog / dish_media_external_embeddings 生成パイプライン（実restaurant×category実データ）

issue本文の「candidate → restaurant match → category match → embed check → accepted dish_media」というfunnelを、`dev.dishes`（実際にrestaurant_id×category_idが紐づいている本番相当のレコード）を起点に、無料範囲（YouTube Data API v3のみ）で再現した。BigQueryやdev DBへの書き込みは一切行わず、`discover-restaurant-dish-media`コマンドの出力はすべて本ディレクトリ内のJSONに閉じている。

**サンプル抽出**: `dev.dishes` × `dev.restaurants` × `dev.dish_categories` をJOINし、日本国内(緯度24-46, 経度123-146)の2,648組から、SHA-256決定的サンプリングで20組を抽出(`fixtures/restaurant_dish_sample_20.csv`)。

**歩留まり改善ループ（設計→PoC→評価を3ラウンド実施）**: レビューで「dev.dishes全体で60%程度の紐付けが必要」という目標を示されたため、単発の実測で終わらせず設計を3回改善して評価するループを回した。

| ラウンド | 変更内容 | restaurant_matched | accepted_to_catalog |
|---|---|---:|---:|
| v1 | タイトル完全一致のみ、`maxResults=1`(top1のみ評価) | 1/20 (5%) | 1/20 (5%) |
| v2 | `maxResults=3`に増やし複数候補から最良を選択、概要欄(videos.list由来の全文)とチャンネル名も判定材料に追加、店名の括弧以降を除いた「コア名」でのマッチも許容 | 5/20 (25%) | 5/20 (25%) |

```

```

**v2で見つけた誤検出（重要な発見）**: 「Studio Sweets box 宇治金時」が概要欄一致でrestaurant_match_confidence=1.0として採用されたが、中身を確認すると動画は無関係な短編ドラマで、店名は「【撮影協力】\nStudio Sweets box 宇治金時」というロケ提供クレジットに載っていただけだった。**動画の主題ではなく単なる場所提供クレジットに店名が載っているだけの偽陽性**である。v3ではクレジット系キーワード（撮影協力/取材協力/ロケ協力/提供 等）の直後20文字以内に店名が出現するケースを検出し、confidence 0.0（不採用）にする補正を入れた。これにより誤検出は消えたが、母数が5→4に減っている（v2の25%は本番期待値としては使えない数字だった）。

v3の最終判定基準は`evaluate_restaurant_match()`に実装した4段階（issue本文22項の強度階層に対応）:

| confidence | 根拠 | issue22項の対応 |
|---:|---|---|
| 1.0 | 店名がそのままタイトルに出現 | Very strong |
| 0.9 | コア名(括弧以前)が投稿者チャンネル名に出現 | Strong(公式アカウント相当) |
| 0.8 | コア名がタイトルに出現 | Strong寄り |
| 0.7 | 店名/コア名が概要欄に出現、クレジット文脈でない | Medium（採用ラインちょうど） |
| 0.0 | クレジット文脈のみ、または根拠なし | Weak（不採用） |

v3で採用された4件はいずれも目視確認済みの真陽性: 「LANDMARK.」（山口市、ラーメン、タイトル完全一致）、「札幌らーめん ほくと亭」（タイトル完全一致）、「マッシモッタヴィオ」（タイトル完全一致）、「一休 (もんじゃ焼き、お好み焼きなど)」（タイトルにコア名「一休」が出現、実際にこの店主へのインタビュー記事動画）。生成された`dish_media_catalog`行・`dish_media_external_embeddings`行はユーザー提示の列構成（google_place_id, category_id, provider, external_content_id, canonical_url, thumbnail_url, media_type, availability_status, restaurant_match_confidence, category_confidence, published_at, last_verified_at, build_run_id / dish_media_id, provider, external_content_id, canonical_url, sanitized_embed_html, cache_expires_at, availability_status, last_verified_at）とそのまま一致する形で`out/dish_media_discovery_2026-08-12.json`に出力した。

**funnelの内訳（v3, ボトルネックの所在）**: `video_found=18/20(90%)`に対し`restaurant_matched=4/20(20%)`。つまり**ボトルネックは「動画が見つからない」ことではなく「見つかった動画がその店舗を名指ししていない」こと**にある。18件中14件はグルメ系YouTuber/foodvlogの実食レビューで、料理そのものは映っていても店名をタイトル・概要欄で明示していないケースが大半だった。これはissue本文が指摘する「SNS投稿の最大の難所は『どの実店舗のものか』」という論点そのものであり、テキストの単純一致というアプローチの構造的な限界でもある。

**60%目標に対する評価**: 5%→20%まで4倍改善したが、`0000_open_data_poc`の数十万店規模で狙う60%には無料範囲のYouTubeキーワード検索単独では届かない可能性が高い。issue本文が最初から提案している以下のアプローチの方が本命：
- **Route A(restaurant-aware discovery)**: Overture `socials`等で店舗の公式SNSアカウントが分かっている場合、キーワード検索ではなくそのアカウントの投稿を直接見にいく（今回のRoute B型「キーワード検索→後から店名照合」より格段に精度が高いはず。ただし本PoCの20サンプルにはOverture social linkの有無を確認する時間が無く未検証）

**quota状況**: 本ラウンドの反復で日次無料枠(10,000 units)の大半を消費した（本PoC全体でのYouTube累計消費は約8,300 units）。Route Aサンプルでの追加検証や、20件を超えるサンプルでの統計的により意味のある検証は、quotaリセット後（翌日）に持ち越す。

**結論**: 自分自身のInstagram Professional Accountの基本情報を読むことはStandard Accessで無料・即時にできるが、issue本文が必要とする「他店舗のアカウント/投稿を検索・確認する」(`business_discovery`)も、「投稿を自社サイトに埋め込む」(`instagram_oembed`)も、いずれもMetaの審査（App Review、無料だがリードタイムあり）を通らない限り`OAuthException code 10`で拒否される。TikTok/X oEmbedとは対照的に、**InstagramのoEmbedはMeta Graph API経由である以上「無料だが審査必須」の対象そのもの**であり、無審査で使える無料の抜け道は無い。

Threads APIは同じApp作成フローで「アプリレビュー必須（ユースケース3件）」が明示されていたが、Threads独自のOAuth（threads.net、Facebook Loginとは別建て）のセットアップは時間の都合で本PoCでは未実施。ただしInstagram/oEmbedと同じ審査ゲートが明記されていたため、同様の結論になる可能性が高い。

**Business Verificationは断念。** App Review・Business Verificationとも金銭的には無料だが、Business Verificationには法人登記情報の提出が必須。今回のユーザーは法人登記をしていないため、この経路は選択しないと決定した。したがって、Instagram/Threadsは「開発者自身のアカウントのStandard Accessのみ利用可能、他店舗検索・oEmbedを含む一般利用は不可」で確定とする。issue本文が当初から示していた「Instagramは主探索エンジンではなく補助ソース」という位置づけと整合する結論になった。

## Round3: Route B再モデル化と供給上限Sの実測（2026-08-13, #1279）

### 前提の訂正1: カバレッジモデル（Route A → Route B）

`coverage_youtube_only.py` / `coverage_combined.py` の `1-(1-p)^k` モデルは、k を「その店舗が既に `dishes` に持っているカテゴリ数」として与えていた。これは Route A（既存dish登録の範囲内でしか探索しない）の前提であり、オーナー確認により Route B が正であるため誤り。Route B では試行単位が「店舗」ではなく「クエリ」になるため、モデルの形自体が適用できない。両ファイルに SUPERSEDED を明記し、`coverage_route_b.py` で再定式化した。

### 前提の訂正2: 母集団（public.restaurants → Overture全件）

### Round3 アイデアA: チャンネル逆走査（採用候補）

飽和の実測が示すのは「YouTubeの供給が尽きた」ことではなく「**検索ランキングが尽きた**」ことかもしれない、という仮説の検証。同じ動画でも、その動画を作ったチャンネルの過去動画を全列挙すれば検索順位に縛られない。`measure_channel_traversal.py`。

**逆引きマッチャの精度**（ここを外すと全ての数字が無意味になるので先に確定させた）:

| 版 | 規則 | 実測 precision |
|---|---|---|
| v1 | 空白除去して全国辞書に部分一致 | **破綻**（`form`→perform、`ATER`→water、`TOBE`→October、`JA・PAN`→japan） |
| v2 | 日本語/ラテンを分離、ラテンは語境界必須 | 30〜40%（`Value`→"amazing value"、`ブレンド`→"バターブレンド"、`四天王寺`→駅名） |
| v3 | v2 + **locality/region の裏取りを必須**（#1273 §22） | **20/20 = ~100%** |

v3 は S の実測で使ったのと同じ規律。取りこぼし（地名を書かない動画）が出るため下限側に倒れる。

**同一マッチャ(v3)での経路比較**:

| 経路 | コール数 | 列挙動画 | distinct店舗 | 店/コール | 店/動画 |
|---|---:|---:|---:|---:|---:|
| 検索 (ytsearch10) | 40 | 400 | 20 | 0.50 | 0.050 |
| チャンネル逆走査 (最大400本/ch) | 25 | 8,394 | **344** | **13.8** | 0.041 |

**コールあたり28倍**。ただし**動画あたりの歩留まりはほぼ同じ**（0.041 vs 0.050）で、優位性は「1コールで何本見られるか」であって動画の質ではない。yt-dlp のレート制限はコール数で効く（#1283）ので、この差はそのままスループットの差になる。

**チャンネル間の重複はわずか 5.5%**（364組 → 344店）。種にしたチャンネルが地域特化（北海道・栃木・松山・大阪）だったためで、チャンネル数を増やしても当面は線形に伸びる見込み。

上位チャンネルは「ンまい屋さん」85店、「Nagomi vlog」69店、「ぐうるる飯」61店など、いずれも実在のグルメ系チャンネル。

**未検証（次のステップ）**: 日本のグルメ系チャンネルの母数、チャンネル数を増やしたときの飽和、400本上限を外した場合の伸び。これらが分かれば S=17.9% という供給上限そのものを測り直す必要がある（S は検索経由で測ったため、同じく過小評価の可能性がある）。

**外挿は当たった**。52チャンネルのデータから引いた `58.6 × ch^0.803` は400チャンネル時点で 7,206店 を予測し、実測は 7,026店 — **誤差2.6%**。2桁近い外挿が実測で裏付けられたので、1万チャンネルへの外挿もある程度信用してよい。

400チャンネルで引き直すと `distinct = 43.4 × ch^0.856`（指数はむしろ上がった＝飽和は想定より緩い）。

| チャンネル数 | 発見店舗 | dish_media | 総コール | 所要日数 |
|---:|---:|---:|---:|---:|
| 400（実測） | 7,026 | 7,335 | 850 | 0.04〜0.1日 |
| 1,000 | 16,112 | 16,821 | 2,125 | 0.1〜0.3日 |
| 10,000 | **115,768** | **120,864** | 21,250 | **1.1〜3.3日** |

コール効率は実測で **8.3 店/コール**（850コールで7,026店）。検索単独のRoute B（0.50店/コール）に対して **17倍**。

**既知の軽微な問題**: カテゴリ変種の衝突（「中華そば」が `そば` にも当たる）と取りこぼし（「らぁめん」が `ラーメン` に当たらない）。本番では `dish_category_variants` を使うため解消する見込み。

#### Round3 で却下したアイデア（再調査しないこと）

**アイデアB: フルメタデータ取得でカテゴリ付与率を上げる** → 却下。
「概要欄には料理名が書いてあるはず」という仮説だったが、カテゴリ不明の店舗特定済み動画40本をフル取得したところ、取得成功12本・うちカテゴリが付いたのは4本(33%)で、しかも「Early Bird The Bread」→定食 のような誤付与を含む。flat-playlist が1コール400本なのに対しフルメタは1コール1本なので、コスト400倍に対して得られるものが無い。publish直前の少数candidateに対する検証用途としてなら成立しうるが、bulk discovery では使えない。

**アイデアC: カテゴリを動画ではなく店舗側から取る** → 却下。
(a) 店名に134ラベルが含まれる場合、(b) IFAS の `業態` フィールドから引く場合、の2経路を実測したが **+1%(19本)** しか増えなかった。理由は、店名にカテゴリ語を含む店はそもそも動画タイトルにもカテゴリ語が出るため既に回収済みで、残余がそこに該当しないため。IFAS `業態` は70.2%埋まっているものの、値の大半は「食堂」「レストラン」「スナック」等の業種で134カテゴリに写像できない（写像できるのは ラーメン店1,790・焼肉店1,666・牛丼屋1,590 程度）。

これらの却下により、**category 付与率 62.3%（店舗特定済み動画に対して）がこの経路の実用上の天井**と確定した。カテゴリが付かない動画のタイトルに残るのは地名・「ランチ」「グルメ」「テイクアウト」等の一般語で、安価な手段では回収できない。

### 決着: チャンネル起点は「安い」だけで「広い」わけではない

「チャンネル逆走査は検索が返さない動画に到達するので、S=17.9%は過小評価では」という保留を実測で決着させた。チャンネル経由で発見した7,026店から120店を抽出し、**同じ店を店名検索(`ytsearch10:"{店名} {市区町村}"`)で引き直せるか**を測った。

```
検証 120/120 -> 店名検索で再発見できた 113/120 = 94.2%（地名裏取りあり）
                緩い判定(裏取りなし)   115/120 = 95.8%
```

**94.2%**。つまりチャンネル逆走査は隠れた供給層に届いているのではなく、**同じ店を桁違いに安く見つけているだけ**である。したがって:

- 店名検索は供給のほぼ完全な推定量であり、無作為600店で測った **S = 17.9%（深さ補正後20.6%）が実質の天井**
- チャンネル起点の価値は **カバレッジではなくコスト**（0.18店/コール → 5.4店/コール、約30倍）

### 供給上限で頭打ちにした最終推計

天井 = S × N = **141,341〜162,660店**（Overture 789,612 に対して 17.9〜20.6%）

| チャンネル | 天井適用後 | Overture比 | 天井の何% | コール | 日数 |
|---:|---:|---:|---:|---:|---:|
| 400（実測） | 7,163 | 0.9% | 4% | 850 | 0.04〜0.1 |
| 5,000 | 52,675 | 6.7% | 32% | 10,625 | 0.6〜1.7 |
| 10,000 | 82,552 | 10.5% | 51% | 21,250 | 1.1〜3.3 |
| 20,000 | 117,525 | 14.9% | 72% | 42,500 | 2.2〜6.6 |
| 50,000 | 152,856 | 19.4% | 94% | 106,250 | 5.5〜16.6 |

**60%目標（473,767店）は天井の2.9倍であり、YouTube単独では構造的に到達不可能。** これは実装や手法の改善で埋まる差ではなく、「日本の飲食店のうち、店名を識別できる形のYouTube動画を持つ店が約2割しかない」という供給側の事実による。

### 判定: 60%目標は到達不可能、ただし §28 の設計なら射程内

`coverage = S × R_eff` かつ `R_eff <= 1` なので `coverage <= S`。S(支店確定可能) ≈ 20.6% に対し目標60%は必要条件（S>=0.60）を満たさず、**パイプラインの改善では埋まらない差**（3倍）。

一方、#1273 §28（「dish_mediaが付いた店舗だけPostgreSQLへpublishする」）の設計で見ると:

```
789,612 × 20.6% ≈ 162,000 店舗
```

飽和の実測（R_eff = 0.69〜0.91）まで織り込んだ現実的な全国推計は **13.8% = 約109,000店**。これは現行DB（103,528店）とほぼ同規模である。

つまり **「全店舗の60%を埋める」は無理だが、「10万店舗規模のmedia付きDBをゼロから作る」ことはできる**。§28 が当初から示していた「dish_mediaが付いた店舗だけpublishする」という方針と整合する結論になった。
