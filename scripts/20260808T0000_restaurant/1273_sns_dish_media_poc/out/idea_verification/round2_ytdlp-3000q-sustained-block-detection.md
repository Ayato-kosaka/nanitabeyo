フェーズ2で使ったクエリは、フェーズ1の末尾300件と**完全に同一のクエリ文字列**(`tail -n 300 queries_2000.txt`)である。並列5(フェーズ1)と並列10(フェーズ2)でエラー率が偶然にも同じ12.7%になったが、失敗した具体的なクエリの集合を突き合わせると**重複はわずか3/38件**だった。つまり:
- 同じクエリでも実行のたびに成功したり失敗したりする → **クエリ内容に依存しない確率的なブロック**である(特定カテゴリ・特定県が"呪われている"わけではない)。
- 並列5→並列10に上げても、既に劣化した状態からのエラー率は悪化しなかった(12.7%のまま) → 少なくともこの実測範囲では、**並列度を上げること自体が新たなブロックを誘発した証拠は無い**。むしろ劣化は「累積負荷/経過時間」に紐づく現象で、並列度は主要因ではないという仮説を支持する。

### フェーズ3: 追加の回復性チェック(フェーズ2終了直後、アドホック)

フェーズ2終了(`run_burst300_p10.jsonl`最終行のts)から約2分後・約3分後に、`test_plan`外の追加確認として単発クエリを逐次実行した:

## 判定

**hypothesis (a)「時間経過/累積負荷でIP単位のレート制限が発火する」は実測で支持された(CONFIRMED)。** Round1の245クエリ・17分規模では検知できなかった劣化が、今回の2,000クエリ・27.6分規模では明確に観測された: 最初の約1,008クエリ(約15分)は0%エラーだったが、以降は8〜16%(平均約10%)のHTTP 403エラー率に恒常的に転じ、後半のさらなる増悪はなかった(=無限に悪化するわけではなく、ある水準でプラトーする)。これは「クエリ数」よりも「経過時間」または「累積リクエスト数の閾値」に紐づくレート制限機構が存在することを強く示唆する。

**hypothesis (b)「並列5→10で持続的高負荷によりブロック率が増える」は、この実測範囲では支持されなかった(反証寄り)。** 既に劣化した状態(フェーズ1後半)から並列10に切り替えても、エラー率はフェーズ1の同区間(並列5)と同水準(12.7%)に留まり、悪化しなかった。ただし「クリーンな状態から並列10のみで2,000クエリを回す」という直接比較は未実施であり、並列度そのものの寄与を完全に切り分けたわけではない。

**test_planのgo/no-go判定基準(「全区間でerror_rate<5%かつblock_marker_rateがほぼ0ならGo」)に照らすと、明確に`No-Go`。** 中盤7.5%・後半11.2%はいずれも閾値5%を上回り、後半error_rateは前半(0%)の「3倍以上」どころか有限倍にすらならない(0からの立ち上がりのため比較不能だが、実質的に「前半ゼロ→後半11.2%」は明確な悪化トレンドそのものである)。**6,298クエリのフルスイープを単発の連続並列5実行でそのまま回すのは推奨しない。**

副次的な発見として、**当初のブロック兆候キーワードリスト(`sign in to confirm`, `429`, `captcha`等)は今回発生した実際のブロック形態(`HTTP Error 403: Forbidden` on `Unable to download API page`)を一件も検知できなかった**。今後の本番運用の監視ロジックでは、returncode!=0そのものを一次シグナルとして扱い、キーワードマッチングは補助情報に留めるべきである。

## 次のアクション(人間向け)

1. **6,298クエリの全国フルスイープを1回の連続並列5実行で回す計画は見直しが必要。** 実測では約1,000クエリ(15分)を超えたあたりからエラー率が8〜16%で高止まりする。134カテゴリ×47都道府県の全量を対象にするなら、(a) 1セッションあたり800〜1,000クエリ程度で区切ってクールダウンを挟む、(b) 403エラーになったクエリはリトライキューに積んで後で再実行する(今回の実測では同一クエリでも試行によって成否が入れ替わっており、単純リトライで拾える可能性が高い)、のいずれか(または両方)を推奨する。
2. **クールダウンの十分な長さは本検証の範囲外で未確認。** 今回確認できたのは「負荷停止後3分時点でも12〜15%のエラー率が残っている」ことのみ。数十分〜数時間の待機でエラー率がゼロに戻るかどうかは追加の長時間試験(例: 30分間隔で少数クエリを打ち、回復曲線を実測する)が必要。
3. **監視ロジックのブロック兆候キーワードリストに`403`/`Forbidden`/`Unable to download API page`を追加すべき。** 今回の主要な劣化シグナルは事前に用意したキーワードでは検知できなかった。
4. 125件の403エラーは全て`returncode!=0`かつ`video_count=0`で、動画0件のfalse-negativeとしてではなく明確なエラーとして区別できている(サイレントな0件結果と本物のブロックが混同される心配は無い)。リトライ機構を組む際はreturncodeベースで判定すればよい。
5. 本検証は単一サンドボックスIPからの結果であり、本番運用時の実IP(クラウドVM等)でも同様のプラトー(15分/1,000クエリ前後で8〜16%劣化)が再現するかは別途要確認。IPが異なれば閾値も変わりうる。
