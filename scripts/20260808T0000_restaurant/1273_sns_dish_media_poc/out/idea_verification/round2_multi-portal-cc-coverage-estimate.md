# idea検証: multi-portal-cc-coverage-estimate

**title**: 複数ポータル(ぐるなび/Retty/ホットペッパー) Common Crawl収録率実測と全国カバレッジ試算
**判定**: **仮説はほぼ反証(REFUTED寄り)— ホットペッパーのみ小規模に成立、ぐるなび・Rettyは実質0**

食べログ単体(Round1実測: 東京都だけで5,135件・SNS抽出率70%)に対し、ぐるなび/Retty/ホットペッパーを
Common Crawl経由で追加すれば「重複補正込みで全国カバレッジが底上げできる」という仮説を実機検証した。
結論は逆で、**3ポータルのうち2つ(ぐるなび・Retty)は実質ゼロ、残る1つ(ホットペッパー)も全国で
高々1,700件強・実ハンドル抽出率7%程度に留まり、tabelog単体(東京都だけで3,500件超相当)を1桁下回る**。
複数ポータルを組み合わせても全国カバレッジの底上げには実質つながらないというのが実測結果。

加えて、ホットペッパーはサイト全体の利用規約(API規約とは別の一般ToS)に「商業目的での利用」「無断複製・
蓄積」を明文で禁止する条項があることを確認した。Common Crawl経由という技術的な迂回はこのToS上の
義務を免除しない。

## 実施内容と生の結果

### 0. CDX API (index.commoncrawl.org) の疎通確認 → 想定どおり不通、クラスタインデックス直読みにフォールバック

```
$ curl -sv --max-time 15 https://index.commoncrawl.org/collinfo.json
...
* Empty reply from server
```
5回リトライしても全て`HTTP:000`(Empty reply)。事前情報どおり本セッションでも不通が継続していた。
`data.commoncrawl.org`は生きている(`HTTP/2 200`)ことを確認済みなので、CDX APIサーバーが内部的に
参照している生インデックスファイル(`cc-index/collections/CC-MAIN-2026-30/indexes/cluster.idx`、
`cdx-NNNNN.gz`)を直接HTTP Rangeで取得し、index.commoncrawl.orgと同じ二分探索ロジックを手元のPythonで
再実装した。AWS署名・AWS CLIは一切不要(`aws`コマンド自体が本環境に存在せず、`commoncrawl.s3.amazonaws.com`
への直接アクセスは403だったが、`data.commoncrawl.org`経由なら同じオブジェクトが認証不要で200/206で
取得できた)。

```
$ curl -s -o cluster.idx https://data.commoncrawl.org/cc-index/collections/CC-MAIN-2026-30/indexes/cluster.idx
$ wc -l cluster.idx
877051 cluster.idx   # 300シャード(cdx-00000.gz〜cdx-00299.gz)分の境界キー、104MB
```
各行は `<SURTキー> <timestamp>\t<shardファイル名>\t<バイトoffset>\t<バイトlength>\t<累積行数>` の形式。
対象ドメインのSURTキー(例: `com,tabelog)/`)を二分探索でこの境界リストに当て、該当するシャードの
バイト範囲だけを`Range`ヘッダで取得・gunzipすることで、CDX APIと同じ結果を認証なしで得られることを
`com,tabelog)/`で再現確認した(Round1の5,135件と同オーダーの結果を再現、詳細は後述)。

### 1. 各ポータルの店舗詳細ページURL構造の実地確認

- **ぐるなび**: `https://www.gnavi.co.jp/`(トップ)ではなく、店舗個票は別ドメイン
  `https://r.gnavi.co.jp/{7桁英数ID}/`(例: `https://r.gnavi.co.jp/g040702/`)。実際にエリア一覧ページ
  (`https://r.gnavi.co.jp/area/aream2105/rs/`)から店舗リンクを抽出して確認。
- **Retty**: `https://retty.me/`は非ブラウザUAに対し**常に406**を返す(`curl -A 'Mozilla/5.0' https://retty.me/` → `406`)。
  ライブ確認は不能だったため、Common Crawlに残っていた過去クロールのHTMLから実URL構造を逆引きした。
  店舗詳細ページは `https://retty.me/area/PRE{都道府県2桁}/ARE{エリアID}/SUB{サブエリアID}/{店舗ID}/`。
  `PRE13/LCAT9/city/{cityコード}/` は個別店舗ページではなく「〇〇エリアのおすすめまとめ」的な
  **キュレーション記事ページ**であることが実データで判明(仮説のtest_planが想定していた店舗詳細URL
  パターンとは別物なので要注意)。
- **ホットペッパー**: `https://hotpepper.jp/` は `https://www.hotpepper.jp/` に302リダイレクト。ただし
  店舗詳細ページのCDXキー自体は`www`を付けない**裸の`hotpepper.jp`ドメイン**で記録されている
  (`jp,hotpepper)/strJNNNNNNNN/`)。実URLは`https://www.hotpepper.jp/strJNNNNNNNN/`。

### 2. ポータルごとのCDX件数(全国、Common Crawl CC-MAIN-2026-30収録分)

cluster.idxで各SURTプレフィックスが何個のシャードブロックに跨るかを先に確認したところ、
ぐるなび(r.gnavi.co.jp)・Retty(retty.me)・ホットペッパー(hotpepper.jp)はいずれも**1ブロック
(約3,000行/約245KB圧縮)に収まるか、せいぜい8ブロック**であり、tabelog(`com,tabelog)/`、10ブロック、
東京都だけで5,135件)と比べて全国合計でも収録規模が著しく小さいことが、フェッチ前の時点でほぼ確定した。

実際にRangeフェッチして中身を確認した結果:

| ポータル | 対象SURTキー | 全国CDX総件数 | 店舗詳細ページ厳密パターン一致件数 | うちstatus=200 |
|---|---|---:|---:|---:|
| ぐるなび (r.gnavi.co.jp) | `jp,co,gnavi,r)/` | 150 | **0**(全件`robots.txt`の重複クロール) | 0 |
| Retty (retty.me) | `me,retty)/` | 744 | 88 (`/area/PREnn/ARExxx/SUBxxxxx/数字/`) | **0**(全件406) |
| ホットペッパー (hotpepper.jp) | `jp,hotpepper)/` | 20,209 | 1,869 (`/strJ数字/`, ユニーク店舗ID) | **1,741** |
| (参考)食べログ 東京都のみ | `com,tabelog)/tokyo/*` | (Round1実測)7,541 | 5,135 | 5,135(status絞り込み後) |

※ ぐるなび・Rettyは上記が**全国合計**(cluster.idxで対象プレフィックスが1ブロックにしか跨らないことを
確認済みなので、サンプルではなく事実上の全数)。ホットペッパーも対象プレフィックスの全8ブロックを
余さず取得したため全国の(ほぼ)全数。tabelogの行だけはRound1同様「東京都のみ」の数字であることに注意
(全国合計はさらに大きいはずだが本ラウンドでは未計測)。

### 3. ぐるなび: 店舗ページがCommon Crawlにほぼ皆無

```
$ grep '^jp,co,gnavi,r)' gnavi.cdx | sed -E 's/ .*//' | sort -u
jp,co,gnavi,r)/robots.txt
```
店舗ホスト`r.gnavi.co.jp`のCDXレコードは全国で150件、その**全てがrobots.txtの反復クロール**
(異なる日時・異なるWARCセグメントでの再訪問)で、`/g040702/`のような実店舗ページは**1件も
存在しなかった**。ぐるなび側のrobots.txtはstrJ的な包括Disallowは掛けていない
(パラメータ付きURLの個別Disallowのみ)ため、規約でブロックされているわけではなく、単純に
このCommon Crawlスナップショットのクロールフロンティアが`r.gnavi.co.jp`の店舗個票まで
到達していない、という実測結果。原因(JS依存のリンク発見が難しい/優先度が低い等)は未特定だが、
「ぐるなびをCommon Crawl経由で使う」という発想自体が今回のスナップショットでは成立しない。

### 4. Retty: Common Crawl自身のクローラーもUAブロックされている

店舗詳細ページの厳密パターン(`/area/PREnn/ARExxx/SUBxxxxx/数字/`)は全国88件がCDXに存在したが、
**88/88件すべてWARC内のHTTPステータスが406**だった。WARCヘッダーを直接確認:

```
HTTP/1.1 406
...
vary: user-agent
content-length: 0
```
`vary: user-agent`が付いていることから、Retty側がUser-Agentでボット判定していることが分かる。
これは**Common Crawlの公式クローラー自身がRettyにブロックされている**ことを意味し、我々の
検証環境からの直接curlアクセスでも同じ406を再現した(`robots.txt`の取得すら406)。
店舗詳細ページ以外(`PRE13/LCAT9/city/*`のような「エリアまとめ記事」ページ、744件中144件)は
200で取れることもあったが、これらは個別店舗ページではなく複数店へのリンク集記事であり、
JSON-LDも`ItemList`/`BreadcrumbList`止まりで`LocalBusiness`の`geo`は含まれない。
Round1で確立した「CDXでURLが見えれば中身も取れる」という前提が、Retty個別店舗ページに関しては
**成立しない**ことを実機で確認した。

### 5. ホットペッパー: 技術的には成立するが規模が小さく、実ハンドル抽出率も低い

全国1,741件のstatus=200店舗詳細ページからランダム15件をWARCバイトレンジ取得(全て206成功)。

```
[0] https://www.hotpepper.jp/strJ001066878 -> html_bytes=69994 sns=2 jsonld=True
[1] https://www.hotpepper.jp/strJ000660391/ -> html_bytes=137529 sns=2 jsonld=True
...(15件中15件でJSON-LD Restaurant + geo座標を確認、15件中15件で"sns"ヒット2件以上)
```
一見15/15(100%)でSNSリンクが取れているように見えるが、中身を精査すると**その大半はホットペッパー
自身の共有ウィジェットの定型コード**だった:
- `https://platform.twitter.com/widgets.js` (シェアボタンのスクリプト、15/15件で出現)
- `https://www.facebook.com/dialog/share?app_id=114528591936629&href=...` (Facebookシェアダイアログ、15/15件で出現)
- `https://scontent-*.cdninstagram.com/...` (Instagram埋め込みウィジェットの画像CDN、2/15件)

店側が自ら貼った**本物のアカウントリンク**(`instagram.com/<ハンドル>/`形式で、シェアウィジェット・
CDN画像・トラッキングURLを除外したもの)は、**15件中1件のみ**(`https://www.instagram.com/buta.boshi/`、
「サムギョプサル専門店 豚星 京都河原町店」)。実ハンドル抽出率は**7%**で、Round1のtabelog(70%)の
1/10程度に留まる。tabelogの店舗ページはシンプルなHTMLで「SNS」欄に店の公式リンクを直書きしている
ケースが多いのに対し、ホットペッパーは自社シェアウィジェット・埋め込みウィジェットのノイズが
多く、ナイーブな正規表現(`instagram|tiktok|facebook|twitter|x\.com`)だけでは実用に耐えないことが
判明した(除外リストを整備すれば精度は上げられるが、その分ヒット件数自体がさらに絞られる)。

一方、JSON-LDについては全件で`schema.org/Restaurant`型の構造化データがあり、`address`(住所)・
`geo`(緯度経度)が綺麗に取れることを確認した(例: 中里菓子店、北区、`35.736945,139.749571`)。
SNSハンドル発見という当初目的には弱いが、**住所・座標ベースの店舗名寄せ(idea B相当)の入力データ
としては有望**という副次的知見が得られた。

```json
{
  "@type": "Restaurant",
  "name": "中里菓子店",
  "address": {"streetAddress": "中里1-6-11中里SUZUKIBLD", "addressLocality": "北区", "addressRegion": "東京都"},
  "geo": {"latitude": "35.736945", "longitude": "139.749571"}
}
```

### 6. dev.restaurantsとの突き合わせ(参考実施)

ホットペッパーで実ハンドルが取れた「豚星 京都河原町店」で`dev.restaurants`(2,439件)をLIKE検索したが
0件(`SELECT id, name FROM dev.restaurants WHERE name ILIKE '%豚星%'` → 0 rows)。Round1同様、
devデータの地域・件数がサンプル店舗と単純に重ならないだけで、手法の失敗ではない。

### 7. ToS確認(必須)

**ホットペッパー(リクルート)のサイト全体の利用規約**(API規約とは別、`https://cdn.p.recruit.co.jp/terms/hpg-t-1002/index.html`、
サイトフッターから発見)を全文取得しキーワード精査した結果、以下の条項を確認:

> 第10条(利用者の禁止事項) 利用者は、本サービスの利用にあたって、以下の行為を行ってはならないものとします。
> 【3】本サービスを商業目的で利用する行為
> 【18】本サービスの全部又は一部を、当社に無断で、転載、転送、蓄積、販売、貸与、再許諾、出版、
> 自己利用の範囲を超えて複製、複写する行為

これはAPI固有の条項ではなく、**サイト全体に適用される一般利用規約**である。【3】は「商業目的での
利用」そのものを禁止事項として明記しており、API規約の「飲食店から対価を得るビジネスでの利用禁止」
よりもさらに広い(業種を問わず商業目的一般を禁じる)。【18】は取得経路を問わず「無断複製・蓄積」
を禁じており、Common Crawl経由でHTMLを取得しSNSハンドルの対応表として体系的に蓄積する行為は、
文言上この禁止事項に抵触する可能性が高い。**アクセス経路(直接スクレイピング vs Common Crawl経由)が
変わっても、データの出所がホットペッパーである以上、この規約上の義務は消えない**という、
test_planで示唆されていた懸念は妥当だったことを確認した。

- **Retty**: `robots.txt`を含め全リクエストが406で弾かれ、ToS本文ページ(`/rule/`, `/terms/`,
  `/announce/community-policy`等)にも到達できなかった。CC経由で取得できた過去クロールHTML内にも
  ToSページへのリンクは見つかったが(`https://retty.me/announce/community-policy`)、そのページ自体も
  406でライブ内容を確認できず、ToSの具体的文言は本セッションでは検証不能だった(このアクセス困難性
  自体、Rettyのボット対策の厳しさを示す実測結果ではある)。
- **ぐるなび**: 店舗詳細ページ自体がCommon Crawlにほぼ存在しないため優先度を下げ、深追いしなかった
  (ToSの有無以前に、そもそも取得できるデータがない)。

なお、CDX経由の取得はポータルのサーバーに直接アクセスしないため、不正アクセス禁止法/CFAA的な
「アクセス制御回避」のリスクは直接スクレイピングより低いというtest_planの整理は技術的に妥当である。
一方で、抽出したSNSハンドルを「店舗×SNSアカウントの対応表」として体系的に蓄積し事業利用する行為は、
各ポータルが投資して収集した店舗ディレクトリの複製権・データベースの著作権(編集著作物性)に
抵触しうる中〜高リスクとして扱うべきであり、本番投入前の法務レビューが必須という所見は、
ホットペッパーの明文規約によって裏付けられた。単発のSNSハンドル1件を確認する行為(Enrichment)と、
全国規模でポータルの店舗一覧を組織的に複製する行為(Discovery基盤化)ではリスクの質が異なる
という整理も維持する。

## 全国到達可能店舗数の試算

| チャネル | 全国CDXでの店舗詳細ページ数 | 実SNSハンドル抽出率 | 概算・実ハンドル数 |
|---|---:|---:|---:|
| 食べログ(東京都のみ、Round1実測) | 5,135 | 70% | 約3,595(東京都だけで) |
| ホットペッパー(全国) | 1,741 | 7%(精緻化後の実測) | 約122 |
| Retty(全国) | 0 | — | 0 |
| ぐるなび(全国) | 0 | — | 0 |

tabelogは東京都単体の数字であるにもかかわらず、他3ポータルの**全国合計**を1桁以上上回っている。
「複数ポータルを重複補正込みで合算すれば単独ポータルより高い全国カバレッジが出せる」という仮説の
前提(各ポータルが同オーダーの規模感を持つ)が成立しなかったため、重複率の実測(手順6)や
inclusion-exclusion補正の計算自体に意味がなくなった。ホットペッパーの約122件は歩留まりとして
tabelogに対する足しにはなるが、「全国・全カテゴリの現実的カバー」という当初ゴールに対しては
無視できる規模である。地方1県(山梨県等)での個別集計は、ぐるなび・Rettyの全国分がすでに実質0、
ホットペッパーの全国分もこの規模である以上、地方だけを取り出しても追加的な結論は出ないと判断し、
本ラウンドでは実施を見送った(必要になれば同じcluster.idxベースのパイプラインで即座に再現可能)。

## 評価まとめ

| 検証項目 | 結果 |
|---|---|
| index.commoncrawl.org (CDX API) 疎通 | 不通(Empty reply、5/5失敗)。cluster.idx直読みへのフォールバックで代替成立 |
| cluster.idxベースの手動CDX検索(認証不要) | 成功。tabelogで同オーダーの結果を再現し手法の正当性を確認 |
| ぐるなび店舗ページのCC収録 | 実質0件(全国150件は全てrobots.txtの重複、店舗個票0件) |
| Retty店舗ページのCC収録・取得 | CDXには88件存在するが**取得は0/88(406、CC自身のクローラーもUAブロック済み)** |
| ホットペッパー店舗ページのCC収録・取得 | 全国1,741件成功(206取得も15/15成功)。ただしtabelog比で1桁少ない規模 |
| ホットペッパー ナイーブSNSリンク検出率 | 見かけ上15/15(100%)だが大半が自社シェアウィジェットの定型コード |
| ホットペッパー 実SNSハンドル検出率(精緻化後) | 15件中1件(7%)。tabelogの70%を大きく下回る |
| ホットペッパー JSON-LD構造化データ | 15/15件で`schema.org/Restaurant`の住所・geo座標を確認(SNS用途より名寄せ用途で有望) |
| ホットペッパー サイト全体ToS | 「商業目的利用」「無断複製・蓄積」を明文で禁止する条項を実際に確認、API規約より広い |
| Retty ToS本文 | 406ブロックにより本セッションでは文言確認不能 |
| dev.restaurantsとの実マッチ | 0/1(devデータ規模不足、Round1と同様の想定内の結果) |

**総合結論**: 「複数ポータルを組み合わせれば食べログ単体より高い全国カバレッジが出せる」という
仮説は、ぐるなび・Rettyについては実測で明確に反証された(Common Crawl上のデータがほぼ存在しない、
または存在してもボットブロックで中身が取れない)。ホットペッパーのみ技術的には成立するが、
規模(tabelogの1桁未満)・実ハンドル抽出率(tabelogの1/10)・ToS上の商業利用禁止条項の3点で
tabelog単独より明確に劣後する。したがって本アイデアは「複数ポータル化による全国カバレッジの底上げ」
という主目的では**採用に値しない**。ただしホットペッパーのJSON-LD(住所・geo)は、SNSハンドル発見とは
別目的(店舗名寄せ・座標マッチング)の補助データとしては小規模ながら価値が残る。
