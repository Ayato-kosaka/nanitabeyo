# アイデア検証: adaptive-density-weighted-geo-cells

**実店舗密度に応じた可変粒度ジオセル設計(都道府県→区/市町村への適応的分割)**

## 判定: 部分的に不成立(PARTIALLY DISCONFIRMED)

密度の偏りそのものは実測どおり確認できたが、「適応的分割でクエリ予算を1〜2桁圧縮できる」という中核の定量仮説は誤りだった。それどころか、素朴な都道府県一律粒度と比べると適応的分割は**クエリ予算を悪化させる**(分割は追加するだけで、統合しない限りセル数は単調増加するため)。さらに実機のyt-dlp検索で、地名を細かくするほどLong-tailカテゴリの精度が悪化するという、仮説が想定していなかった副作用も確認した。

## 1. 密度の実測(再検証)

`dev.restaurants` を日本国内bbox(緯度24-46/経度123-146)で絞り、`address_components` から `administrative_area_level_1`/`locality` を抽出して集計した(スクリプトはこのレポート末尾に埋め込み・再現可能)。

| 指標 | 仮説の記載値 | 本検証での実測値 |
|---|---|---|
| bbox内 総件数 | 2,097 | **2,101** |
| 東京都 | 1,281件(61%) | **1,285件(61.2%)** |
| 大阪府 | 101件 | **101件** |
| 神奈川県 | 86件 | **86件** |
| 千代田区 | 306件 | **306件** |
| 渋谷区 | 250件 | **254件** |
| 中野区 | 14件 | **14件** |
| 目黒区 | 6件 | **6件** |
| 練馬区 | 5件 | **5件** |

ほぼ完全に一致した(データが数日で微増しているため±数件のズレのみ)。**密度の偏り自体は事実**であり、東京都だけで6割強、区単位でも2桁の差がある。

market_salienceのバケット分布も実測(0.4-1.0を6分位): `23, 7, 34, 42, 14, 14` 件で、仮説が主張する「広く分布」という定性的な主張とも整合する。

### データ品質上の副次的発見(仮説には無かった点)
- `address_components` の `longText` は**日本語と英語が混在**していた(例: `東京都` と `Tokyo`、`大阪府` と `Osaka` が同じテーブル内に併存)。正規化しないと同一都道府県が別集計になり、密度分析そのものが歪む。今回は6件の英日マッピングを手動で補正して集計した。
- bbox内2,101件のうち **45件(2.1%)** は `administrative_area_level_1`/`locality` のいずれも抽出できない(住所コンポーネントにその型が無い)。
- **観測された都道府県は47のうち29のみ**、区市町村は1,741のうちわずか**108combo**だった。dev環境のスナップショット(2,101件)は本番想定の70万件よりも遥かに疎で、かつ東京偏重のサンプルであるため、この後のクエリ予算試算をそのまま本番スケールに外挿することはできない(詳細は3節)。

## 2. クエリ予算シミュレーション(test_planのステップ2)

ルール:「都道府県内の店舗数がしきい値Xを超えたら市区町村単位に分割、それ以外は都道府県単位のまま」。しきい値Xを{10, 30, 50, 100}で振り、`merge_sparse`(低密度県を8地方区分でまとめる簡易版)ありなしも試した。134カテゴリ・YouTube Data API v3(100 units/クエリ、無料枠10,000 units/日)換算。

| 設計 | セル数 | 総クエリ数(×134) | units | 無料枠での必要日数 |
|---|---|---|---|---|
| **都道府県一律(29県のみ観測)** | **29** | **3,886** | 388,600 | **39日** |
| 適応分割 X=100(merge無) | 59 | 7,906 | 790,600 | 80日 |
| 適応分割 X=100(merge有) | 56 | 7,504 | 750,400 | 76日 |
| 適応分割 X=50(merge無) | 77 | 10,318 | 1,031,800 | 104日 |
| 適応分割 X=50(merge有) | 74 | 9,916 | 991,600 | 100日 |
| 適応分割 X=30(merge無) | 81 | 10,854 | 1,085,400 | 109日 |
| 適応分割 X=10(merge無) | 100 | 13,400 | 1,340,000 | 134日 |
| **市区町村一律(108comboのみ観測)** | **108** | **14,472** | 1,447,200 | **145日** |

### 判明した事実
1. **適応分割は都道府県一律より必ず高くつく**。分割ルールは「しきい値を超えたら分割」しかせず、疎な県を統合する仕組みが弱い(merge_sparseを入れても効果は数%程度)ため、セル数は都道府県一律(29)を下回ることが構造的にない。最も安いX=100(merge有)でも56セル・76日で、都道府県一律の39日の**約2倍**である。
2. **市区町村一律との比較でなら圧縮効果はある**が、その幅は「1〜2桁」ではなく**最大でも約1.9倍(145日→76日)**にとどまった。仮説のscale_reasoningが主張する「1桁〜2桁圧縮」は、比較対象を「本番70万件規模で全1,741市区町村を叩く233,294クエリ」という別スケールの数字に対して行っており、**本検証で実際に集計した108combo(=14,472クエリ)とは前提が食い違うapples-to-orangesの比較**だった。dev環境の2,101件は1,741市区町村のうち108しかカバーしていないため、この場でその圧縮率を実証することはできない。
3. 本番の70万件規模では実質的に全1,741市区町村に店舗が存在すると見込まれ、その場合は市区町村一律ベースラインが仮説の想定どおり233,294クエリに近づく可能性が高い。したがって「適応分割が本番でどれだけ効くか」は**このdevスナップショットでは検証不能**であり、真の全国店舗分布(または人口統計等の代理指標)が無いと精度の高い試算はできない。

## 3. 実機yt-dlp検索によるセル粒度別の実質的な影響(test_planのステップ3)

`sns_dish_media_poc.py youtube-search-ytdlp`(Google API quota消費ゼロ)で、High-salienceカテゴリ「寿司」とLong-tailカテゴリ「アクアパッツァ」を、密な区(千代田区)・疎な区(中野区)・都道府県(東京都)の3粒度でそれぞれ検索した(各5件取得)。

**寿司(High-salience)**: 3粒度すべてで妥当な結果、かつ千代田区/中野区間で動画IDの重複ゼロ。
- `寿司 千代田区` → `wXMeYKf8o9I` 「【日本】東京都千代田区「鮨大前」[Japan] "Sushi Daizen" in Chiyoda Ward」など5/5件が店舗特定可能な寿司動画
- `寿司 中野区` → `5jHGr_vxC5A` 「東京 中野散策【立ち食い寿司横丁 中野サンモール】」など5/5件が中野の寿司店動画
- → **細分化は高需要カテゴリでは機能し、区ごとに別の店舗コンテンツを取得できている**(仮説の想定どおり)。

**アクアパッツァ(Long-tail)**: 区レベルに細分化すると地名がノイズとして支配的になり、精度が崩壊した。
- `アクアパッツァ 千代田区` → 5件中4件が無関係(例: `ToD7qobloS4` 「2026 Chiyoda City Board of Education 12th Regular Meeting」、`Wsy1HRRW9N8` 「千代田区と徳川家康公【後編】」)。料理動画は1件のみ。
- `アクアパッツァ 中野区` → 5件中**5件全て無関係**(例: `wrti_vVqIQs` 「【中野区まちづくり】令和8年12月以降 中野駅西改札→中野四季の都市方面デッキ イメージ動画」)。中野区の都市開発PR動画がヒットしただけで、料理動画はゼロ。
- `アクアパッツァ 東京都`(都道府県粒度) → 5件中5件が妥当(例: `48DnEK41uv0` 「【一流イタリア料理店】リストランテ アクアパッツァ ディナー実食」)。

→ **仮説が想定していなかった副作用**: 「密な地域ほど細かく割るべき」という設計は検索エンジン側のクエリ予算(=ヒット件数)の話であり、YouTube検索のランキング上は稀少なLong-tailカテゴリほど地名キーワードの比重が支配的になり、無関係な行政・まちづくり系動画に埋もれる。つまり**適応分割の最適な粒度はカテゴリの人気度によって逆方向に振れる**(High-salienceは細かく割るほど良いが、Long-tailは粗いままの方が精度が高い)。この効果はセル数×クエリ数の予算計算だけでは捉えられない。

## 総合評価

| 検証項目 | 結果 |
|---|---|
| 密度の偏り(東京61%、区で2桁差)の実在 | ✅ 確認(数値はほぼ完全一致) |
| market_salienceの分布の広さ | ✅ 確認 |
| 適応分割が都道府県一律よりクエリ予算を削減する | ❌ 不成立(むしろ約2倍に悪化) |
| 適応分割が「1〜2桁」圧縮を達成する | ❌ 不成立(市区町村一律比で最大でも約1.9倍) |
| 本番スケール(70万件)への外挿可能性 | ⚠️ devスナップショットが疎すぎて検証不能(29/47都道府県、108/1,741市区町村しかカバーしていない) |
| 細粒度化がカテゴリを問わず有効 | ❌ 不成立(High-salienceでは有効、Long-tailでは精度が崩壊) |

**結論**: 密度に応じた可変粒度という発想の方向性(疎な地域を都道府県のまま留める)は無駄クエリを避ける上で理にかなっているが、このアイデアが主眼に置いていた「クエリ予算の1〜2桁圧縮」は本検証のデータでは再現できず、むしろ素朴な都道府県一律の方が予算面では優位だった。また実際にYouTube検索で確認したところ、粒度をむやみに細かくするとLong-tailカテゴリの精度がむしろ悪化するという、予算計算だけでは見えない副作用が実機で確認された。次に検討すべきは「セル数を減らす」方向のアイデア(例: カテゴリの人気度によって検索粒度を変える、地名ではなく駅名/ランドマークを使う等)であり、本アイデアをこのまま採用することは推奨しない。

## 再現方法

```bash
# 密度実測(psql, dev.restaurants, 読み取り専用)
psql "$DATABASE_URL" -c "
  with jp as (select id, address_components from dev.restaurants
    where latitude between 24 and 46 and longitude between 123 and 146),
  p as (select jp.id,
    coalesce((select comp->>'longText' from jsonb_array_elements(address_components) comp
      where comp->'types' ? 'administrative_area_level_1' limit 1), 'UNKNOWN') as prefecture,
    coalesce((select comp->>'longText' from jsonb_array_elements(address_components) comp
      where comp->'types' ? 'locality' limit 1), 'UNKNOWN') as locality
    from jp)
  select prefecture, locality, count(*) from p group by prefecture, locality order by prefecture, count(*) desc;
"

# yt-dlp実機検索(quota消費ゼロ、最新yt-dlp 2026.07.04 + Python3.11が必要)
python3 sns_dish_media_poc.py youtube-search-ytdlp \
  --queries <(printf '寿司 千代田区\n寿司 中野区\n寿司 東京都\nアクアパッツァ 千代田区\nアクアパッツァ 中野区\nアクアパッツァ 東京都\n') \
  --max-results 5 --output out/density_test.json
```

シミュレータ本体(`verify_adaptive_geo_cells.py`)と生データCSV(`pref_locality_counts.csv`)はこのセッションのスクラッチパッドに置いた一時ファイルで、リポジトリには含めていない(このディレクトリ運用ルール「新規ファイル作成のみ・既存ファイル不変更」に従い、恒久的な検証ツールとして残す場合は別途チケット化を推奨)。
