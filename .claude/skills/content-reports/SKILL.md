# Content Reports

通報を「消すか消さないか」で悩むと毎回ぶれる。**カテゴリを 1 つ選ぶだけ**にして、
処置はカテゴリ側に固定する。判断が速くなり、同じ事案で結論が揺れなくなる。

## 絶対に守ること

この 4 つは、他のどの判断よりも優先する。

1. **通報だけでコンテンツを消さない。閾値でも消さない。消すのは常に人の承認を得てから。**
   通報爆撃がそのまま検閲の道具になる。この方針はテーブル設計にも書いてある
   （`20260825T0500_create_content_reports.sql` の「通報しても投稿は即時非表示にしない」）
2. **`reason_text` を外部へ転記しない。** 自由記述で、第三者の個人情報を含みうる。
   GitHub Issue にも、チャットの引用にも、PR 本文にも出さない。
   出してよいのは `reason_code`（選択式）と件数だけ
3. **通報された画像・動画を公開しない。** `evidence-collect.yml` の公開先は
   **公開バケット**である。通報対象のメディアをそこへ上げると、
   問題のあるコンテンツを自分たちで再配布することになる。**見るのは `posts?ids=` と GCS の URL を
   貼って、オーナー自身に開いてもらう**（§5）
4. **確信が持てないものを断定しない。** 確信度を必ず添え、低いものはオーナーへ回す

## 前提（コードで確認済みの事実）

| 事実 | 出典 |
| --- | --- |
| 対象は投稿（`dish_media`）とレビュー（`dish_reviews`）の 2 つだけ。ユーザー・店舗は対象外 | `content_reports.target_type` の CHECK |
| 1 人が同じ対象を何度も通報できない | `UNIQUE (reporter_user_id, target_type, target_id)` |
| **匿名ユーザーも通報できる**（`users` 行が無い）。`reporter_user_id` に FK は無い | 同マイグレーションのコメント |
| このテーブルは表示側から参照されない。通報の有無で見え方は変わらない | 同上 |
| RLS はポリシー無しで有効。クライアント直アクセス不可、API（service role）経由のみ | 同上 |
| ステータスは `pending` / `reviewing` / `actioned` / `rejected` | `status` の CHECK |

## 1. 読む

`content_reports` は PostgreSQL にある。**`db-script-run.yml`** で `scripts/` 配下の
Python を資格情報つきで動かして読む。BigQuery ではない（error-triage とはここが違う）。

集計は日次ワークフローが Issue に出す。**未処理 0 件の日は Issue を作らない**ので、
`content-report` ラベルの open Issue が無ければその日は何もしなくてよい。

Issue に載せてよいのは次まで。

- `target_type` / `target_id`
- `reason_code` ごとの件数
- **別々の通報者**が何人いるか（`UNIQUE` があるので distinct count = 実人数）
- 対象の作成日時、対象の作者 id
- 対象が既に `deleted_at` されていないか

**`reason_text` は載せない。** 必要なら DB を直接見る。

## 2. 中身を見る

**メタデータだけで判断しない。** 通報カテゴリと実際に写っているものが食い違うのが
虚偽通報の典型なので、**実物を見る**。

1. 対象の `media_path` / `thumbnail_path` から **GCS のオブジェクト URL** を組み立て、
   ローカルへ落として **Read ツールで開く**。画像はそのまま見える
2. レビューが対象なら `comment` 本文を **PostgreSQL から読む**（§1 の `db-script-run.yml`）。
   **BigQuery には無い** — `dish_reviews` はどのデータセットにも同期されておらず、
   API もレビュー本文をログへ出していない（2026-08-24 実測）。**本文は Issue へ転記しない**

⚠️ **署名 URL を自分で作ろうとしないこと。** `StorageService.generateCdnSignedURL` 相当の
署名鍵に Claude が届くとは限らない。届かない環境で「署名 URL を貼る」手順を書くと、
その場で詰まる。**署名の要らない経路（GCS の URL / アプリの `posts?ids=`）で済ませる。**

⚠️ **「200 が返った」は「見た」ではない。** 過去に、公開できたことを確認しただけで
中身を見ておらず、日本語が全部豆腐（□）のエビデンスを納品した事故がある。
**自分の目で開くまで、見たと言わない。**

⚠️ 動画は 1 フレーム目だけでは判断できないことがある。判断に効く場面が
別のところにあるなら、そう言って**オーナーへ回す**。

## 3. カテゴリを 1 つ選ぶ

処置はカテゴリに固定されている。**カテゴリを選ぶことだけが判断**である。

| カテゴリ | 具体例 | 処置 |
| --- | --- | --- |
| 法令違反・なりすまし・個人情報 | 他人の顔や表札・ナンバーが特定できる形で写る、他人になりすます | **削除** |
| スパム・広告 | 料理と無関係な宣伝、同一文面の連投 | **削除** |
| 攻撃的表現 | 特定個人・属性への攻撃 | **非表示**（可逆） |
| 事実誤認・低評価への不満 | 「まずいと書かれた」「評価が不当」 | **措置なし**（レビューは意見） |

**「どちらとも言える」ときはカテゴリを選ばない。**確信度を下げてオーナーへ回す（§5）。

### 迷いやすいところ

- **料理と無関係（`irrelevant`）は削除だが、「料理が写っていない」だけでは削除しない。**
  店内の雰囲気や器の写真は、このアプリでは正常な投稿である
- **低評価そのものは通報理由にならない。** 星 1 でも、体験の記述なら措置なし
- **「まずい」は攻撃的表現ではない。** 味の評価はレビューの本体である。
  攻撃的表現に当たるのは、料理ではなく**人**に向いているとき

## 4. 虚偽通報を見分ける

**通報者側の信号**と**中身との一致**の 2 つで見る。片方だけでは決めない。

| 信号 | 何を疑うか | 見方 |
| --- | --- | --- |
| **カテゴリと中身が食い違う** | 一番強い信号。`sexual` の通報で普通の料理写真 | §2 で実物を見た結果 |
| 同一通報者が短期間に多数を通報 | 濫用 | `reporter_user_id` ごとの件数と時間分布 |
| 通報が**特定の 1 人の投稿に集中** | 嫌がらせ | 対象の作者 id で束ねる |
| 通報者に他の活動が無い | 捨てアカ | 匿名ユーザーは `users` 行が無いのが**正常**。これ単独では根拠にならない |
| 対象が古く、それまで無通報 | 掘り起こし | 対象の `created_at` と通報の `created_at` の差 |

⚠️ **匿名ユーザーであることを虚偽の根拠にしない。** 通報の敷居を上げないために
匿名を許可しているので（オーナー確定仕様）、匿名＝怪しいと扱うと設計意図を壊す。

### 別々の通報者が N 人集まったとき

閾値がやってよいのは **確認キューへ積むこと**だけ。
**自動で消さない。自動で非表示にもしない。**
「複数人が同じものを通報した」は、優先して見る理由であって、処置の根拠ではない。

## 5. 確信度と、オーナーへの回し方

**すべての判定に確信度を添える。**

| 確信度 | 意味 | 出すもの |
| --- | --- | --- |
| **高** | 見れば分かる。カテゴリが一意に決まる | カテゴリ・根拠（何が写っていたか）・推奨処置 |
| **低** | 文脈次第、判断が割れる、動画で場面を追い切れない | **判断しない。**下の 2 つの URL と、迷った理由を出す |

### 低いときの導線 — 画面は作らない

**アプリに管理画面を追加しない。** GitHub Issue のコメントで完結させる。

Claude が Issue コメントへ **2 つの URL** を貼る（**画像そのものは貼らない**）。

| URL | 何のため |
| --- | --- |
| `https://<アプリのホスト>/{locale}/posts?ids=<dish_media_id>` | **アプリの公開ルート**。画像も動画もそのまま再生できる。特別な権限が要らない |
| GCS のオブジェクト URL（署名なし） | アプリ側で再生できないときの逃げ道。バケットの所有者であるオーナーはコンソール経由で見られる |

- オーナーがどちらかを開いて実物を見る
- Issue へ **番号で返す**: `1: 削除 / 2: 非表示 / 3: 措置なし`

`posts?ids=` を使うのは、**Claude が署名鍵に届かなくても成立する**からである
（`app/[locale]/(tabs)/posts.tsx` が `ids` を受けて `v1/dish-media` から組み立てる公開ルート）。

管理画面を作らない理由:

- 認証・権限・監査ログが要り、**アプリの攻撃面が増える**。通報という
  一番荒れやすい機能のために増やす面ではない
- 通報は日に数件の規模で、専用画面の運用コストに見合わない
- Issue なら**判断の記録がそのまま残る**。誰がいつ何を承認したかを後から追える

## 6. 実行する

**承認があったものだけ**を実行する。承認は**その 1 件ぶん**で、
別の通報や後日の同種案件には効かない。

- 削除は `DELETE /v1/dish-media/:id` / `DELETE /v1/dish-reviews/:id` を使う。
  **DB を直接 UPDATE しない**（API 側の論理削除の作法・`lock_no`・
  巻き込み範囲の判断がすべて飛ぶ）
- 実行したら `content_reports.status` を `actioned` / `rejected` へ、
  `resolved_at` と `resolution_note` を埋める
- **`resolution_note` に `reason_text` を写さない**

### 削除の巻き込み範囲を先に確認する

`dish_media` と `dish_reviews` の削除は**巻き込み範囲が違う**。
「投稿を消したらレビューも消える」と思い込まないこと。
現行の仕様は #1513 / PR #1531 に総当たりの表がある。**実行前にそこを見る。**

## 7. 書き方

Issue コメントには次を書く。**書かないものも決まっている。**

書く: 対象の種別と id / 通報件数と別々の通報者数 / `reason_code` の内訳 /
**実物を見て何が写っていたか** / カテゴリ判定 / 確信度 / 推奨処置 / `posts?ids=` と GCS の URL

書かない: `reason_text` / 通報者の id / 対象作者の個人情報 / 画像そのもの

見ていないものを見たと書かない。動画を最後まで確認していないなら、そう書く。
