# Error Triage

#1196 の仕組みが自動起票した Issue を人間の判断へ橋渡しするためのスキル。

このスキルを使うときは、次を順に読み、すべて適用する。

1. [`TRIAGE.md`](./TRIAGE.md) — 1件を捌く手順と判断の型。**反証された仮説の実例**もここ
2. [`FORENSICS.md`](./FORENSICS.md) — 根本原因を確定させる BigQuery の掘り方と、既知の落とし穴
3. [`CLUSTERING.md`](./CLUSTERING.md) — 「重複してそう」を正しく畳む方法
4. [`DOMAIN.md`](./DOMAIN.md) — **このプロダクトでそのエラーが何を意味するか**。ログとコードだけでは
   読めない前提（fallback の設計意図、除外ルールの実態、非同期境界）と、コードへ日本語コメントを残す手順

**役割分担**（追記先を迷ったらこの表で決める。同じことを2ファイルに書かない）:

| | 何を書くか | 書かないこと |
|---|---|---|
| TRIAGE.md | 判断の型、close / skip の使い分け、反証された仮説 | クエリ、プロダクト固有の前提 |
| FORENSICS.md | クエリの書き方、ログの構造、BigQuery の落とし穴 | 判断基準、業務的な意味 |
| CLUSTERING.md | 重複の類型、束ね方 | 個別の根本原因 |
| DOMAIN.md | プロダクト固有の前提・設計意図・数値の意味 | 手順（TRIAGE） / クエリ（FORENSICS） |

修正が必要と判断した Issue の実装は、このスキルでは扱わない。`.claude/skills/parallel-development` へ引き渡す。

## 最初に頭へ入れること

**Issue 本文の `messagePattern` は正規化で情報が落ちている。** 特に「1行目だけ残す」ルールは、メッセージが2行目以降にあるエラー（Prisma が典型）で診断情報を丸ごと捨てる。実例として、25人が踏んでいた障害が Issue 上では

```
| **何が** | `PrismaClientKnownRequestError:` |
```

としか出ておらず、これだけでは「どのPrismaエラーか」が判断できなかった。BigQuery を引いて初めて

```
Invalid `prisma.dish_media_views.create()` invocation:
Foreign key constraint violated on the constraint: `dish_media_views_impression_id_fkey`
```

と分かった。

**したがって、Issue 本文だけで close / skip を決めてはいけない。** 数字（件数・影響ユーザー数）は信用してよいが、原因の記述は不完全である前提で FORENSICS.md の手順を踏む。

## 原則

- **推測で分類しない。** 「たぶん海外だけ」「たぶんフォールバックしてる」は、実データで確かめるまで仮説として扱う。初回トリアージでは、この種の仮説が2件とも実データで覆った（→ TRIAGE.md「反証された仮説の例」）。
- **原因と影響範囲を混同しない。** 「真因は X だった」と「誰が影響を受けているか」は別の問いで、オーナーが見ているのは多くの場合後者（→ DOMAIN.md §1）。
- **`err/skip` は恒久無視。** 一度付けると以後そのfingerprintは二度と起票されない。「今は直さない」と「永久に見なくてよい」は違う。前者は close だけで足りる（close 後に再発すれば自動 reopen される）。
- **重複を畳む前に、本当に同一根本原因かを確認する。** 連鎖（Aの失敗がBを引き起こす）は別Issueとして残す価値がある。
- **ログレベルの軸は「深刻さ」ではなく「人間の対応が要るか」。** `error` = 回復不能で人手が要る、`warn` = 設計どおり回復した。そして**回復可能かを知っているのは呼び出し元だけ**なので、低レイヤの I/O 関数が `error` を宣言してはいけない（`logger.error` + `throw` の log-and-throw は二重記録＋レベル矛盾を生むアンチパターン）。定義と実例は TRIAGE.md「ログレベルの定義」。
- **severity が間違っているだけのものは、Issue を消すのではなくアプリ側のログレベルを直す。** ただし直してよいのは**メソッド専用 catch の 1 行**まで。汎用 catch は触らず `err/skip` で畳む（→ TRIAGE.md「境界」）。SQL の除外ルールへ足すのは最後の手段（除外は「見えなくする」ので、後から気づけない）。**例外は「同じ事象が文言で割れて `err/skip` が終わらない」場合**で、このときだけ正規化フィールドで畳む（→ TRIAGE.md「`err/skip` で止まらないエラーがある」）。
- **影響ユーザー数は 25h 窓の値**で、run をまたいで合算されない。「1日あたり何人」として読む。
- **未認証ユーザーは `affectedUsers` に入らない。** `anonymousOccurrences` が別枠にある。サインアップ・ログイン経路の障害はここを見ないと過小評価する。

## 1日の流れ

```
schedule（09:00 JST）で自動起票
   ↓
新規Issueを一覧（error-triage ラベル / open）
   ↓
クラスタリング（CLUSTERING.md）── 同一根本原因ごとに束ねる
   ↓
束ごとに調査（FORENSICS.md）── BigQuery で根本原因を確定
   ↓
判断（TRIAGE.md）── 対応 / スキップ / 重複 / severity誤り
   ↓
修正が要るもの → parallel-development へ
   ↓
★ 振り返り（下記）── スキル自身を更新する。ここまでやって1周が終わる
```

**束ねてから調査する。** 1件ずつ調べると、同じ根本原因を何度も掘ることになる。初回は 20 件のうち 7 件が単一の根本原因（Google Places の日次クォータ枯渇）だった。

## 振り返り — 1周ごとにスキルを更新する（必須）

**トリアージを1周回したら、Issue を閉じて終わりにしない。** 次の5問に順に答え、
「はい」のものだけ該当ファイルへ追記する。**この工程を飛ばした周は完了扱いにしない。**

| # | 問い | 追記先 |
|---|---|---|
| 1 | 立てた仮説が実データで覆ったか / オーナーに訂正されたか | TRIAGE.md「反証された仮説の例」 |
| 2 | 新しい重複の類型を見つけたか | CLUSTERING.md |
| 3 | 新しい BigQuery の落とし穴を踏んだか（コスト・スキーマ・欠損） | FORENSICS.md |
| 4 | プロダクト固有の前提を新たに知ったか | DOMAIN.md |
| 5 | 「コードを読んでも意図が分からず、オーナーに聞いて初めて分かった」箇所があったか | **ソースへ日本語コメント**（→ DOMAIN.md 末尾の手順） |

守ること:

- **根拠のないことを書かない。** 追記してよいのは「実データで確認した」か「オーナーが確認した」ことだけ。
  推測をスキルへ書くと、次回以降の判断がそれを前提にしてしまう。
- **既存の記述が誤っていたら、追記ではなく訂正する。** 特に「反証された仮説の例」は、
  そこに書いた結論自体が後で覆ることがある。覆ったら訂正を追記して、誤った結論を残さない。
- **数値には出所を添える。** 「N件/M人/日」は観測窓と一緒に書く。
- **更新はトリアージの PR に相乗りさせる。** スキル更新専用の PR を毎回立てない。
  ソースへの日本語コメントも同様に、その Issue の修正 PR へ載せる
  （修正が不要でコメントだけになる場合は、コメント単独の PR でよい）。
