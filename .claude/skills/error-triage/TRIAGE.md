# Triage — 1件を捌く手順と判断の型

## 手順

1. **一覧を取る。** `error-triage` ラベル / open。`<!-- fp:… -->` を持たない Issue（親 #1196 や設計 Issue）は対象外。
2. **束ねる。** CLUSTERING.md。1件ずつ調べない。
3. **束ごとに根本原因を確定させる。** FORENSICS.md。Issue 本文の要約だけで決めない。
4. **判断する。** 下の型に当てはめる。プロダクト固有の前提は DOMAIN.md を先に見る。
5. **記録して閉じる。** 判断の根拠（件数・影響ユーザー数・生ログの要点）を本文へ残す。
6. **修正が要るものを引き渡す。** parallel-development へ。
7. **振り返る。** SKILL.md「振り返り」。ここまでで1周（省略しない）。

## 判断の型

| 状況 | 操作 | 通知 | 再発時 |
|---|---|---|---|
| 直した | close（completed） | — | close + 24h 以降に 3 件以上で自動 reopen |
| 今は直さない（優先度が低いだけ） | **open のまま**。本文へ理由を書く | — | 毎日カウントが更新される |
| 恒久的に無視してよい | `err/skip` + close（not planned） | — | **二度と起票されない** |
| 重複（代表がある） | `err/skip` + close。本文へ代表 Issue 番号 | — | 代表側が追跡 |
| 旧ビルドにしか無いバグ | `err/skip` + close。本文へ commit id の根拠 | — | 現行ビルドに出たら別 fingerprint で立つ |
| severity が誤り | close せず、**アプリ側のログレベルを直す Issue** を別に立てる | — | 修正後は自然に消える |
| 調査が必要 | open のまま。調査結果を本文へ追記 | — | — |

**`err/skip` と close の使い分けを間違えない。**
`err/skip` は「永久に見なくてよい」。「今は直さない」は close でも open でもなく、
**open のまま理由を書く**のが正しい（close すると再発判定の対象になり、24h 後に勝手に reopen される）。

## ログレベルの定義（このリポジトリの標準）

**トリアージはこの定義に照らして「事実の記録として正しいか」を判定する。**

| レベル | 意味 | 判定の問い |
|---|---|---|
| `error` | **回復不能。人間の対応が必要。** | 放置すると機能が壊れたままになるか |
| `warn` | **設計どおり回復した。** フォールバック / リトライ / 代替導線が機能した | 傾向は見たいが、1件ずつ人が対応する必要はないか |
| `log` / `debug` | 通常の出来事 | — |

**軸は「深刻さ」ではなく「人間の対応が要るか」。** 外部 API が落ちること自体は深刻に見えるが、
呼び出し元が別候補へ切り替えて成功しているなら、それは**設計どおりの回復**であって error ではない。

### 回復可能かを知っているのは呼び出し元だけ

低レイヤの I/O 関数（外部 API ラッパなど）は、**自分の失敗が回復可能かを知らない**。
同じ失敗が、

- 候補が他にもある呼び出し元では → 回復可能（`warn`）
- 候補が尽きた呼び出し元では → 回復不能（`error`）

になる。したがって **低レイヤ側で `error` を宣言してはいけない。**
レベルを決める権利は、回復設計を持っている呼び出し元にある。

### log-and-throw はアンチパターン

```ts
} catch (error) {
  this.logger.error('XxxApiCallError', 'fn', { … });  // ← 自分で error として記録し
  throw error;                                         // ← そのまま投げ直す
}
```

これをやると:

1. **同一事象が二重に記録される。** 呼び出し元も catch してログを出すので、1回の失敗が 2 行になる。
2. **レベルが矛盾する。** 呼び出し元は「回復した(`warn`)」と言い、低レイヤは「エラーだ(`error`)」と言う。
   トリアージはこの矛盾を毎日 Issue として受け取ることになる。
3. **どちらが真かをログだけでは決められない。** 毎回コードを読み直す羽目になる。

**投げるなら記録しない。記録するなら投げない。**
例外を throw した時点で、その事象をどう扱うかの決定権は呼び出し元へ移っている。

実例（#1320）: `getPhotoMedia`（`api/src/core/external-api/external-api.service.ts`）が
`logger.error` + `throw` だったが、**唯一の呼び出し元** `tryGetPhotoMedia`
（`api/src/v1/locations/locations.service.ts`）はこれを catch して `PhotoMediaFallback` を
**`warn`** で記録し、次の写真候補へ進んでいた。→ `logger.warn` へ修正（1行）。

> **log-and-throw を見つけても、機械的に全部直しに行かない。**
> 直すのは、いま起票されていて判断の対象になっている fingerprint の分だけ。
> リポジトリ横断の一括修正はトリアージの仕事ではない。

## severity が誤っているとき

「`error` ではなく `warn` が適切」と判断した場合、**Issue を消すのではなくアプリ側を直す**。

| 対処 | 効果 | 副作用 |
|---|---|---|
| アプリのログレベルを `warn` へ変更 | ✅ 根本解決。以後起票されない | 別PRが要る |
| SQL の除外ルールへ追加 | ログは `error` のまま、トリアージだけ除外 | 後から気づけない |
| `err/skip` | そのfingerprintだけ無視 | 類似の新fingerprintは起票され続ける |

判定材料は FORENSICS.md §4。**フロントが `api_call_error` を出しているなら `warn` へ落としてはいけない。**
呼び出しは失敗しており、ユーザーに見えている。
ただし「呼び出しが失敗した」と「ユーザーが詰んだ」は別で、退避導線のログまで見る（DOMAIN.md §2）。

### 「ログレベルを直す」と「`err/skip` で畳む」の境界

どちらもできる場面がある。**差分が 1 行で済むかどうかで決める。**

| 状況 | 対応 |
|---|---|
| **メソッド専用の catch** で、そのメソッドの失敗の意味が一意に決まる | ログレベルを直す（1行）。`err/skip` は不要 |
| **汎用 catch**（ループの per-item catch、何でも拾う `catch (error)`） | **触らない。`err/skip` で畳む。** レベルを分けるには例外の種類で分岐する必要があり、固有ロジックが増える |
| 「解消しない」と決めた失敗で、レベル自体は正しい | `err/skip` のみ。実装 0 行（→ DOMAIN.md §2-1） |

実例（2026-08-15、オーナー確定）:

| | 対応 | 理由 |
|---|---|---|
| `getPhotoMedia` の `GooglePlacesPhotosAPICallError`（#1320） | `logger.error` → `logger.warn`（1行） | メソッド専用 catch。唯一の呼び出し元が回復設計（候補の順次試行）を持つ |
| `dishes.service.ts` の `BulkImportPlaceError`（#1334） | **触らず `err/skip`** | place ごとの汎用 catch。ここを warn にすると本物のコード例外まで埋まる。例外の種類で分岐を足すのは、前回差し戻されたパターンそのもの |

> オーナーの原則: 「ソースコード上、本来エラーじゃないのにエラーで走るのはおかしい。
> ただし固有のロジックが増えすぎて API がめちゃくちゃになるなら入れない。
> **単純にログレベルを変えるだけで済むなら、入れた方がいい。**」

## 修正の大きさを、問題の大きさに合わせる

**このスキルで一番やらかしやすいのがここ。** トリアージは「見え方を直す」作業で、
**製品の設計を直す作業ではない**。ログレベルや起票の有無を変えたいだけなのに実装へ踏み込むと、
毎回オーナーに差し戻される。

### 禁止（オーナー明示）

- **エラーレベルを変える系で、実装をガッツリ変えない。**
  > 「今回みたいに、エラーレベルを変える系はそんなガッツリ実装変えないで欲しい。」
- **共通経路を一件のために書き換えない。** `api/src/core/filters/api-exception.filter.ts` は
  `useGlobalFilters` で**全例外**にかかる。特定の 1 グループを黙らせるために触るのは NG。
  > 「この共通関数を変えるのはNGでしょ。」
- **一件を分類するためだけに型・モジュールを新設しない。**
  > 「外部APIの失敗のうち『上流のクォータ枯渇』だけを型で区別するためのモジュールとか作るのは
  > 明らかに強引すぎます。（…）無理やり一件だけ外すみたいなのは辞めてください。」
- **「解消しない」と決まっている問題に、実装を足さない。** 見なくてよいなら `err/skip` で足りる。

### 直す場所は「バグっている側」

**API が仕様どおり動いているなら、たとえサーバ側で検知・救済できても触らない。**

> 「API はなにもバグってない綺麗な設計ができてる。フロントエンドのバグなのでフロントエンドで、直すように。」

「サーバでも検知できるようにしておけば再発に気づける」は**理由にならない**。
壊れた値を送っている側が直れば検知対象も消えるし、サーバ側では値を復元できない
（"大阪市" から国は推測できない）。防御的な検証をレイヤーをまたいで足すと、
**バグっていないコードに責務が増える**だけになる。

### 着手前のチェック

1. **これはトリアージの話か、製品の設計の話か。** 後者ならオーナーへ設計判断として出す。
2. **バグっているのはどの層か。** そこだけを直す。他の層は「読んで確かめた」だけで手を出さない。
3. **共通経路（グローバルフィルタ／共有定数／全例外にかかるもの）を触ろうとしていないか。**
4. **`err/skip` で足りないか。** 足りるなら実装は 0 行。
5. **差分の規模が問題の規模に釣り合っているか。**
   実例: 「日次クォータ枯渇は解消しない」と決まっている案件に対して
   **22 ファイル / +1,785 行**を出して差し戻された。適正は `err/skip` ラベル 1 個だった。
6. **実装指示を受けていても、規模が膨らんだ時点で手を止めて確認する。**
   「教科書的な設計で」と言われて始めた作業でも、共通経路や別レイヤーへ手が伸びる規模になると
   分かったら、実装して見せるのではなく先に規模を出す —
   「この案件の実害は X。実装すると Y ファイルで共通フィルタに触れる。`err/skip` なら 0 行。どちらにしますか」。

## `err/skip` は fingerprint 単位なので、思ったより狭く効く

fingerprint は `surface | functionName | eventName | httpStatus | route | messagePattern` から
合成され、**`messagePattern` を含む**。

つまり「Google Places のクォータ枯渇」に `err/skip` を付けても、
**同じ関数の他の失敗（認証失敗・上流 5xx・レスポンス形式変更）はメッセージが違うので別 fingerprint** となり、
従来どおり起票される。

**「skip すると同じ関数の障害が全部隠れる」は誤り。** この誤解から
「専用イベント名を新設して分離してから skip する」という遠回りをして差し戻された。
分離は最初から不要で、**fingerprint が既にメッセージで判別している**。

逆に注意すべきは、メッセージが正規化で潰れて別事象が同一 fingerprint に入る場合。
skip する前に FORENSICS.md で生ログのメッセージを確認する。

## `err/skip` で止まらないエラーがある — 文言で割れる事象

上の「狭く効く」は両刃である。**同じ事象が発生源ごとに違う文言で出るとき、`err/skip` は
モグラ叩きになる。** 1件 skip しても、次の run で文言違いの新しい Issue が立つ。

実例（#1196 / 2026-08）。「端末が現在地を返せない」というひとつの事象が、

- event 名 2 種（`current_location_fetch_failed` / `current_location_failed`。log-and-throw で二重記録）
- OS ごとの文言 9 種（Android / iOS / Web で `getCurrentPositionAsync` の文言が全部違う）
- 経路 3 種

に割れ、**最大 54 通りの fingerprint** を生む。実際に 10 件が起票され、skip しても止まらなかった。

### 見分け方

新規 Issue を一覧したとき、**タイトルが似ているのに fingerprint が違うものが3件以上並んでいたら**これを疑う。
確認は「文言を除いたら同じか」— FORENSICS.md で生ログを引き、`payload` に
**すでに正規化された分類フィールド**（`kind` / `code` のような、値が数個に閉じている列）が
あるかを見る。あれば、それが畳む先である。

### 処置 — 例外的に SQL の除外ルールへ足す

このスキルの原則は「除外ルールへ足すのは最後の手段」（除外は見えなくするので後から気づけない）だが、
**文言で割れる事象はこの例外にあたる。** `err/skip` を積み増しても運用が終わらないので、
正規化フィールドで畳むしかない。

ただし足すときは、**必ず event 名などで対象範囲を閉じること。** 値だけで判定してはいけない。

> `kind` は payload の汎用キーである。`kind IN ('denied','timeout','unavailable')` とだけ書くと、
> 将来まったく別の機能が `kind: 'timeout'` を積んだ瞬間、**その不具合が理由も告げずに除外される。**

判断の軸は**どちらの失敗が見えるか**である。

| 失敗の向き | 起きること | 気づけるか |
|---|---|---|
| 除外が狭すぎた | Issue が立つ | **見える**（うるさいだけ。次の周で直せる） |
| 除外が広すぎた | Issue が立たない | **見えない**（障害が起きていても分からない） |

**見えるほうの失敗へ倒す。** 上の実例では `STARTS_WITH(eventName, 'current_location_')` で閉じた
（将来 event が増えても効くよう前方一致にし、命名規約だけを前提にした）。

### 足したあとに必ず確認すること

除外ルールの変更は**過去ログに対して実測で検証できる**。最低この2つを数える。

1. **旧ルールで除外されていて、新ルールで残るもの** — 0 でなければ退行である
2. **新しい条件に巻き込まれる無関係な行** — 0 でなければ範囲が広すぎる

上の実例では 1,122 件除外 / 退行 0 件 / 巻き込み 0 件 を確認してからマージした。

**識別子（`EXCLUSION_REASONS`）が実態と合っているかも見る。** `user_denied_permission` のまま
timeout を畳むと、オーナーが読む run サマリの除外内訳が嘘になる（→ `device_location_failed` へ改名した）。

## 反証された仮説の例

いずれも「ありそう」に見えたが、実データで否定された。**推測で分類しない**ことの実例として残す。
**ここに書いた結論自体が後で覆ることがある。覆ったら訂正を書き足す**（誤った結論を残さない）。

### 「原因が海外地点の話であればスキップで良い」（初回）

→ **真因は課金枯渇だった。**

```
Claude API request failed: 400
  "Your credit balance is too low to access the Anthropic API."
→ 1,456 件 / 208 人/日
```

`callClaudeAPI` / `fallbackToClaude` / `generateDishCategoryRecommendations` /
external の 400 は、すべてこれ1つが原因だった。スキップしていたら
**208人/日が影響を受け続ける課金切れを見逃していた**。

> **訂正（オーナー確認）**: このとき「地理は無関係だった」と結論したのは誤り。
> **原因（課金枯渇）と影響範囲（誰が影響を受けるか）を混同していた。**
> 日本の住所は gate whitelist（`region:country:JP`）にマッチするので、そもそも Claude 経路へ
> 行かないのが正しい。日本のユーザーがここに到達している時点で別のバグがある。
> 課金を戻しても、その問題は残る。→ DOMAIN.md §1

### 「フロントでフォールバックしてるはず。warn にすべきかな？」（初回）

→ **backend は 500 を返し、フロントは `api_call_error` を出していた。**

```
backend   searchRestaurants: Google Places 429
          "Quota exceeded for quota metric 'SearchTextRequest'
           and limit 'SearchTextRequest per day'"        682 件 / 125 人

frontend  /…/bulk-import: api_call_error (500)           340 件 / 125 人
                                              ↑ 影響ユーザー数が一致
```

`warn` へ落としていたら、**日次クォータ枯渇という実障害が毎日隠れる**ことになっていた。

> **訂正（オーナー確認）**: このとき「フォールバックしていなかった」と断定したのは誤り。
> 根拠にしたのは `api_call_error` の存在だけで、その後の UX ログを見ていなかった。
> 実際には 0 件確定後に Google Maps への退避導線が出ており、`api_call_error` 340件/125人 と
> `google_maps_fallback_dialog_shown` は完全一致、うち 115人（92%）が実際に Maps を開いていた。
> **`error` のままにする判断は変わらないが、理由が違う**（ユーザーが詰んでいるからではなく、
> 実障害を毎日可視化し続けるため）。→ DOMAIN.md §2

### 「1日に25人も Prisma 関連の障害うけてるってこと？」（初回）

→ **その通りだった。** しかも Issue 本文では原因が読めなかった。

```
Issue 本文:  `PrismaClientKnownRequestError:`      ← ここで切れている
生ログ:      Invalid `prisma.dish_media_views.create()` invocation:
             Foreign key constraint violated on the constraint:
             `dish_media_views_impression_id_fkey`
```

正規化の「1行目だけ残す」ルールが、Prisma のようにメッセージが2行目以降にある
エラーで診断情報を全部落としていた。**数字は信用してよいが、原因の記述は不完全**という
このスキルの前提はここから来ている。

### 「単発だから様子見」（2026-08-23 / 3 件まとめて外した）

1件1ユーザーの open な Issue 4 件について、**Issue 本文とコードだけで**経緯を組み立てて
オーナーへ報告した。生ログを引いたら **3 件とも違っていた。**

| # | 本文＋コードからの推測 | 生ログで分かった実際 |
|---|---|---|
| #1433 | ①旧ビルド残存 → ②サインイン失敗で放置できない | **ユーザーが同意画面でブラウザを閉じただけ**（`url_shape.error = "access_denied"`）。直後に検索へ戻って使い続けている |
| #1475 | 認証エラー画面が出てアプリが使えなくなった | **画面は出ていない。** 2 秒後に検索 API が成功。回線の一瞬の途切れ |
| #1477 | UUID でない値が混ざっていた | **`ids` が空だった**（`{"ids":[]}` → `?ids=`）。サーバ側の `"".split(",")` が `[""]` を作って落ちた |

**共通する誤りは「payload の構造化フィールドを見る前に物語を作ったこと」。** #1249 で
`error_name` / `error_code` / `status` / `provider` / `url_shape` を積むようにしたのは、
まさにこれを読むためだった。**本文の `messagePattern` が薄いときほど payload に答えがある。**

そして経緯は **その user_id の前後のイベント列**を見れば確定する。何を押して、何が出て、
そのあとアプリを使い続けたのか離脱したのか、まで分かる。`payload` 列を外せばスキャンも安い。

```sql
SELECT timestamp, jsonPayload.error_level, jsonPayload.event_name, jsonPayload.path_name
FROM `food-scroll.nanitabeyo_logs_prod.run_googleapis_com_stdout`
WHERE timestamp >= TIMESTAMP '<当日>' AND timestamp < TIMESTAMP '<翌日>'
  AND jsonPayload.log_type = 'frontend_event_logs'
  AND jsonPayload.user_id = '<user_id>'
ORDER BY timestamp
```

**「様子見」を選ぶ前に、この 2 本（payload 全体 → 当該ユーザーの時系列）を引くこと。**
4 件のうち実バグは 1 件で、残り 3 件はログレベルの誤りだった。どちらも「様子見」では永久に片付かない。

## 記録の書き方

close / skip する Issue には、**後から辿れる根拠**を残す。最低限:

- 根本原因（生ログからの引用。1〜2行）
- 件数 / 影響ユーザー数 / 匿名件数
- 判断とその理由
- 重複なら代表 Issue 番号
