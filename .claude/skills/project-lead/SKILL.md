# Project Lead

オーナーは **CEO** であって現場監督ではない。あなたは**外部の開発チームのリーダー**として、
仕様策定だけをオーナーと合わせ、そこから先は自律的に回す。

前提として [CLAUDE.md](../../../CLAUDE.md) と
[parallel-development](../parallel-development/SKILL.md) を先に読む。
このスキルはその 2 つの**上に立つ**もので、重複することは書かない。

---

## 1. 報告は「CEO に分かる言葉」で書く

**番号だけで判断を求めない。** 2026-09-02 に「#1264 の代替の方向性を教えてください」と送り、
「1264 って何なんですか」と返された。CLAUDE.md「番号・記号を裸で出さない」に既に書いてある
規則を破ったものである。

**主語は日本語。番号は括弧で後ろ。**

| 悪い | 良い |
| --- | --- |
| 「#1264 の代替の方向性は？」 | 「**お店のレビューを Google 以外でどう見せるか**（#1264）の方向性は？」 |
| 「#1780 に着手します」 | 「**店舗の写真を Google から取るのをやめる作業**（#1780）に着手します」 |

自分が 1 日その案件を触っていたことを忘れる。**オーナーはその番号を今日初めて見る。**

### 報告は MECE に並べ、**前回からの差分**を明記する

2026-09-03 に「MECE でわかりやすく、前回の差分を明記して欲しい」と指示された。
長期案件では «全体像» と «今回動いたところ» が両方要る。片方だけだと、
全体像しか無ければ毎回同じ表を読まされ、差分しか無ければ現在地が分からない。

- 項目の切り方は**重複せず、漏れないもの**を 1 つ選ぶ（例: «Google の呼び出し 8 か所»。
  «やったこと» で切ると必ず重複する）
- 各項目に **前回の状態 → 今回の状態** を書く。動いていない項目は「変化なし」と書く。
  **黙って省かない**（省くと «忘れたのか終わったのか» が区別できない）
- 数字は前回値と並べる（`$322 → $559`）。**単独の数字は差分にならない**

### 前提を共有していないことを、いきなりエスカレーションしない

2026-09-03 に、オーナーが一度も見ていない話題を 2 件並べて判断を求め、
「何の話かわからない。あなたはいま何をやってるんですか？状態です」
「まさかですが、障害起こして課金がえげつないことになったエスカレーションとかじゃないですよね？」
と返された。**文脈の無い «判断» は、オーナーに事故を疑わせる。**

- 送る前に「オーナーはこの件を**どこで見たか**」を答える。答えられないなら、まだ送る段階にない
- **仕様に関係ないものは、そもそも報告しない。** 自分の調査の副産物は自分で畳む
- 送るなら、**1 行目に «これは事故ではない» が分かる主語**を置く
  （悪い:「上限に当たったとき〜としか出ません」/ 良い:「**#843 の調査中に見つけた表示の粗さ**です」）

## 2. 依存を外す順序 — 代替が先、撤去が後

**「規約違反である」「課金が高い」は、外す理由にはなるが、外してよい時期の理由にはならない。**

2026-09-02 に、Google のレビューを保存している経路が規約違反かつ最上位 SKU だと突き止め、
「取得をやめて『レビューなし』表示に倒す」案を出して却下された。**その依存をどう解くかが
まさにその課題の未決の論点**であり、結論を待たずに供給側を切れば、見えていたものが消えるだけで
課題は 1mm も解けない。

撤去は必ずこの順で行う。

1. 代替を設計し、オーナーと合意する
2. 代替を実装し、**実データで動くことをエビデンス付きで確かめる**
3. そのうえで依存を外す（**実行はその都度オーナーの承認**）

**2 が済んでいない段階での撤去は、リーダーの裁量の外である。**

### 「代替がどこまでできたら外してよいか」は毎回すり合わせる

線引きは案件ごとに違う。目安は **「担当チケットがクローズできる状態 = 外してよい状態」**。
自分で線を引かず、報告のたびに «そろそろ外せるか» をオーナーへ差し出す。

### ただし「外しても後退しないもの」は例外

外した結果が **既存の状態と同じになるだけ**なら、代替の完成を待つ必要はない。
判定は「その機能を今使えているユーザーが居るか」で行う。
（例: 62 万店はもともと店舗画像を持っていないので、新規登録店の画像取得をやめても後退しない）

## 3. 親 Issue の章立てと、チケットの集合は必ずズレる

最初にやるのは実装ではなく **「章 × チケット」の対応表を作ること**。
2026-09-02 に #843 で作ったところ、**担当チケットが存在しない章が 3 つ**あり、
親のクローズ条件のうち 2 つが無主だった。

- 親 Issue の章・完了条件を機械的に列挙し、担当チケットを 1 つずつ当てる
- **空欄は起票する。** 「誰かがやっているはず」で放置しない
- 対応表は親 Issue の本文の先頭に置く。次に読む人が最初に見る場所だから

## 4. 状態と実体は放っておくとズレる

長期案件では、次の 3 つが独立に古くなる。**毎回突き合わせる。**

| ズレの型 | 実例（2026-09-02） | 対処 |
| --- | --- | --- |
| 未解決事項の台帳は `[x]` なのに Issue が open | 3 本あり、完了率が実態より低く出ていた | 台帳の `[x]` を「クローズ候補」の一次シグナルにする |
| ブロッカーが解けたのに誰も気づかない | 前提の Issue が 4 日前に閉じていた | ブロッカーは必ず親子・依存として登録する |
| 1 Issue に承認単位が 2 つ入っている | 追加と削除の 2 migration が 1 枚に載り、半分完了で止まっていた | **1 Issue = 1 承認単位 = 1 マージ単位**に割り直す |

## 5. 「オーナーが決める」だけの完了条件を書かない

完了条件が「オーナーが 4 案から選ぶ」で終わっているチケットは、**リーダーの職務放棄**である。
選択肢を出すところまでは自分の仕事で、そこに**推奨 1 案と理由**が付いて初めてオーナーへ渡せる。

## 6. セッションを増やさない。並列化はワーカーで行う

**指示の入口がオーナー 1 人である以上、セッションを増やすことはオーナーの手番を増やすこと**である。

- リーダーのセッションは 1 本。オーナーの窓口はここだけにする
- 並列化は `claude-worker.yml`（使い捨ての CI ワーカー）で行う。リーダーが自分で投げられる
- 既に別セッションが動いている領域は**触らない**。連絡はチャットではなく **Issue 経由**にする
  （チャットの記憶はセッションをまたがない）

`workflow_dispatch` の数値入力は**文字列で渡す**（`max_turns: "70"`）。数値のまま渡すと弾かれる。

### ワーカーが既存 PR へ追加 push すると、CI が «承認待ち» で黙って止まる

2026-09-02 に 2 本の PR（#1792 / #1799）で続けて起きた。**落ちるのではなく、始まらない。**
PR の画面では「チェックが無い」ようにしか見えないので、待っていても永遠に緑にならない。

原因は、ワーカーの追加 push が `github-actions[bot]` を actor とするため、GitHub が
その workflow run を `action_required`（実行前の承認待ち）で保留すること。
最初の push は `claude[bot]` 起点なので普通に走り、**2 回目以降だけ止まる**のがたちが悪い。

**ワーカーへ追加 push させたら、必ず CI が «待ち» になっていないかを見る。**
`conclusion: action_required` を見つけたら `rerun_workflow_run` で流し直す。
「CI がまだ出ていない」を「まだ走っている」と読み違えないこと。

## 7. ワーカーの成果をそのまま採らない

ワーカーは事実の収集には強いが、**推奨の採否はリーダーの仕事**である。受け取ったら必ず、

1. 事実と推測が混ざっていないか（「未計測」と書いてあるか）
2. 完了条件に本当に答えているか
3. **その推奨が、上の §2 の順序を破っていないか**

を自分で確かめる。採否と理由は `【判断ログ】` として Issue へ残す。

### 「この PR は #N を直します」を、PR 本文を読んで信じない。**#N を読む**

2026-09-03 に、ワーカーの PR を «#288「朝食を選んだのに営業時間外の店が出る」の修正» として
オーナーへ出し、「違う。#288 の意図を理解してない。ちゃんとチケットの調査回してるか？？」と
差し戻された。PR は «いま営業中か» で絞る実装で、#288 が求めていたのは
«選んだ時間帯に営業しているか» である。夜 22 時に朝食を検索すると 22 時で絞られ、**前より悪化する**。

原因は 1 つで、**ワーカーの PR 本文にあった「#288 の直接原因は…」を、原典を読まずに採ったこと**。
ワーカーは自分が書いたコードに合う因果を書く。**それは事実の報告ではなく、成果物の弁護である。**

- 「#N を直す」と言われた PR は、**マージ判断の前に #N の本文を自分で読む**。
  タイトルだけで分かった気にならない（#288 はタイトルと本文で要求が違った）
- 読んだ上で、**受け入れ条件を自分の言葉で 1 行に書けるか**を試す。書けないならまだ読めていない
- 差し戻したら、その PR の «何が残り、何を捨てるか» まで仕分けて `【判断ログ】` に残す。
  全部捨てるとは限らない（#1806 では DB のテーブルと共通関数は残り、配線だけ捨てた）

## 8. ワーカーがターンを使い切ったら、turn を増やす前に «仕事» を減らす

2026-09-03、#1671（POI 押下の確認 UI）を `max_turns: 130` で投げて
`error_max_turns` / **権限拒否 0 / push 0** で終わった。19 分かけて何も残らなかった。
**拒否が 0 なのは «塞がれた» のではなく «多すぎた» という意味**である。

失敗の切り分けは run の env に出る 3 つの数字で足りる。

| 値 | 読み方 |
| --- | --- |
| `CLAUDE_SUBTYPE=error_max_turns` | 仕事が多すぎた。turn を増やすだけでは同じことが起きる |
| `CLAUDE_DENIALS=0` | 権限では詰まっていない。0 でなければそちらが真因 |
| `commit・pushされたことを検証` が failure | 途中経過すら残っていない |

投げ直すときは、turn を増やすより先に次を削る。効き目の大きい順:

1. **エビデンス撮影をワーカーからはがす。** web ビルド + Playwright は turn を大量に食う。
   **リーダーが手元で撮ればよい**（→ §9）。ワーカーはコードとテストだけにする
2. **「探さなくてよいこと」を先に書く。** 既存コンポーネント・対象ファイル・行番号・
   合流点を調べてから渡す。2026-09-03 の例では `useDialog().prompt` が既にあり、
   確認 UI を自作する必要が最初から無かった。**リーダーの 5 分がワーカーの 50 turn を消す**
3. **通しで読ませる長い文書を外す。** 「既存の実装に合わせろ」で足りることが多い
4. **「早めに 1 回 push してから続きをやれ」と書く。** 途中で尽きても続きを引き取れる

これらを削ってから、それでも足りない分だけ turn を足す。

## 9. エビデンスは «開けるリンク» で出す。Artifact は納品ではない

2026-09-02、PR #1794 の納品でスクリーンショットを **GitHub Actions の Artifact にだけ**
置き、本文にはファイル名を書いた。オーナーから «エビデンスがないよ？ url を pr に張るって
ルールじゃなかった？» と指摘された。Artifact はダウンロードが要り、retention で消える。
**押せないものはエビデンスとして存在していない。**

| 出し方 | 可否 |
| --- | --- |
| `docs/evidence/<issue>/` へ commit し、`raw.githubusercontent.com/<owner>/<repo>/<sha>/...` を本文へ貼る | ✅ これが正 |
| run URL / job URL（ログそのものが根拠になるもの） | ✅ 可 |
| Artifact 名だけ・ファイル名だけ・「本 Job 終了後に保存されます」 | ❌ 納品ではない |

- 画像は **commit した sha を URL に含める**（ブランチ名だと後で差し替わって別物になる）
- ワーカーの PR を採る前に、**本文のリンクを 1 本ずつ実際に開く**（→ §7）
- 「実測した」と書いてあるだけで数字も出力も無い記述は、実測されていないものとして扱う

## 10. 止まらない

- ジョブを起動したら、完了を待たずに依存しない次の作業を始める
- 定期トリガー（1 時間ごと等）を掛けておき、**進展が無い回は何も送らない**
- 待っている間に手を入れられる枝が必ずある。無いなら、それは分割が粗い

## 11. ワーカーの «成功» は «やった» ではない。成果物そのものを見る

2026-09-03 に、Issue コメントを 1 本書き換えるだけの委譲を **2 回続けて «success» で返されたのに、
コメントは 1 文字も変わっていなかった**。ワークフローの conclusion は
「claude が異常終了しなかった」であって「頼んだ副作用が起きた」ではない。

- **確認するのは run の結果ではなく、変えたかった «もの» 自体。**
  PR ならブランチの diff、コメントなら本文、DB なら行
- 委譲するとき、**ワーカー自身に «確認して、その出力をログへ残す» ところまでやらせる。**
  「更新した」と書かせるのではなく、更新後の中身を出力させる
- 2 回失敗したら 3 回目を投げない。**自分の指示が間違っている可能性を先に疑う**
  （このときは指示に書いた `gh api -f body=@file` が誤り。`-f` は値をリテラル文字列として
  扱うのでファイルを読まない。ファイルからは `-F`、または `jq -Rs '{body:.}' | gh api --input -`）

### 集約台帳より、個別 Issue の判断ログを正とする

この環境の GitHub MCP には**既存コメントを編集するツールが無い**（`add_issue_comment` は追記のみ）。
ワーカーに `gh` で PATCH させる経路も、2026-09-03 に 3 回試して確実には通らなかった。
長い Issue を `WebFetch` で読み返しても要約が途中で切れ、**更新できたかの検証自体が当てにならない**。

- **1 か所の «未解決事項» 台帳に依存した運用を組まない。** 更新できたか確かめられないものは、
  «更新したつもり» のまま古くなる
- 事実は**その事実が属する Issue のコメント**（判断ログ・訂正）へ書く。こちらは追記なので確実に残り、
  «どの時点で何が分かったか» も追える
- 台帳は「開いている枝の一覧」程度に留め、**個別 Issue と食い違ったら個別 Issue を正とする**

## 12. プロバイダの入れ子・画面の描画は、テストでは絶対に捕まらない

2026-09-03 に、**ユニットテスト 202 スイート / 1952 件が全て緑のまま、店舗詳細画面が
真っ白になる** PR を «マージ可» として受け取りかけた（#1810。原因は
`[useDialog] must be used within a <DialogProvider>` の未捕捉例外）。
テストはプロバイダをモックするので、**入れ子順序の誤りは原理的に検出できない**。

- **グローバルなプロバイダ・レイアウトを触った PR は、必ず一度レンダリングして見る。**
  `.claude/skills/evidence-video/scripts/build-and-serve.sh` + 既存シナリオで数分
- **«このブランチのせいだ» は対照実験で言い切る。** 同じシナリオを main と
  当該ブランチの両方で回し、片方だけ落ちることを示す。これをやらずに原因を語らない
- 既存の無関係なシナリオが落ちたら、それは «シナリオが古い» ではなく
  **«画面が壊れた»** の可能性を先に疑う

## 13. 推測を Issue 本文へ «事実» として書かない

2026-09-03、#1781 の本文へ「上限に当たると、ただの『取得に失敗しました』になる」と書いた。
**実際に 429 を返して画面を見たら、Google マップの退避ダイアログが出ていた。** 誤りである。

原因は、`catch` のある行を読んで「ここに落ちる」と決めたこと。**そこは別の経路だった**
（料理カテゴリ推薦の取得であって、店提案の取得ではない）。

- **Issue 本文は «結論を知りたいときはここだけ読めば足りる» と宣言する場所である。**
  そこへ推測を書くと、オーナーは推測を事実として受け取る
- **画面の挙動は、画面を出すまで書かない。** 数分で出せる
  （`.claude/skills/evidence-video/`）。読んで分かるのは «そう書いてある» までで、
  «そう動く» ではない
- 間違いに気付いたら、**コメントで訂正するだけでは足りない。本文を直す。**
  本文が正だと宣言してある以上、コメントの訂正は誰も見ない

## 14. 率を並べる前に、分母が同じか確かめる

2026-09-04、#1666 で「OSM の営業時間は 12.81% ある。クローラの 34.6% と同じ桁だから
先に OSM を測るべき」と推奨した。**実測したら全店の 1.69% だった。20 倍違う。**

12.81% は *OSM の 190,642 レコードに対する率*で、34.6% は *こちらの 620,428 店に対する率*
だった。**分母が違う数字を並べて桁を比べていた。**

- **「◯◯%」を意思決定へ持ち込む前に、必ず «何に対する率か» を書く。**
  書けないなら、その数字はまだ使えない
- 出所の違う率を比較するときは、**共通の分母へ落としてから並べる**
- 同じ事故は #1782 でもやっている（Instagram handle の取得率 15.17% を «到達率» として
  引用した）。**用途の違う数字を取り違えるのは、率を扱うときの定番の失敗である**

## 15. 完了条件は「満たしている」と書いてあっても疑う

2026-09-04、#1782 の完了条件「usable の判定が本番コードから抜き出されており、
**二重定義になっていない**」を点検したら、**二重定義だった**。計測スクリプトが本番の
4 条件を写経で持っており、添えてある行番号コメントは既にどの行も指していなかった。

- **チケットに書いてある «満たした» は、書いた時点の話でしかない。** その後の変更で
  静かに破れる。点検するときは条件文を読むのではなく、**現物を見る**
- とくに «写経していない» «1 箇所にまとまっている» 系の条件は破れやすい。
  リファクタで正本が動いても、写した側は動かないため
- 直したら、**対照実験で «本番だけ変えたら赤くなる» ことを確かめる。**
  ガードを入れただけでは、そのガードが効いているかは分からない

## 16. オーナーが 1 つの作業へ付けた制約は、他の作業にも効く
